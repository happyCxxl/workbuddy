# 04 · 设计概览

> 本文件回答：系统整体怎么设计的、核心取舍是什么。
> 只写**概览与取舍**；API 细节见 `07-接口`，数据细节见 `06-数据`。

## 系统上下文

> 本系统在更大技术版图中的位置：依赖什么、被谁依赖。

- 浏览器 SPA（`web/`）→ `biz` HTTP 接口；`biz` 调 `worker`（算法）、`model`（模型网关 → 外部模型服务）、`auth`（JWT 鉴权）、`file`（本地 / MinIO 存储）、`infra`（DB 基类与 Redis / 限流）、`vector`（Milvus 适配）。
- 外部依赖：MySQL、Redis、MinIO、Milvus（docker 编排）；模型供应商 API 由 `model` 模块对接。

## 核心设计思路

> 方案策略：分层方式、核心机制、这样组织的理由。

- 五层：契约层（`common`）/ 基础层（`infra`）/ 适配层（`file`、`vector`、`model`）/ 算法层（`worker`）/ 应用层（`biz`）。
- 模块按职责划分，依赖只可自上而下；结构由 `check-modules` 把关。
- 任务执行：进程内执行池 + Redis 队列；限流走 Redis 令牌桶（bucket4j），多实例下仍有效。

## 关键取舍

> 设计中做过的权衡：选了什么、放弃了什么、代价是什么。

- 单体多模块，不做微服务拆分：单人维护成本优先，模块边界由 Maven 强制。
- 进程内队列，不引入独立消息中间件：当前并发规模下单机足够。
- 存储双实现（本地 / MinIO），由 `StorageProvider` 路由：开发期免依赖容器，运行期可切换对象存储。
