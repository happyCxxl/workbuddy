### 模块并入基础设施的判定（vector 与 file 的取舍记录）

判定只看四条，不按“模块大小”或“代码行数”决定：

1. **是否纯技术适配**：只封装外部系统的连接、协议与生命周期，不含业务判断；
2. **是否持有领域数据**：有没有自己的业务表、状态机与生命周期；
3. **依赖方向**：并入后是否让基础层反向承载业务、放大下游模块的依赖面；
4. **门禁与演进**：测试/覆盖率口径是否与基础设施一致，后续替换后端是否应独立演进。

按此判定：

- **vector 并入**：仅封装 Milvus 客户端生命周期、集合管理与查询口径，无领域表、无 Controller、无自动配置；只被 worker 使用且只依赖 common。并入后模块图少一个叶子节点，`worker → infra` 方向不变，符合第 1、3、4 条。
- **file 不并入**：`file` 持有 `wb_file_object` 档案与存储路由、数据源一致性、上传/下载语义，是领域服务而非适配器；`file` 依赖 `infra` 属于正常向下依赖，反向并入会让 `infra` 同时承载“基础设施 + 文件业务”，依赖它的模块被动获得文件领域语义，违反第 2、3 条；其测试口径与对象存储后端的独立演进也不适合并入（第 4 条）。
- **对象存储适配下沉**：MinIO / 本地磁盘的 SPI、连接参数与实现只封装外部系统，无领域表；`file` 保留档案持久化、内容寻址与存储源路由，通过 `file → infra` 使用适配器，符合第 1、3 条。

被否方案：`file` 并入 `infra`（不采用，理由如上）；`vector` 保持独立模块（不采用，收益仅是形式上的模块隔离，代价是多一个 pom、多一条依赖边与分散的 Milvus 版本管理）。
