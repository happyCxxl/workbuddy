## 0. 目标、范围与执行协议

**目标**：把两份文档中的全部可修复项（审计 30 项 + 复核新增 10 遗漏 + 8 未覆盖实例）按依赖关系组织成可执行、可复跑、不违背现行规范的修复批次。

**执行协议（用户新增约束，优先级最高）**：
1. 修复按「批次 → 条目」推进，每个条目为一步。
2. **每步只做修改，不执行任何 git add / commit**；改完立即停下，报告：改动文件清单 + 关键 diff 摘要 + 验证结果 + 未决问题。
3. 用户查看变动（`git status` / `git diff`），**确认无误后才提交该步**（Conventional Commits + 中文 + scope，规范与代码仍分开提交）；不确认则按用户意见调整，仍不提交。
4. 提交完成、且用户同意后，才进入下一步修改。
5. 每批的最后一步附该批的验证命令结果；任何门禁/检查失败都先报告，绝不 `--no-verify` 绕过。

**为什么这样修——总原则**：
1. **规范先于代码、分开提交**（common/06 §6.1:49）。
2. **最小改动**（common/02）：优先改一行文案而非引入新机制。
3. **不新增第三方依赖**（根 AGENTS.md Never#4）：P3-9 手写轮询断言，P3-5 不加 eslint-plugin-import。
4. **门禁只收紧不放宽**（Never#5）：checkstyle 加 PackageName 是收紧；门禁/钩子脚本改动均在本计划内获批。
5. **不为存量立规**（JAVA-META-002）：无规则可挂的 SpotBugs 豁免选择改代码消除。
6. **等级语义决定执行方式**：JAVA-LOG-004【应该】→ 补代码不加机器阻断；TEST-011「信号、不阻断」→ 按信号处置。
7. **单一事实源**：接入点、目录地图、检查器文案只在一处维护。
8. **写文件一律用代理写工具**（Never#1），每步提交信息符合规范，每批附验证命令（WORK-05）。
