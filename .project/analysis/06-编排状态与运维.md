# 编排、状态与运维：现状、问题与优化方案

> 本文件是 `.project/analysis/` 专题分册之一，覆盖任务触发、消费、状态机、产物持久化、上游门禁与运维。
> 结论基于源码静态审查，未启动服务、未运行测试；未运行时验证的判断标 `[推断]`。

## 1. 环节职责与边界

- 任务模型：`wb_knowledge_pipeline_task`，按 `(fileResultId, stage, upstreamProductId, strategyVersionId)` 标识一次执行；
- 触发：控制面 API → `TaskTriggerSupport.trigger` → 执行键查重 → 新建 QUEUED → Redis 叫醒；
- 消费：`PipelineTaskConsumer` 扫库领批 → 按 stage 分发 Runner；
- 状态：QUEUED / RUNNING / SUCCESS / PARTIAL_SUCCESS / FAILED；
- 产物：`wb_knowledge_pipeline_product` + 对象存储单 JSON；
- 运维：watchdog 超时、启动补偿、上游门禁、存储源切换。

## 2. 真实执行流程

1. 上传 `/files`：扩展名白名单 → 100MB → 空文件 → Tika 魔数 → OOXML protected / 保留图片 → 格式白名单 → 写对象存储；
2. 提交 `KnowledgeBaseFileServiceImpl.submit`：`requestId` 幂等 → 文件校验（重读、sha256、大小双源、Tika、试解析）→ 同库 sha256 去重 → 短事务三写 `wb_source_file` / `wb_file_result` / `wb_submit_log`；**不建任务**；
3. 解析触发 `ParseControlServiceImpl.parse` → `TaskTriggerSupport.trigger`：执行键查重；已有任务任何状态一律拒绝 40431；新建 QUEUED 入 Redis；
4. `PipelineTaskConsumer`：Redis BRPOP 叫醒 → 扫库领批 QUEUED → 按 stage 分发到 Runner；watchdog 按环节超时；`claim` 用条件更新 QUEUED→RUNNING；
5. Runner 执行：读上游产物 → 算法 → `TaskRunnerSupport.complete` 写产物 + step log + 终态；
6. 下游触发：人工再次调用控制面，指定上游产物；
7. 启动补偿：`TaskStartupCompensator` 每分钟重投 stale QUEUED。

## 3. 问题清单

| #    | 问题                     | 代码证据                                                                                   | 影响                                                 | 层级        |
|------|--------------------------|--------------------------------------------------------------------------------------------|------------------------------------------------------|-------------|
| O-01 | 全链路人工逐环节         | `TaskTriggerSupport` 注释与 `ParseControlService` 注释均写“完成后停在终态，不自动触发下游” | 每文件 5 次点击；批量入库不可行                      | 编排模型    |
| O-02 | 失败不可重跑             | 执行键唯一 + 已有任务任何状态拒绝 + 无 attempt 字段 + 无重触发接口                         | 一次失败整条链报废                                   | 任务模型    |
| O-03 | 同内容重提被拒           | `KnowledgeBaseFileServiceImpl.rejectDuplicateInKb` 按 sha256 查同库已有文件结果            | 解析失败后连“重新提交”这条后路也没有                 | 去重口径    |
| O-04 | 并发全局 2               | `knowledge.task.concurrency=2`，单池承载 5 个环节                                          | 一个慢解析阻塞所有文档的所有环节                     | 资源模型    |
| O-05 | 超时后产物可能仍落库     | `ProductPersistence.persist` 只校验存储源，不检查任务是否已 FAILED                         | 失败任务留下孤儿产物；下游靠门禁拒绝但空间泄漏       | 并发/一致性 |
| O-06 | PARTIAL_SUCCESS 直接放行 | `UpstreamProductGate` 对 SUCCESS/PARTIAL 都放行，PARTIAL 只 log.warn                       | 下游把缺页解析当完整输入                             | 状态语义    |
| O-07 | 切换存储源会卡住整条链   | `ChainStorageSupport.requireStorageMatch` 在触发/产物写入时校验                            | 换存储后旧文件无法继续处理                           | 存储模型    |
| O-08 | 无迁移框架               | 档案明确“尚无 Flyway/Liquibase”                                                            | 修列宽/加字段成本高，容易漂移                        | 数据运维    |
| O-09 | 测试固化缺陷             | `PipelineTaskConsumerTest` 断言 BUILD_INDEX “不在五路分发内”；图片占位片有测试守护         | 缺陷长期存活，门禁全绿                               | 验证体系    |
| O-10 | `BUILD_INDEX` 任务空转   | `TaskStartupCompensator` 每分钟重投 stale QUEUED；BUILD_INDEX 无消费者                     | 永久 QUEUED；补偿器反复投递                          | 接线缺口    |
| O-11 | 产物先写后判终态         | `ProductPersistence.persist` 先写对象存储，再写 DB 行，最后更新任务产物引用                | 任一步失败留下孤儿对象/半成品                        | 持久化顺序  |
| O-12 | 步骤日志与产物分开写     | `stepLogPersistence.save` 在 `productPersistence.persist` 之后                             | 产物成功但 step log 失败时，任务状态与排障信息不一致 | 持久化顺序  |
| O-13 | 无任务 attempt/审计      | `WbPipelineTask` 无 attempt；失败原因只在 error 字段                                       | 无法区分“第几次执行”，无法做重试统计                 | 任务模型    |

## 4. 根因

1. 任务模型是“一次性幂等作业”，不是“可重试流水线”：执行键唯一、无 attempt、无重跑、无自动下游。
2. 控制面把“触发”当“执行”，没有编排层：每个环节独立 API，下游依赖人工指定上游产物。
3. 状态机把“算法局部失败”和“内容完整”混为一谈：PARTIAL_SUCCESS 直接放行，失败页不隔离。
4. 产物持久化与任务终态没有互斥：先写产物、后判状态，失败会留下半成品。
5. 去重口径基于“文件结果存在”，不区分成败：失败后无法重新提交同内容。
6. 运维基础设施缺失：无迁移框架、无任务重试/审计、补偿器只重投不区分环节。

## 5. 可复用骨架

| 能力       | 现状                                               | 可复用性                |
|------------|----------------------------------------------------|-------------------------|
| 触发查重   | `TaskTriggerSupport` 已有执行键/Redis 叫醒         | 高；需要加 attempt/重跑 |
| 消费循环   | `PipelineTaskConsumer` 已有扫库/领批/分发/watchdog | 高；需要加 BUILD_INDEX  |
| 状态回写   | `TaskRunnerSupport` 已统一 complete/fail           | 高；需要加产物互斥      |
| 上游门禁   | `UpstreamProductGate` 已有 SUCCESS/PARTIAL 规则    | 中；需要区分质量        |
| 启动补偿   | `TaskStartupCompensator` 已有 stale QUEUED 重投    | 中；需要按环节/attempt  |
| 产物持久化 | `ProductPersistence` 已有对象存储 + DB 行          | 中；需要顺序/事务       |
| 存储源路由 | `ChainStorageSupport` 已有匹配校验                 | 高；需要迁移策略        |

## 6. 优化方向

### 6.1 先让链路可重跑

1. **任务 attempt**：任务表加 `attempt`/`parentTaskId`；执行键带 attempt；FAILED 任务允许新执行。
2. **重触发接口**：按文件结果/环节重跑；同内容重提不再一律拒绝，区分“已有成功结果”和“仅有失败结果”。
3. **自动下游（可选）**：配置开关；成功后自动触发下一环节；失败/部分成功按策略停或继续。
4. **产物与终态互斥**：写产物前校验任务 RUNNING；写完产物后再置终态；失败时清理孤儿或标记。
5. **PARTIAL 语义**：上游门禁按“失败页比例/关键页缺失”决定放行/阻断；PARTIAL 带失败清单。

### 6.2 再让运维可控

6. **BUILD_INDEX 消费**：扫库阶段/dispatch 加 BUILD_INDEX；补偿器按环节区分。
7. **并发隔离**：按环节分池或按知识库限流；重任务不阻塞轻任务。
8. **迁移框架**：引入 Flyway/Liquibase（需用户批准新增依赖）；至少先做 schema 版本表。
9. **存储迁移**：`ChainStorageSupport` 增加迁移/跳过策略，不因切换存储卡死旧链。
10. **可观测性**：任务 attempt/耗时/错误码/产物 ID 进统一日志与指标；step log 与产物一致。

## 7. 讨论清单

| 顺序 | 讨论项       | 需要确认的取舍                             |
|------|--------------|--------------------------------------------|
| 1    | 重跑模型     | 加 attempt vs 新任务；执行键是否带 attempt |
| 2    | 自动下游     | 是否默认开启；失败/部分成功策略            |
| 3    | 同内容重提   | 允许重提条件；去重口径                     |
| 4    | PARTIAL 门禁 | 失败页比例阈值；关键页定义                 |
| 5    | 产物互斥     | 先写产物还是先判终态；孤儿清理             |
| 6    | 并发         | 按环节分池 vs 全局；默认并发               |
| 7    | 迁移框架     | 是否引入 Flyway；依赖审批                  |
| 8    | 存储切换     | 迁移/跳过策略；旧链处理                    |
