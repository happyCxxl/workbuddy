# .project — 项目事实档案（模板）

> 本目录记录项目的**事实**（是什么、现在怎样）；规则在项目的规范目录（如 `.agent/standards/`）。
> 用法：复制整个 `.project` 目录到项目根；把本目录的 11 份文件填好后放进 `.project/archive/`，配置写入 `.project/archive/config.json`。
> 填写方式：客观项自动采集，判断项给出候选与理由；用户逐项确认或提出修改要求，由 AI 重填。

## 通用骨架约定

1. 每份文件开头一句话说明「本文件回答什么问题」。
2. 每个字段标注填法：**AI 采**（客观事实，自动采集）或 **AI 拟**（给出候选与理由，由用户确认或修改）。
3. **字段与小节必须自带「作用」**：写明谁消费它、驱动什么动作——保证新会话与新模型不靠外部知识也能填对。
4. 不适用的字段填「无」，不删字段——结构对所有项目统一。
5. **「尚未成型」是合法值**：用于 0→1 项目的事实类字段，必须写明补齐触发点（如「首次提交后」「M1 完成时」）。与「无」的区别：**「无」是永远没有，「尚未成型」是将来会有**。
6. 文内不写规则与沿革。

## 事实来源与裁决

| 等级 | 来源                                             | 用途                                                   |
|------|--------------------------------------------------|--------------------------------------------------------|
| L1   | 代码、构建文件、编排与配置                       | 一切能从代码读出的事实只能从这里采                     |
| L2   | 运行产物：git 历史、检查器输出、测试与覆盖率报告 | 时间线与质量数字                                       |
| L3   | 项目文档（README / docs）                        | 只用于代码读不出的意图：目标、非目标、使用者、取舍理由 |

1. L3 与 L1 冲突时以 L1 为准，并把与实现不符的文档记入 `11-质量与风险` 的债务表。
2. 凡 L3 来源的字段，值后标注来源文件与核对日期。
3. 无法与代码核对的说法标【待核对】，不进事实区。

## 保鲜与漂移

- **状态文件**：`.project/archive/status.json` 记录每份档案的 `status`（`已复核` / `待复核` / `尚未成型`）、`reviewed`、`baseline`（复核时的 HEAD 短哈希）、`note`；它是**唯一的新鲜度事实源**，档案文档内不写日期。
- 复核超过 90 天视为过期。
- **提交前触发**：`.husky/pre-commit` 运行 `node .project/tools/sync.mjs --gate`——仅当提交含命中档案管辖路径的代码改动时，要求 `status.json` 同提交更新（该档案条目 `baseline` 等于当前 HEAD）；只改文档或测试不触发。配对表在 `.project/archive/config.json`。
- **更新流程**：按 `.project/prompts/sync.md` 执行。
- **结构化验证**：`node .project/tools/check-project-docs.mjs`（防写错数字；随档案更新自动执行）。

## 引擎与配置（机制与项目无关）

| 层               | 内容                                                                                    | 位置                                    |
|------------------|-----------------------------------------------------------------------------------------|-----------------------------------------|
| 引擎             | 读暂存、glob 匹配、解析档案、比对、报告                                                 | `.project/tools/check-project-docs.mjs` |
| 提取器（内置）   | `git-timeline`、`modules`、`edges`、`dirs`、`files`、`annotations`、`services`、`count` | 同上（注册表）                          |
| 配置（项目数据） | 每份档案的 `watch` 路径与 `checks` 声明                                                 | `.project/archive/config.json`          |

- 模板默认配置为空（`{"docs": {}}`）：只保留提交触发的路径配对能力，不做事实比对。
- 导入项目时：运行 `node .project/tools/sync.mjs --suggest` 取得候选 → 按 `.project/prompts/sync.md` 与用户确认 → 写入 `.project/archive/config.json`；结构示例见 `config.example.json`。
- 注册到项目入口：按 `.project/prompts/sync.md` 的注册规则，在 `AGENTS.md` 追加一行指针（只追加，不改写既有内容）。
- 入口统一为 `node .project/tools/sync.mjs`（无参看状态，`--gate` 提交门禁）；引擎内不得出现任何具体项目的路径、前缀或技术栈词汇——那些只能进配置。

## 字段归属（每个事实只归一个文件）

| 事实                               | 归属文件        |
|------------------------------------|-----------------|
| git 时间线、仓库地址               | `01-身份`       |
| 模块清单、依赖边、顶层目录         | `05-结构`       |
| 表清单、存储布局                   | `06-数据`       |
| 接口路径清单                       | `07-接口`       |
| 编排服务、环境                     | `08-运行与部署` |
| 检查器快照、覆盖率、测试规模、债务 | `11-质量与风险` |

其余文件只能引用路径，不复述数值。

## 两种用法

| 档案层                     | 存量项目                        | 0→1 项目                                                    |
|----------------------------|---------------------------------|-------------------------------------------------------------|
| 意图层（`01/02/03/04/10`） | AI 通读仓库归纳后拟稿，用户确认 | AI 访谈法：按下节「开场脚本」提问，给出候选与理由，用户拍板 |
| 事实层（`05/06/07/08/11`） | AI 扫描仓库自动填充             | 先填「尚未成型（补齐触发点）」，随开发替换为实际值          |

## 0→1 访谈开场脚本

七个问题，按顺序问；每个问题都写明它决定哪些档案内容。

1. **它是什么、谁用？** → `01` 一句话描述与类型、`02` 使用者
2. **它解决什么问题？现在靠什么凑合？** → `02` 解决什么问题；现在的方式记入 `10` 决策（将被取代的备选）
3. **做成什么样算成功？** → `02` 目标、`11` 质量要求（验收标准）
4. **明确不做什么？** → `02` 非目标（本可以合理成为目标、但本期选择不做的事）
5. **有什么给定前提？**（必须用的技术、可投入时间与资源） → `03` 约束
6. **交付形态与落点？**（服务 / 库 / CLI / 脚本；跑在哪） → `01` 类型、`08` 运行形态
7. **第一个里程碑是什么？** → `05`/`06`/`07`/`08`/`11` 的「尚未成型」补齐触发点

## 文件清单

| 文件               | 回答什么问题                                               |
|--------------------|------------------------------------------------------------|
| `01-身份.md`       | 这是什么项目、谁负责、活没活着                             |
| `02-背景与目标.md` | 处于什么环境、解决什么问题、做到哪为止（含非目标、术语表） |
| `03-约束.md`       | 哪些东西是给定的、不能动的                                 |
| `04-设计概览.md`   | 系统整体怎么设计、核心取舍                                 |
| `05-结构.md`       | 代码怎么组织的                                             |
| `06-数据.md`       | 数据长什么样、存在哪、怎么演进                             |
| `07-接口.md`       | 对外暴露什么契约                                           |
| `08-运行与部署.md` | 怎么跑起来、跑在哪                                         |
| `09-横切关注点.md` | 贯穿所有模块的通用机制                                     |
| `10-决策与取舍.md` | 关键决策是什么、否掉了什么                                 |
| `11-质量与风险.md` | 质量要求、现状差距、风险                                   |
| `status.json`      | 复核状态（唯一的新鲜度来源，不属于档案正文）               |

## 红线

1. 只写事实，不写规则。
2. 密钥、凭据、连接串永不入内。
3. 每个数字只在此处维护，别处引用不复述。
