# CONTRIBUTING — workbuddy 协作与规范迭代指南

> 读者是人（贡献者 / 协作者）。AI 编码代理的入口是 `AGENTS.md`（根）与 `web/AGENTS.md`（前端），
> 两边口径同源：本文写「人的责任与流程」，AGENTS.md 写「代理的行为约束」，条款冲突时以规范正典（§6 地图）为准。

## 1. 环境与常用命令

前置：JDK 21、Maven 3.9+、Node ≥20 + pnpm、Docker Desktop。安装与启动细节见根 `README.md`。

| 场景                | 命令                                                                                            |
|---------------------|-------------------------------------------------------------------------------------------------|
| 基础设施            | `cd docker && docker compose up -d`（首次自动建库建表）                                         |
| 后端构建 + 静态门禁 | `mvn verify`（SpotBugs / Checkstyle / PMD / CPD，有告警即失败）                                 |
| 后端测试            | `mvn -o test`（推送门禁已含全量；开发期按改动范围分档见 `.agent/standards/java/06-测试.md` §8） |
| 改了公共模块后      | `mvn -o -q install -DskipTests` 回写本地 `.m2`（否则 CLI 门禁读旧 jar）                         |
| 前端全量校验        | `cd web && pnpm lint`                                                                           |
| 推送门禁预跑        | `sh tools/pre-push-gate.sh`（`FORCE_GATE=1` 强制重跑）                                          |

构建口径已固化在仓库（`.mvn/jvm.config` UTF-8 输出、父 pom `<proc>full</proc>`），克隆即得，无需个人配置。

## 2. 开发工作流（两段门禁）

1. **提交前（pre-commit，秒级）**：钩子对暂存文件就地格式化（format-md / lint-staged 的 fix 结果回写索引）。
2. **推送前（pre-push，全量）**：按推送范围跑注释口径 → 编码检查 → 前端 `pnpm lint` → 后端静态门禁，
   结果按指纹缓存（同一次推送重试直接跳过，改任何文件自动失效）。细节见 `.agent/checkers/README.md` 与 `.agent/checkers/backend.md`。
3. 门禁失败：修到全绿再推；修不动就如实报告，**禁止 `--no-verify` 绕过**。

## 3. 提交与分支

- 提交信息：Conventional Commits + 中文描述 + scope，例：`feat(模型): ...`、`fix(docker): ...`、`docs(web): ...`、`refactor(分页): ...`。
- 当前阶段：直推 `main`。引入更多协作者后切换 PR 流程（§4），并启用分支保护
  （`.github/CODEOWNERS` 与 PR 模板已就位，届时在仓库设置开启 Require review from Code Owners 即可）。

## 4. 评审（多人协作后启用）

- PR 描述三要素：**做了什么（What）/ 为什么（Why）/ 影响范围**；涉及取舍的关联 ADR 或 `docs/design/` 文档；
  AI 参与生成的 PR 同样遵守。
- 评审标准（借 Google eng-practices）：变更「确定改善整体健康度」即可放行，不追求完美；非阻塞意见加 `Nit:` 前缀；
  风格问题指向规范与门禁，不在评审里反复拉扯；24 小时内给首轮反馈。
- 机器能拦的不进人工评审：格式 / lint / 类型 / 命名已由门禁覆盖，评审聚焦架构、契约与业务正确性。

## 5. AI 辅助开发守则（人的责任侧）

- **You own the code**：AI 生成的代码在提交那一刻就是提交人的代码——同一套门禁、同一评审标准，
  「AI 写的」不作为 bug 或安全事故的免责理由。
- AI 代码的测试与自查标准**不低于手写代码**；交付前对照交付自查清单逐项核对
  （后端 `.agent/checkers/backend.md`、前端 `.agent/standards/frontend/delivery-checklist.md`）。
- 密钥、内网地址、客户数据禁入 prompt；模型输出当「可能过时的资料」，依赖用法以仓库现状与一手文档为准。
- 发现 AI 反复犯同类错误：往 `AGENTS.md` §2 加一条**可判定**的 Never 并记演进日志（见 §6）——这是规范的主要生长方式。

## 6. 规范体系地图与变更流程

| 层       | 文件                                                                        | 受众                |
|----------|-----------------------------------------------------------------------------|---------------------|
| AI 入口  | `AGENTS.md`（根）、`web/AGENTS.md`（前端就近）                              | AI 代理             |
| 协作流程 | 本文                                                                        | 人                  |
| 规范正典 | `.agent/standards/`（java、frontend 两个子目录）、`docs/README.md` 全局约定 | 人 + 代理按路由必读 |
| 检查口径 | `.agent/checkers/`（跨侧、后端、前端三份）                                  | 人 + 代理           |
| 决策记录 | `.agent/adr/`（只增不改）                                                   | 人 + 代理           |

变更流程（规范的规范）：

1. **先改规范，再改代码**：确需偏离规范时，先提交规范变更（评审通过）再动代码；个人习惯让位于规范。
2. **单一事实源**：同一口径只在一处维护，其余地方引用不复述（本文与 AGENTS.md 亦遵守）。
3. **踩坑驱动**：AI 或人犯的每个「不该犯的错」→ 沉淀为一条可判定规则 + 演进日志，不预先堆砌规则。
4. **结构变更同步**：目录 / 门禁 / 构建口径 / 功能域增减时，同步 AGENTS.md 路由表与本文地图；
   指针有效性由 `tools/check-agents.mjs` 机器校验（落地后生效）。
5. **重大取舍写 ADR**：只增不改，被取代标 Superseded。
6. **规则增删的审批**：新增、修改、退役规则由仓库所有者批准；提交人先在审计记录中提出，批准后落文档与索引。

## 7. 新功能域接入约定

后续功能域（可能是 Java 之外的语言）接入时：

1. **先决策后动手**：在 `.agent/adr/` 记一条接入决策（技术栈选型、与既有功能域的关系、目录落位）。
2. **目录落位**：新功能域在仓库根新建独立顶层目录，不塞进既有 `workbuddy-*` 模块或 `web/`；
   Java 侧新模块沿用 `workbuddy-<域>` 命名并保持依赖方向单一。
3. **依赖矩阵同步**：新模块或模块间新增依赖边，必须改 `.agent/standards/java/01-分层与依赖.md` §1 的表并写 ADR；
   `node tools/check-modules.mjs` 校验文档与 `pom.xml` 一致，不一致推送被拦。
4. **规范就近落位**：新功能域目录下建自己的 `AGENTS.md`（命令 + Never + 指针）；条款正文统一收进 `.agent/standards/<域>/`，入口只留指针。
5. **门禁接入**：新语言的 lint / 类型检查 / 测试须接入 pre-push 门禁与 CI（`tools/pre-push-gate.sh` 与 workflow 各加一步），
   口径对齐既有两段式（提交就地修复、推送全量校验）。
6. **登记**：在根 `AGENTS.md` §1 与 §3 路由表补一行；在本文 §1 命令表补构建命令。
