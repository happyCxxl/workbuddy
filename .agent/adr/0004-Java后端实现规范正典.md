# ADR-0004：Java 后端实现规范正典（`.agent/standards/`）

| 项   | 值             |
|------|----------------|
| 状态 | 接受           |
| 日期 | 以提交日期为准 |

## 背景

- 前端已有实现规范正典（`.agent/standards/frontend/前端开发规范.md`，13 节、三级分级），后端没有对等物：`docs/README.md`「全局约定」写的是接口契约（响应体、错误码、鉴权、限流、分页字段），`.agent/checkers/backend.md` 写的是检查引擎与自测清单，两者都不回答「类怎么分层、后缀怎么取、事务标在哪、测试写到什么程度」。
- 实测形态漂移：请求对象有 `Dto`（22）、`Request`（9）、`Filter`（1）三种；响应对象有 `VO`（56）、`Response`（1）、`View`（1）三种；`@Component` 144 个、`@Service` 43 个，`Support` 26 个、`Handler` 13 个、`Assembler` 9 个，后缀职责无文可依。
- 门禁覆盖面：Checkstyle、PMD、SpotBugs、CPD 均为行内或字节码级规则，能保证「每行合法」，不能保证「同类功能形态一致」。
- 跨会话与跨机器的代理协作中，代码形态的传递靠「就近模仿」：没有指定参考实现，模仿对象随机。

## 决策

1. 在 `.agent/` 下新增 `standards/` 作为 Java 实现形态的唯一正典；`docs/` 保持业务文档定位，`tools/` 保持检查器定位，三者不互相复述。工程治理文档统一收在 `.agent/`：`adr/` 放取舍，`standards/` 放条款。
2. 条款采用三段模型：**编号**（`JAVA-<域>-<序号>`）、**三级分级**（必须 / 应该 / 可以）、**执行者**（机器检查或评审项）。没有执行者的条款不得标【必须】。
3. 命名裁决：请求对象统一 `Xxx<动作>Dto`，响应对象统一 `XxxVO`；`Request`、`Response`、`View`、`Param`、`Filter` 后缀不再新增，存量按模块并入。
4. 注释裁决：不写 `@author`、日期与人员；注释只写做什么。
5. 存量策略：冻结现状（基线只减不增）+ 按模块收敛，不做一次性全库整改。
6. 参考实现用 `.agent/standards/exemplars/README.md` 指向仓库内真实文件，不复制代码片段，避免第二份事实源。
7. 机器检查不新增第三方依赖：结构规则用 Node 脚本做 import 级扫描，ArchUnit 作为后续可选升级，需另写 ADR。

## 备选与否决原因

| 备选                                        | 否决原因                                                                                 |
|---------------------------------------------|------------------------------------------------------------------------------------------|
| 把实现条款并入 `docs/README.md`「全局约定」 | 该文件是业务与契约文档，混入实现条款后两端都要改，且页面文档已大量引用它的章节号         |
| 把实现条款并入 `.agent/checkers/backend.md` | 该文件是检查引擎说明与自测清单，条款正文会淹没在检查口径里                               |
| 新建 `workbuddy-backend` 文档模块           | 仓库没有对应代码模块，路径与模块一一对应关系被破坏                                       |
| 直接引入 ArchUnit 做结构约束                | 新增第三方依赖，违反根 `AGENTS.md` §2 第 4 条；import 级扫描可覆盖分层与跨层调用两类规则 |
| 一次性整改 849 个文件的形态差异             | 改动面过大，与在研功能冲突，评审无法逐条消化                                             |
| 只写一份《后端开发规范》单文件              | 条款会膨胀到数百行，且无法逐条挂执行者与状态                                             |

## 后果

- 入口保持薄：根 `AGENTS.md` 只增一行路由，条款正文不外溢。
- 规则可审计：每条【必须】能在索引表里查到执行者与状态。
- 存量偏离短期共存：基线记录现有违规，门禁只拦新增。
- 规范具有生长路径：踩坑 → 新编号 → 试用 → 生效 → 退役。
- 代价：文档与代码的一致性由 `check-java-conventions` 与评审共同维持，新增一条规则需要同时改索引与执行者。
