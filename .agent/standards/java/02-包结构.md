# 02 · 包结构

> 本文件只写**分包规则**，与具体产品、具体模块无关；任何模块按自身性质套用其中对应的一条。
> 具体的模块清单与能力清单不在本文件。

## 1. 分包维度

（JAVA-LAYER-004）顶层按**业务能力**分包，不按技术角色分包。

- 一个业务能力 = 一个包；能力包内再按角色分包。
- 禁止在模块根下平铺 `controller`、`service`、`mapper` 这类角色包——它们会把所有能力混在一起，能力一多就无法判断某个类属于谁。
- 例外：**单应用能力装配模块**允许根下角色包。判定标准是模块只承载一个业务能力，能力入口收敛在 `controller/<功能>` 子包；新增第二业务能力时必须新建能力包/模块，不得继续把新能力塞进根角色包。适用模块由使用方按此标准自行判定，不在本规范中列举。

（JAVA-LAYER-004）角色包固定为下列六个，按需使用，不得自造：

| 角色包         | 职责                                        | 允许依赖                  |
|----------------|---------------------------------------------|---------------------------|
| 能力根包       | 对外契约：用例接口、领域服务接口            | —                         |
| `controller`   | HTTP 入口：绑定参数、调用契约、包装响应     | 能力根包的接口            |
| `service/impl` | 用例实现：编排、事务边界                    | 根包契约、`db`、`support` |
| `db`           | 单表数据访问：CRUD 与查询组装，不含业务判断 | 实体                      |
| `convert`      | 数据载体之间的单向转换：入参↔实体↔出参      | 数据载体                  |
| `support`      | 能力内部助手：统计、解析、守卫              | `db`、其它 `support`      |

## 2. 跨能力规则

- 能力之间只允许依赖对方的**根包契约**（接口）；不得引用对方的 `controller`、`service/impl`、`db`、`convert`、`support`。
- 不得反向依赖入口层：任何包都不得引用 `controller`。
- 能力内 `db` 只被本能力的 `service/impl` 使用。

## 3. 模块性质决定分包维度

不同性质的模块套用不同的分包维度，不要求全项目统一：

| 模块性质                       | 分包维度                      | 说明                                          |
|--------------------------------|-------------------------------|-----------------------------------------------|
| 应用层（对外接口 + 用例编排）  | 业务能力 → 角色               | 第 1 节那六个角色                             |
| 契约层（跨模块共享的数据契约） | 契约类型                      | 请求、响应、实体、枚举、错误码、工具          |
| 适配层（对接外部系统）         | 适配对象                      | 每个外部系统一个包                            |
| 算法层（领域处理）             | 业务能力 → 契约 / 实现 / 助手 | 域根包放契约，`impl` 放实现，`support` 放助手 |
| 基础层（技术基座）             | 技术类别                      | 持久化、缓存、限流、消息                      |

### 3.1 技术职责包

（JAVA-LAYER-009）模块级技术职责按**变化原因**分包，不以类上是否带配置注解作为唯一标准：

- 声明式配置与配置绑定，是“怎么装配”的职责；
- 启动期校验、装载、启动链驱动，是“启动后执行什么”的职责；
- 运行期框架适配器（过滤器、拦截器、回调处理器、统一异常出口等），是“请求/回调发生时怎么处理”的职责。

三类职责不得长期混在同一包；运行期适配器应按适配关注点独立成包，不得塞入声明式配置包。包名必须表达职责；类后缀仍按角色命名，不因所在包强制统一。具体包名与目录映射由项目档案登记，不在本规范中列举。

### 3.2 助手包

（JAVA-LAYER-010）**助手包按关注点分包**：一个助手子包只承载一个关注点（统计、映射、访问、某能力域的读写等），不得把所有助手平铺在同一层。

- 子包名表达关注点，不表达“杂项”；`utils`、`misc`、`common` 这类名字不算关注点。
- 同一关注点内的类放在同一个子包，跨关注点的助手不得同包；一个子包出现第二个关注点时即拆。
- 单包类数超过 10 视为关注点混杂的信号，按评审处理（拆分，而不是换名）。
- 助手子包之间的相互引用不受限制，但不得反向依赖能力实现包或入口层。

依据：助手类是最容易长成杂物间的一层——关注点一旦混居，新增代码会继续往同类堆放，后继者只能靠类名猜归属。按关注点分包的收益是“加功能时先找包、找不到才建包”，成本是一次性搬迁。

## 4. 新增一个能力

1. 在所属模块下建能力包，命名用业务名词，不用技术名词。
2. 按需要的角色建子包；不需要的角色不建空包。
3. 不新增模块；只有当该能力的依赖与既有能力冲突（不同外部系统、不同执行模型）时，才按 `01-分层与依赖.md` 的流程新增模块。

## 5. 契约类型包的内容约束

（JAVA-LAYER-007）请求/响应模型包（`dto`）只放**数据载体**：字段与访问器，不含处置逻辑——抛错、异常处理、循环与 `switch`。

访问器里的空值默认与等值比较属该类型的固有契约，允许保留。

出现处置逻辑即说明它不是契约而是行为，须移出到能力包并按用例归位。

这条同时是覆盖率分母的前提（见 `06-测试.md` 的 JAVA-TEST-009）：只有确认 `dto` 包内没有处置逻辑，把它排除出覆盖率统计才不构成漏洞。领域记录与枚举不在此列——它们承载业务规则与码值解析，留在分母内接受覆盖率约束。

## 6. 禁止

- 模块根下平铺角色包。
- 能力包之间引用对方的内部包。
- 建空包占位。
- 用技术名词命名能力包（如 `utils`、`manager`、`common` 作为能力包名）。
