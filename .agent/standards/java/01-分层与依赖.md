# 01 · 分层与依赖

> 本文件只写规则，与具体模块名无关；模块清单与依赖白名单属于项目实例，由工具数据维护。

## 1. 依赖方向

（JAVA-LAYER-003）依赖只能指向更底层，禁止反向依赖，禁止环。

| 层                             | 可以依赖                       | 不可以依赖     |
|--------------------------------|--------------------------------|----------------|
| 应用层（对外接口与用例编排）   | 契约层、基础层、适配层、算法层 | —              |
| 算法层（领域处理）             | 契约层、基础层、适配层         | 应用层         |
| 适配层（对接外部系统）         | 契约层、基础层                 | 应用层、算法层 |
| 基础层（技术基座）             | 契约层                         | 其它所有层     |
| 契约层（跨模块共享的数据契约） | 无                             | 所有层         |

（JAVA-LAYER-003）**基础层可被任意模块依赖，反向禁止**；其余层之间的边必须登记在白名单里。

依据：阿里《应用分层》第 1 条——上层依赖下层；Clean Architecture 的依赖规则——依赖必须指向更稳定的方向，内层不知道外层的存在。

## 2. 模块划分

（JAVA-LAYER-001）模块按**职责**划分，不按技术名词划分：

| 模块类型 | 职责                                                       |
|----------|------------------------------------------------------------|
| 契约层   | 跨模块共享的数据契约：请求、响应、实体、枚举、错误码、工具 |
| 基础层   | 共享技术基座：持久化、缓存、限流、外部系统适配             |
| 适配层   | 单一外部系统的适配                                         |
| 算法层   | 领域算法与策略                                             |
| 应用层   | 对外接口 + 用例编排，通常是唯一可启动模块                  |

- 一个模块只承担一个职责；新增模块前必须先证明它放不进既有模块。
- 模块之间的依赖以**白名单**登记；新增一条边，必须在同一次提交里登记并写明依据。
- 新增边之前先试三条替代：工具下沉契约层、接口放契约层由目标模块实现、用事件或队列解耦。三条都不成立才加边。

## 3. 跨层调用

（JAVA-LAYER-002）类级调用只能沿下列边：

| 从                   | 到                           |
|----------------------|------------------------------|
| 入口层（Controller） | 用例接口                     |
| 用例实现             | 数据访问、域内助手、算法策略 |
| 数据访问实现         | 映射接口                     |
| 映射器               | 无                           |

禁止：

- 入口层依赖数据访问、映射器、实体、域内助手。
- 用例直接依赖映射器（统一经数据访问）。
- 适配器与算法反向依赖入口层。
- 任何层反向依赖入口层。

## 4. 文件规模

（JAVA-LAYER-005）单文件 ≤400 行；超出的类按数据访问、业务判断、映射三类拆开，不靠行内折叠。

## 5. 接口层

（JAVA-LAYER-006）单一实现的用例仍保留接口，实现类用 `Impl` 后缀。

依据：阿里手册命名风格第 14 条——Service 与 DAO 暴露接口、实现类用 `Impl` 区分。Spring Boot 3 的事务代理走 CGLIB、Mockito 也能直接 mock 类，接口不是技术必需，行业规约要求保留。
