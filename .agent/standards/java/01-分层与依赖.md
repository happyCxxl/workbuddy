# 01 · 分层与依赖

> 条款编号见 `00-总则与规则索引.md` §5.1。包级目录清单见 `02-包结构.md`。

## 1. 模块与职责

依赖列即白名单：表中没有的边一律视为违规（JAVA-LAYER-001）。一致性由 `tools/check-modules.mjs` 与各模块 `pom.xml` 双向核对。

| 模块               | 职责                                                       | 对外提供                                          | 依赖                                     | 被谁依赖                                      |
|--------------------|------------------------------------------------------------|---------------------------------------------------|------------------------------------------|-----------------------------------------------|
| `workbuddy-common` | 契约对象、领域对象、枚举、错误码、异常、注解、工具         | DTO、entity、enums、`ErrorCode`、`ThrowUtil`      | 无                                       | infra、file、model、vector、worker、auth、biz |
| `workbuddy-infra`  | 基础设施适配：持久化基类、Redis、限流                      | `InfraDbService`、Redis 封装、限流切面            | common                                   | file、auth、biz                               |
| `workbuddy-file`   | 文件存储与提供者路由（本地 / MinIO）                       | `FileStorage`、`StorageProvider`、`StorageRouter` | common、infra                            | worker、auth、biz                             |
| `workbuddy-model`  | 模型目录、模型网关                                         | `ModelRegistry`、模型调用                         | common                                   | worker、biz                                   |
| `workbuddy-vector` | 向量库适配（Milvus）                                       | Milvus 客户端与集合操作                           | common                                   | worker                                        |
| `workbuddy-worker` | 环节领域算法：解析、组装、预处理、切片、向量化、索引、检索 | 环节策略接口与实现                                | common、file、model、vector              | biz                                           |
| `workbuddy-auth`   | 认证与鉴权配置、令牌过滤器                                 | `SecurityConfig`、`JwtAuthFilter`                 | common、infra、file                      | biz                                           |
| `workbuddy-biz`    | HTTP 接口与应用编排（唯一可启动模块）                      | REST API                                          | common、infra、file、worker、model、auth | 无                                            |

## 2. 依赖方向

允许的边（单向，自上而下）：

```
biz ──> auth ──> file ──> infra ──> common
 │        │       │
 │        └───────┴──────> common
 ├──> worker ──> file / model / vector ──> common
 └──> model ─────────────────────────────> common
```

约束（JAVA-LAYER-001）：

- 依赖只能指向更底层的模块；反方向 import 一律不合规。
- **§1 的表是白名单**：只能存在表中列出的边。新增一条边，必须在同一提交里改 §1 并写 ADR，ADR 需回答「为何不能下沉到 common，或改用接口倒置」。
- 新增这条边之前先试三条替代：工具方法下沉 `common`、接口放 `common` 由目标模块实现、用事件或队列解耦。三条都不成立才加边。
- 循环依赖由 Maven 构建拦截（编不过），不需要额外扫描。
- `common` 保持零内部依赖，新增 `workbuddy-*` 依赖即不合规。
- `worker` 是领域算法、`file` 是存储适配，二者都不得依赖编排层（`biz`）与鉴权层（`auth`）；这条由 §1 的白名单保证，表里没有的边会被 `check-modules` 拦下。

一致性校验：`node tools/check-modules.mjs` 比对 §1 的表与各模块 `pom.xml`——pom 多出未登记的边报错，表中登记但 pom 里已删的边告警。

## 3. 跨层调用

（JAVA-LAYER-002）允许的调用边只有下列六条：

| 从            | 到                              | 说明                      |
|---------------|---------------------------------|---------------------------|
| Controller    | Service                         | 只调接口，不调实现类      |
| ServiceImpl   | DbService、Support、worker 策略 | 事务边界在这一层          |
| TaskRunner    | DbService、Support、worker 策略 | 任务链路，不经 Controller |
| Support       | DbService、其它 Support         | 不开启事务                |
| DbServiceImpl | Mapper                          | 只做数据访问              |
| Assembler     | 无（纯映射）                    | 不查库、不判断            |

禁止：

- Controller 依赖 `DbService`、`Mapper`、实体、`Support`。
- Controller 直接使用其它模块的 service（如 `filecenter.service`），应经 `biz` 的 Service 转发。
- Service 直接依赖 `Mapper`（统一经 `DbService`）。
- `Support` 与 `Assembler` 被 Controller 直接调用。
- 任何层反向依赖 `controller`。

检查方式：Controller 目录下的 `import` 只允许出现 `biz.service`、`common.dto`、`common.utils`、`common.exception`、`common.annotation`、`common.error` 与框架依赖；违规由阶段②的 import 扫描拦截。存量偏离见 `.agent/remediation.md`。

## 4. 正例与反例

正例：Controller 只做三段——绑定、调用、包装。

```java
@GetMapping("/page")
public R<IPage<ModelItemVO>> page(@Valid ModelQueryDto query) {
    return R.ok(modelService.page(query));
}
```

反例：Controller 里查库、拼装 VO、判断权限。

```java
@GetMapping("/page")
public R<IPage<ModelItemVO>> page(ModelQueryDto query) {
    IPage<WbModel> page = modelDbService.page(query);   // 越过 Service，依赖 DbService
    return R.ok(page.convert(this::toVo));              // 映射写在 Controller
}
```

## 5. 新增模块或新增包

（JAVA-LAYER-004）新增包先在 `02-包结构.md` 登记职责与允许依赖，再建目录；未登记的包不得合入。

1. 先写 ADR（`.agent/adr/`），记录技术栈、边界与依赖方向。
2. 新模块在仓库根建 `workbuddy-<域>`，依赖只能指向 §2 已存在的模块。
3. **在 §1 的表里登记该模块**：职责、对外提供、依赖、被谁依赖；新增的边同时说明理由。
4. 既有模块之间要新增一条边时，同样改 §1 并写 ADR，按 §2 的三条替代先试。
5. 在 `02-包结构.md` 登记该模块的包职责。
6. 跑 `node tools/check-modules.mjs` 确认文档与 `pom.xml` 一致。
7. 门禁与 CI 同步接入（`.agent/CONTRIBUTING.md` §7）。

## 6. 文件规模与接口层

- （JAVA-LAYER-005）单文件 ≤400 行；超出的类按数据访问、业务判断、映射三类拆开，不靠行内折叠。判定由阶段②的规模扫描执行，存量 26 个文件（主代码 7、测试 19）记在 `.agent/remediation.md`，新文件超限即失败。
- （JAVA-LAYER-006）单一实现的 Service 仍保留接口。这是本项目的约定：契约与实现分离，外部只依赖接口。Spring Boot 3 的事务代理默认走 CGLIB、Mockito 也能直接 mock 类；它不是技术必需，而是为保持全库形态一致。
