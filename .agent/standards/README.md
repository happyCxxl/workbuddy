# 项目规范

> 规范 = **规则 + 手段**。规则说「必须怎样」，手段保证「确实这样」。
> 主要读者是 AI：写法按「能稳定执行」设计，人能读懂只是附带要求。

## 1. 每条规则要能回答四件事

| 要素         | 含义                                                   |
|--------------|--------------------------------------------------------|
| 解决什么问题 | 根因层面的问题，不是表面现象                           |
| 行业怎么做   | 阿里手册 / Google / 框架官方文档，给出一手依据         |
| 我们怎么做   | 本项目的规定，并写明依据——外部出处，或本项目决策的理由 |
| 怎么保证     | 机器检查（首选）或正反例（次选）；两者都没有就不算规则 |

缺任何一项的条款，不得写进规范。

## 2. 怎么加载

| 场景       | 路径                                               |
|------------|----------------------------------------------------|
| 进入规范   | 本目录 `00-索引.md`                                |
| 改任何代码 | `common/02-交付行为约束.md`、`common/03-反模式.md` |
| 改 Java    | `java/00-总则与规则索引.md` → 对应主题             |
| 改前端     | `vue/00-规则索引.md` → 对应主题                    |

按任务路径就近加载，不读全文。

## 3. 五条硬约束

1. **每条【必须】都要有执行者**：机器检查或可判定的正反例，二者必居其一。
2. **规范先于代码**：确需偏离，先改规范并通过评审，再改代码。
3. **只写决定，不写沿革**：取舍的依据写进规则正文的「行业怎么做 / 我们怎么做」，规范里不留讨论过程。
4. **篇幅克制**：单篇正文 ≤150 行，入口 ≤80 行；索引不设上限，长度由规则数量决定。
5. **依据优先外部**：外部已有规定时按 阿里手册 > Google Java Style > 框架官方文档 取用；外部没有规定的，由本项目决定并写明理由。**存量实现不作为依据**，只作为迁移成本。

## 4. 等级

| 等级     | 含义           | 违反后果               |
|----------|----------------|------------------------|
| 【必须】 | 可判定的底线   | 不合规，机器或评审拦截 |
| 【应该】 | 多数场景更优   | 偏离须在交付说明写理由 |
| 【可以】 | 同等选项的默认 | 全库一致即可           |

## 5. 新增、修改、删除

1. 复制 `_template.md` 起草，分配编号（语言前缀 + 序号，编号不复用）。
2. 写齐四要素：问题、行业做法、我们的决定、判定方式。
3. 规范与代码分开提交：先规范、后代码。
4. 规则必须绑定执行者：能机器化的接检查器，不能的挂进评审项。
5. 删除：从索引与正文同时移除，序号作废、不复用。

## 6. 版本

本规范按提交迭代：**每一次提交即一次版本更新**。不维护独立版本号，历史以 `git log` 为准。
