# 00 · 总则与规则索引

> 本文件只写规则体系自身的约束，与具体产品、具体模块无关；规则正文在 `01`–`07` 各域文档。
> Python 域的基底是 Google Python Style Guide：本目录只写「例外条款、判断性规则、契约条款」，机械可判定的格式与风格交给 ruff 与 Pyright，不在正文复述。

## 1. 分级

| 等级     | 含义                   | 违反后果                       |
|----------|------------------------|--------------------------------|
| 【必须】 | 可判定的底线           | 不合规；能机器化的一律机器拦截 |
| 【应该】 | 多数场景更优的写法     | 偏离须在交付说明中写明理由     |
| 【可以】 | 同等选项里取一个作默认 | 保持全库一致即可               |

## 2. 基底与例外

（PY-META-001）**基底**：风格以 [Google Python Style Guide](https://google.github.io/styleguide/pyguide.html) 为基底；本目录条款与基底冲突时以本目录为准；ruff 与 Pyright 的配置是格式与类型的唯一执行者。

- 风格类问题先查基底与工具配置；能由工具判定的不得再写进正文。
- 对基底的偏离必须写进本目录各域文档并注明依据；散落的「团队惯例」不算数。

依据：Shopify 以 Google 指南为基底、只维护少量例外；微软编码标准写明「纯机械发现交给工具，正文只写需要设计判断的规则」。

（PY-META-002）依据优先外部：Google Python Style Guide > 框架官方文档（FastAPI、SQLAlchemy、Pydantic）> 本项目决策；存量实现不得作为立规依据。

（PY-META-003）构建期必须执行下列检查，任一不通过即阻断：格式与 lint（ruff）、类型检查（Pyright strict）、测试与覆盖率、形态约定、依赖漏洞审计。清单与执行者接入见 `../common/07-检查手段.md`；失败即阻断，不提供「先过再修」的开关。

（PY-META-004）能机器化判定的条款不得标「评审」；**评审项上限 5 条**——指评审清单的条目数，不是规则条数。判定为「评审」的规则必须挂在其中一个条目下。超出上限时先补扫描器，或把该条降为「应该」。

## 3. 规则编号

`PY-<域>-<三位序号>`，域取值：

| 域    | 覆盖                                |
|-------|-------------------------------------|
| META  | 规则体系自身的约束                  |
| LAYER | 分层、依赖方向、函数与类的分配      |
| NAME  | 命名与文件组织                      |
| DTO   | 请求/响应形态、校验、分页、全局契约 |
| ASYNC | 异步边界、超时、资源所有权          |
| DATA  | 数据访问、迁移、事务、库归属        |
| ERR   | 异常与错误码                        |
| LOG   | 日志级别、内容、脱敏                |
| TEST  | 测试结构与确定性、覆盖率            |
| DOC   | 注释与 docstring                    |
| AI    | AI 服务特有约束                     |

编号一经分配不复用；规则删除后序号作废。

等级标注：未标注等级的规则默认为【必须】；【应该】【可以】规则在正文就地标注等级。

## 4. 执行者

每条【必须】必须有主执行者；允许「主执行者 + 兜底」两项。

| 判定值       | 含义                                    |
|--------------|-----------------------------------------|
| `构建期检查` | 构建或测试前执行，失败即阻断            |
| `静态分析`   | 源码扫描（ruff、Pyright），接入推送门禁 |
| `形态检查`   | 命名、结构、导入的约定扫描              |
| `覆盖率`     | 覆盖率工具按阈值判定                    |
| `评审`       | 交付前按评审清单逐条核对                |
| `变更门禁`   | 推送或合并时执行                        |

无判定表的正文（`01`、`03`、`04`、`05`、`06`），规则执行者以 §5 评审项为准。

## 6. 评审项（上限 5 条，见 PY-META-004）

> 评审项指下面清单的条目数，不是规则条数；判定为「评审」的规则必须挂在其中一个条目下，机器能判定的不得挂这里。

交付说明里给出逐项结论，未核对的按未交付处理：

- [ ] **结构与命名**：分层依赖单向；函数与类的分配（数据类承载、无状态逻辑用函数、不为分组参数建类）；命名与私有约定；类型注解完整、无无理由 `Any`；docstring 只写契约（LAYER-001~012、NAME-001~004、DOC-001~003）
- [ ] **契约与数据形态**：Pydantic 模型只承载字段；信封、恒 200、ID 字符串、分页、幂等键、request_id 口径合规；SSE 事件结构固定（DTO-001~012）
- [ ] **异步、异常与日志**：async 边界与超时；资源所有权；异常继承内置；错误码集中登记且分列；日志级别、脱敏与 requestId（ASYNC-001~006、ERR-001~005、LOG-001~003）
- [ ] **数据访问**：repository 只查写、不写业务规则；迁移可回滚可重复；事务边界在用例层；向量与元数据同事务；库归属唯一（DATA-001~008）
- [ ] **AI 服务**：模型出口唯一；循环状态机契约；结构化输出校验；用量记录；prompt 安全；工具审批留痕；评测集执行（AI-001~008）

## 7. 新增、修改、删除一条规则

1. 复制 `../_template.md` 起草，分配编号，并在「判定」一行写明执行者。
2. 改规范与改代码分开提交：先规范、后代码。
3. 依据写进该规则的「行业怎么做 / 我们怎么做」两段，随提交留痕。
4. 规则必须绑定执行者：能机器化的接检查器，不能的挂进 §5 评审项。
5. 删除：从正文移除即可（本文不维护规则副本），序号作废、不复用。
