# 01 · 项目前提

> 本文件是规范的约束底座：技术栈、运行形态、开发方式。后面所有规则都从这些前提出发，不是从「行业通常这样」出发。
> 编号 `COMMON-PROJ-xx`。

## 1. 项目定位

（COMMON-PROJ-01）workbuddy 是一个**工作台**：知识库（文档输入 → 解析 → 组装 → 预处理 → 切片 → 向量化 → 索引 → 检索）是第一个功能域，后续会接入其它功能域，可能引入 Java 与 Vue 之外的语言。

- 约束：功能域之间不得共享实现细节，只共享契约。
- 后果：模块边界、包结构、依赖方向都是硬约束，不是风格偏好。

## 2. 技术栈

| 层       | 选型                                       | 约束                                       |
|----------|--------------------------------------------|--------------------------------------------|
| 后端     | Java 21 / Spring Boot 3.2.5 / Maven 多模块 | 8 个 `workbuddy-*` 模块，只有 `biz` 可启动 |
| 前端     | Vue 3 + TypeScript + Vite + Element Plus   | SPA，界面纯中文，不使用 JSX                |
| 存储     | MySQL / Redis / MinIO / Milvus             | 由 `docker/` 编排，本地一键起              |
| 构建门禁 | Maven 插件 + Node 脚本 + husky             | 见 `07-检查手段.md`                        |

（COMMON-PROJ-02）不新增第三方依赖，除任务明确要求且在交付说明写明理由。能用现有依赖解决的，禁止引新库。

## 3. 运行形态

（COMMON-PROJ-03）后端是**单体多模块**，不是微服务：一个进程、一个数据库、一个 Redis。任务通过进程内执行池与 Redis 队列调度，不跨服务调用。

- 后果：事务可以跨表；但**不得跨进程**，所以「事务内调外部 IO」一律禁止。
- 后果：模块之间是编译期依赖，不是网络边界，依赖方向必须由规范与工具守住。

## 4. 开发形态

（COMMON-PROJ-04）**单人开发，AI 承担主要实现**。没有第二个人做人工代码评审，跨会话、跨机器。

由此产生的三条硬约束：

1. **规范必须自足**：AI 新区只能靠读文档恢复上下文，不能依赖「上次那个人记得」。
2. **能机器化的必须机器化**：没有评审人，只能靠门禁兜底。
3. **规则必须有执行者**：没有执行者的条款不写，写了也不会被执行。

（COMMON-PROJ-05）一切产出以仓库为准：口头结论、会话记忆、外部聊天记录都不算数；结论要落到文档或代码里。

## 5. 语言接入

（COMMON-PROJ-06）接入新语言时：

1. 在 `.agent/standards/<语言>/` 建目录，规则前缀用该语言名（如 `JAVA-`、`VUE-`、`PY-`）。
2. 在根 `00-索引.md` 登记语言、负责的功能域、规则数量。
3. 门禁接入 `.agent/tools/pre-push-gate.sh` 与 CI。
4. 跨语言共用的条款放 `common/`，语言专属的放各自目录，不得互相复述。

## 6. 质量目标

（COMMON-PROJ-07）代码的评价标准按优先级排：

| 优先级 | 目标   | 含义                                           |
|--------|--------|------------------------------------------------|
| 1      | 可维护 | 改一个需求只动该动的地方；新人/AI 能按规范读懂 |
| 2      | 可扩展 | 新功能域、新语言、新存储能接进来而不改老代码   |
| 3      | 可读   | 名字表达意图，结构反映职责，注释只补信息       |
| 4      | 一致   | 同类问题全库只有一种写法                       |

（COMMON-PROJ-08）不以「代码短」「写得快」「看起来高级」为质量目标；抽象层数、设计模式数量都不是成绩。
