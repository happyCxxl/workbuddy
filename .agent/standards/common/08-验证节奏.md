# 08 · 验证节奏

> 本文件管「什么时候跑哪一档、跑挂了之后怎么办」。档位怎么划见 `../java/06-测试.md` §7，测试该写什么见 `04-测试策略.md`，检查器清单见 `07-检查手段.md`；本文件只解决一件事：验证的时间成本不打断开发节奏。
> 编号 `COMMON-VERIFY-xx`。

## 1. 一次改动只跑一档

（COMMON-VERIFY-01）每次验证只跑与当前改动范围相匹配的一档，不默认取全量档。等级【必须】。

- 问题：改一个方法也跑全量，单次等待由最慢的档决定，与改动大小无关；节奏被最慢的命令定义。
- 行业：Google 的提交前只跑「快且可靠」的测试，全量交给提交后异步执行，提交前通常只限于变更所属项目；Fowler 把提交构建与部署流水线分开，前者允许走捷径、限时十分钟量级。
- 我们：档位按范围递进（检查器 → 定向用例 → 模块 → 全量），通过上一档才升档；拿不准时才取更全的一档。
- 判定：无自动判定；交付说明里的命令与改动范围可核对。

## 2. 构建产物优先复用

（COMMON-VERIFY-02）默认增量构建。清理式重建只在构建配置或依赖版本变化、以及怀疑产物被污染时执行。等级【必须】。

- 问题：每次都从零编译，把已经算过的产物重算一遍，成本与改动大小无关。
- 行业：Bazel、Gradle 与各家内部构建系统都按输入指纹复用产物；Maven 官方 build cache 扩展按模块输入算 key 并支持远端缓存。清理只用于验证缓存本身是否正确。
- 我们：迭代中不习惯性清理；确需清理时，一次清理后的连续多档验证共用同一份产物。
- 判定：无自动判定；命令清单可核对。

## 3. 失败只回退一层

（COMMON-VERIFY-03）验证失败后，修复点落在哪一层就只重跑那一层；不因为「保险」重跑整套。等级【必须】。

- 问题：一次失败触发的重跑比失败本身更贵；连续几轮全量重跑，把单点问题放大成小时级等待。
- 行业：只跑受影响的范围、只重试失败用例，是主流 CI 系统的默认行为；靠重跑全量换取「心里踏实」不在其中。
- 我们：先跑最小可复现范围，绿了再逐层升档，不跳回顶层重来。
- 判定：无自动判定；验证命令的推进顺序可核对。

## 4. 退出码是判据，日志不是

（COMMON-VERIFY-04）验证的成败以进程退出码为准。禁止把输出接进过滤器后，以「没看到报错」判定通过。等级【必须】。

- 问题：管道后取到的退出码来自过滤器而非被测命令，失败被记成成功；判据退化为读日志，漏读一次就多跑一轮。
- 行业：CI 一律以退出码判成败，日志只用于定位。
- 我们：输出重定向到文件再读文件，退出码单独判断；需要摘要时在命令结束后取日志尾部。
- 判定：无自动判定；语言侧若有验证编排脚本，须透传子进程退出码。

## 5. 慢档不占关键路径

（COMMON-VERIFY-05）预计超过档位目标耗时的验证放到后台执行，期间继续做不依赖它的工作，结果回来再决定下一步。等级【应该】。

- 问题：前台阻塞让等待时间全额进入开发时间，且无法并行。
- 行业：Google 的平均提交等待约十一分钟，多数在后台发生；长测试交给异步流水线，失败由专人处理并优先回滚。
- 我们：慢档后台跑，前台只保留秒级检查。
- 判定：无自动判定。

## 6. 全量档一轮一次

（COMMON-VERIFY-06）全量档只在交付与推送前执行一次，同一轮改动内不重复触发。等级【必须】。

- 问题：全量跑两遍不提高置信度，只延长交付时间；重复触发通常来自「上一次没看懂结果」，属于第 4 条的次生问题。
- 行业：提交后由流水线异步跑全量、失败用回滚兜底，而不是要求作者反复自证。
- 我们：一轮改动一次全量；全量失败后只重跑失败用例所在的那一层。
- 判定：推送门禁与流水线记录可比对。

## 7. 档位上限与超时处置

（COMMON-VERIFY-07）各档的目标耗时按下表执行；超出时按下表的处置，不靠「再等等」解决。

| 档       | 范围                           | 目标耗时 | 超出时                   |
|----------|--------------------------------|----------|--------------------------|
| 检查器   | 按改动文件触发的检查器（注释、形态、文档结构、规范边界、入口指针、模块结构、用例质量） | 秒级     | 放后台，继续下一次编辑   |
| 定向用例 | 单个用例类或方法               | 一分钟内 | 检查是否误用了整模块构建 |
| 模块     | 该模块的全部用例               | 数分钟   | 移到后台，不在前台等     |
| 全量     | 依赖链、静态检查与覆盖率       | 一轮一次 | 放后台，期间不重复触发   |

- 问题：档位没有上限时，慢的那一档会自然占据全部可用时间。
- 行业：提交构建的十分钟量级上限、测试选择的时延预算，都是把「等待」当成需要被约束的资源。
- 我们：超时就换处置方式，不是加长等待。
- 判定：无自动判定；各档耗时由语言侧的验证编排脚本输出。
