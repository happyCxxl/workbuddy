# 06 · 协作流程

> 读者是人（贡献者 / 协作者）；AI 代理的入口是项目的全局入口与前端就近入口（文件名由项目约定）。
> **本文件是流程（SOP），不是法条**：它没有规则编号、不进评审项、不设判定；代理的行为约束见 `02-交付行为约束.md`，态度类要求见 `10-工作习惯指南.md`。

## 1. 环境与常用命令

前置：JDK 21、Maven 3.9+、Node ≥20 + pnpm、Docker Desktop。安装与启动细节见项目的运行说明。

| 场景                     | 命令                                                                         |
|--------------------------|------------------------------------------------------------------------------|
| 基础设施                 | `cd docker && docker compose up -d`（首次自动建库建表）                      |
| 构建 + 静态检查 + 覆盖率 | `mvn verify`（SpotBugs / Checkstyle / PMD / CPD / JaCoCo，任一不达标即失败） |
| 单元测试（不含覆盖率）   | `mvn -o test`                                                                |
| 覆盖率单跑               | `mvn -o jacoco:report jacoco:check`                                          |
| 改了公共模块后           | `mvn -o -q install -DskipTests` 回写 `.m2`（CLI 门禁读的是本地仓库的 jar）   |
| 前端全量校验             | `cd web && pnpm lint`                                                        |
| 推送门禁预跑             | `sh .agent/tools/common/pre-push-gate.sh`（`FORCE_GATE=1` 强制重跑）         |

## 2. 开发工作流（两段门禁）

1. **提交前**：钩子对暂存文件就地格式化（format-md / lint-staged 回写索引），秒级返回。
2. **推送前**：按推送范围依次跑编码检查 → 文档结构 → 入口指针 → Java 形态与 Javadoc → 模块结构 → 单元测试 → 前端 `pnpm lint`。
3. **门禁失败**：修到全绿再推；修不动如实报告，禁止 `--no-verify` 绕过。
4. 依据：本项目决策——单人开发、无人工评审，门禁是唯一的强制层。

## 3. 提交与分支

- 提交信息：Conventional Commits + 中文描述 + scope。依据：conventionalcommits.org；scope 用中文是项目补充。例：`feat(模型): ...`。
- 单人阶段直推 `main`；协作者达到 2 人时切换 PR 流程（§4）并开启分支保护（`.github/CODEOWNERS` 与 PR 模板已就位）。

## 4. 评审

（协作者 ≥2 时启用）

- PR 描述三要素：做了什么 / 动机 / 影响范围；涉及取舍的关联项目设计文档。依据：Google eng-practices 的 CL 描述建议。
- 评审标准：变更「确定改善整体健康度」即可放行，不追求完美；非阻塞意见加 `Nit:` 前缀。依据：Google eng-practices。
- 机器能拦的不进人工评审：格式、lint、类型、命名由门禁覆盖，人工聚焦架构、契约与业务正确性。
- 首轮反馈时限 24 小时。依据：本项目决策（Google 只要求尽快）。

## 5. AI 辅助（人的责任侧）

- **You own the code**：AI 生成的代码在提交那一刻就是提交人的代码，同一套门禁与评审标准；「AI 写的」不构成免责理由。
- AI 代码的测试与自查标准不低于手写代码。
- 同类错误反复出现时，沉淀成一条可判定规则，并记入项目入口的演进日志。

## 6. 规范变更流程

1. **先改规范，再改代码**：确需偏离时，先提交规范变更（评审通过）再动代码。
2. **单一事实源**：同一口径只在一处维护，其余位置引用不复述。
3. **踩坑驱动**：每个「不该犯的错」沉淀为一条可判定规则，不预先堆砌。
4. **结构变更同步**：目录、门禁、构建口径、功能域增减时，同步项目入口的路由表与本文；指针由 `.agent/tools/common/check-agents.mjs` 校验。
5. **规则增删由仓库所有者批准**：依据写进规则正文的「依据」栏与提交信息。

## 7. 新功能域接入约定

1. **先定约束**：选型与边界写进 `01-项目前提.md` §3 的约束表与 §5 的 `COMMON-PROJ-03`、`COMMON-PROJ-04`，随提交留痕。
2. **目录落位**：新功能域在仓库根建独立顶层目录，不塞进既有后端模块或前端目录；Java 新模块沿用既有模块命名前缀，依赖方向单一。
3. **依赖矩阵同步**：新增模块或依赖边，改项目的模块清单与依赖白名单；`node .agent/tools/common/check-modules.mjs` 校验模块结构（目录存在、无环、无自依赖）。
4. **规范就近落位**：新功能域目录下建就近入口（命令 + 禁止项 + 指针），条款正文收进 `.agent/standards/<域>/`。
5. **门禁接入**：新语言的 lint / 类型检查 / 测试接入 pre-push 与 CI，口径对齐两段式。
6. **登记**：项目入口的路由表与本文 §1 命令表各补一行。
