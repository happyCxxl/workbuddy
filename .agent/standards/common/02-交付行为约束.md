# 02 · 交付行为约束

> 本文件约束「一次改动怎么进行」：动手前读什么、改哪些文件、交付前验证什么、完成后怎么报告。执行者是人还是 AI 都适用。
> 产物形态见 `03-反模式.md`（不该出现的写法）与各语言目录（该怎么写）。
> 过程类条款没有自动判定手段，等级一律【应该】；能落到门禁的才是【必须】。

## 1. 先读后写

（COMMON-WORK-01）动某个目录前，先读该目录所属的规范，以及同族最近的一份实现。等级【应该】。

- 问题：AI 靠邻近代码模仿；不读就按通用最佳实践写，与本项目形态冲突。
- 行业：Cursor Rules 要求先读仓库再改；Cinder 的 agent 文档写明「agent 靠正常探索发现约定」。
- 我们：规范与同族实现各读一份，再动手。
- 判定：无自动判定，靠自查。

## 2. 最小改动

（COMMON-WORK-02）只改任务相关文件：不顺手重命名、不重排 import、不格式化无关代码。等级【应该】。

- 问题：无关改动放大阅读成本，把真实意图埋在噪音里。
- 行业：Cursor 的作用域限定；评审实践要求 diff 聚焦。
- 我们：diff 只含任务声明的范围。
- 判定：无自动判定，靠自查（可核对 diff 文件清单）。

## 3. 禁止发明

（COMMON-WORK-03）新增依赖、抽象、工具类之前，先在本仓库检索等价物；有就复用，没有才新建。等级【应该】。

- 问题：每个会话都造一套自己的工具，同类逻辑多份实现。
- 行业：AGENTS.md 标准要求入口只放难以自行发现的信息，其余靠检索。
- 我们：先检索，再决定新建。
- 判定：无自动判定，靠自查。

## 4. 口径不猜

（COMMON-WORK-04）规范未覆盖且有歧义时停下来问，不自行发明口径。等级【应该】。

- 问题：猜出来的口径写进代码后，没人知道它从哪来。
- 行业：通用 agent 实践要求歧义时提问，而不是补全。
- 我们：问一句的代价低于返工。
- 判定：无自动判定，靠自查。

## 5. 验证闭环

（COMMON-WORK-05）交付前执行规范指定的验证命令，并贴出结果；失败就报失败。等级【必须】。

- 问题：跨会话时没人知道哪一部分没有验证。
- 行业：Cinder「确定性执行优先于散文」；AGENTS.md「命令必须可执行」。
- 我们：按改动范围选验证档，见 `04-测试策略.md`。
- 判定：`.agent/tools/pre-push-gate.sh` 与 CI 执行；结果未给出视为未完成。

## 6. 依赖不凭记忆

（COMMON-WORK-06）库的用法以仓库现状与一手文档为准；不确定就查，不凭训练记忆写 API。等级【应该】。

- 问题：编造的方法名与配置项能通过编译，在运行期才失败。
- 行业：幻觉 API 是已知的模型失效模式；AGENTS.md 建议把可执行命令写进入口。
- 我们：查仓库现状与官方文档。
- 判定：编译、启动校验与集成测试兜底。

## 7. 报告如实

（COMMON-WORK-07）未完成、未验证、有已知风险，交付时逐项写明，不用「应该没问题」收尾。等级【应该】。

- 问题：把验证成本转移给下一个会话。
- 行业：agent 实践要求区分「已做 / 未做 / 不确定」。
- 我们：逐项写「已验证 / 未验证 / 已知风险」。
- 判定：无自动判定，靠自查。
