# 02 · 交付底线

> 只收**有执行者**的条款：能机器判定的接检查器，不能的挂评审项（`java/00` §5、`vue/00` §6）。
> 态度类要求（先读后写、最小改动、口径不猜、报告如实等）不是法条，见 `10-工作习惯指南.md`。
> 编号 `COMMON-WORK-xx`，编号不因搬迁而改变。

## 1. 禁止发明

（COMMON-WORK-03）新增依赖、公共类或工具方法之前，按固定顺序检索等价物，并在交付说明里给出检索证据；有就复用，能由既有实现抽公共的不另起一份。等级【应该】。

- 问题：每个会话都造一套自己的工具，同类逻辑多份实现。生成一个新类比检索既有实现显得更快，代价转移给后来的人：同一语义有 N 个事实源，改一处漏 N-1 处。
- 行业：Google《What to look for in a code review》把「重复实现已有能力」与 over-engineering 一并列为需要指出的事项；代理入口文件约定要求入口只放难以自行发现的信息，其余靠检索。
- 我们：按三档顺序检索，三档都落空才允许新建；交付说明里逐档写结论：
  1. **依赖库已有**：先看构建文件里的依赖声明与标准库是否已提供该能力；有就直接用，不写等价工具方法。
  2. **本仓库已有**：按能力关键词检索类名与注释（`grep`），看同包邻近类，再查项目的能力索引（`09-可复用能力索引.md`）；命中即复用。
  3. **可由既有实现抽公共**：已有两处同类逻辑时，按 `COMMON-ANTI-03` 抽公共，不写第三份。
- 判定：评审——交付说明缺这三档结论的按未交付处理；新增公共类或工具类时，说明里必须指出它为何不能并入既有实现，或为何抽在指定位置。

## 2. 验证闭环

（COMMON-WORK-05）交付前执行规范指定的验证命令，并贴出结果；失败就报失败。等级【必须】。

- 问题：跨会话时没人知道哪一部分没有验证。
- 行业：Cinder「确定性执行优先于散文」；代理入口约定「命令必须可执行」。
- 我们：按改动范围选验证档，见 `04-测试策略.md` 与 `08-验证节奏.md`。
- 判定：变更门禁——`.agent/tools/common/pre-push-gate.sh` 与 CI 执行；结果未给出视为未完成。

## 3. 文件编码

（COMMON-WORK-08）仓库内所有文本文件必须是 UTF-8；禁止用系统编码的文本写入命令（`Set-Content`、`Out-File`、`>` 重定向）修改仓库文件。等级【必须】。

- 问题：Windows 中文环境下这类命令按 GBK 解码再写回，中文变成合法但错误的字符；编译、类型检查与 lint 都发现不了。
- 行业：UTF-8 是跨平台事实标准；Google、Linux 与主流工具链均以 UTF-8 为默认。
- 我们：写文件一律用带编码选择的编辑器或代理的写文件工具。
- 判定：静态分析（`check-encoding`）；不设行内豁免，需要举例时写转义序列。

## 4. 入口文件

（COMMON-WORK-09）仓库内的代理入口文件：其中引用的仓库路径必须真实存在；单个入口不超过 200 行。等级【必须】。

- 问题：入口指向已删文件，读者按图索骥落空；入口膨胀后每次进场都占用上下文，挤掉真正的工作空间。
- 行业：代理入口约定——入口只放难以自行发现的信息，其余靠检索；指针指向正文，不复制正文。
- 我们：入口只写命令、红线与指针，细节下沉到正典文档。
- 判定：静态分析（`check-agents`）；指针失效即失败，超预算只提示。

## 5. 表格形态

（COMMON-WORK-10）文档中的 Markdown 表格必须对齐：列宽取该列最大显示宽度，单元格两侧各留一个空格，分隔行不带空格。等级【必须】。

- 问题：宽窄不一的表格在中英文混排下错行，读者得自己数格子。
- 行业：主流 Markdown 格式化器与代码托管平台都把表格对齐视为格式契约，由工具完成，不靠手数空格。
- 我们：提交前由格式化器统一修复，不要求手写对齐。
- 判定：变更门禁（`format-md` 就地修复，不阻断）。

## 6. 中间产物不入库

（COMMON-WORK-11）构建、检查、验证产生的中间产物不得进入版本库；仓库内只放源码、配置、规范与随源码维护的测试数据。等级【必须】。

- 问题：命令输出、覆盖率报告、构建目录被无过滤的 `git add -A` 一并带入后，代码库被持续污染：评审要在 diff 里人工分辨哪些是真改动。
- 行业：忽略清单与「构建产物不入库」是主流工具链的默认约定；CI 另有产物清单校验。
- 我们：命令输出写到被忽略的位置（仓库外，或已忽略的构建目录）；提交前先看 `git status` 的文件清单，不用无过滤的 `git add -A`。
- 判定：静态分析（`check-artifacts`——扫描已跟踪文件，命中中间产物形态即失败）。

## 7. AI 生成用例的附加要求

（COMMON-WORK-12）AI 产出测试时，必须在交付说明里给出三件事，缺项按未交付处理。等级【必须】。

1. 每条用例守护的规则编号或错误码。
2. 一句话说明「该用例因什么改动而失败」。
3. 未被验证的行为清单及原因（不可达、依赖未接入、缺环境），不得用通过率掩盖。

- 问题：模型会优化被给定的指标。只要求「覆盖率达到 N%」，得到的就是恰好让 N% 成立的用例；不要求它声明「哪些没验证」，盲区就会被通过率掩盖。
- 行业：公开讨论中一致的观察是——AI 生成的用例倾向断言实现细节、过度使用替身，且不会主动报告「这段行为我验证不了」，除非被明确要求。
- 我们：把来源、可证伪性与未覆盖清单写成交付物，让「不知道」必须被写出来。
- 判定：评审 + 静态分析（`check-test-quality` 拦恒真断言、无断言用例与缺来源说明）。
- 禁止：删除或弱化既有断言来迁就实现；为让覆盖率达标而新增用例；把实现细节写成断言。

## 8. 规范自包含

（COMMON-WORK-13）规范正文必须自包含：只引用 `.agent/` 内的路径与通用标准；不得引用使用方的项目名、模块名、项目目录、项目档案或机器路径。等级【必须】。

- 问题：规范一旦依赖项目事实，换项目就不能复用；项目改名或目录调整还会让规范静默失效。
- 行业：可复用规则集与项目事实分离，事实由使用方单向引用规则。
- 我们：规范只写判定标准；需要项目事实时由项目文档引用规范，不反向引用。
- 判定：静态分析（`check-scope`——引用 `.agent/` 之外路径即失败）；正文点名外部文件名靠评审。
