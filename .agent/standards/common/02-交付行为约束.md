# 02 · 交付行为约束

> 本文件约束「一次改动怎么进行」：动手前读什么、改哪些文件、交付前验证什么、完成后怎么报告。执行者是人还是 AI 都适用。
> 产物形态见 `03-反模式.md`（不该出现的写法）与各语言目录（该怎么写）。
> 过程类条款没有自动判定手段，等级一律【应该】；能落到门禁的才是【必须】。

## 1. 先读后写

（COMMON-WORK-01）动某个目录前，先读该目录所属的规范，以及同族最近的一份实现。等级【应该】。

- 问题：AI 靠邻近代码模仿；不读就按通用最佳实践写，与本项目形态冲突。
- 行业：Cursor Rules 要求先读仓库再改；Cinder 的 agent 文档写明「agent 靠正常探索发现约定」。
- 我们：规范与同族实现各读一份，再动手。
- 判定：无自动判定，靠自查。

## 2. 最小改动

（COMMON-WORK-02）只改任务相关文件：不顺手重命名、不重排 import、不格式化无关代码。等级【应该】。

- 问题：无关改动放大阅读成本，把真实意图埋在噪音里。
- 行业：Cursor 的作用域限定；评审实践要求 diff 聚焦。
- 我们：diff 只含任务声明的范围。
- 判定：无自动判定，靠自查（可核对 diff 文件清单）。

## 3. 禁止发明

（COMMON-WORK-03）新增依赖、抽象、工具类之前，先在本仓库检索等价物；有就复用，没有才新建。等级【应该】。

- 问题：每个会话都造一套自己的工具，同类逻辑多份实现。
- 行业：AGENTS.md 标准要求入口只放难以自行发现的信息，其余靠检索。
- 我们：先检索，再决定新建。
- 判定：无自动判定，靠自查。

## 4. 口径不猜

（COMMON-WORK-04）规范未覆盖且有歧义时停下来问，不自行发明口径。等级【应该】。

- 问题：猜出来的口径写进代码后，没人知道它从哪来。
- 行业：通用 agent 实践要求歧义时提问，而不是补全。
- 我们：问一句的代价低于返工。
- 判定：无自动判定，靠自查。

## 5. 验证闭环

（COMMON-WORK-05）交付前执行规范指定的验证命令，并贴出结果；失败就报失败。等级【必须】。

- 问题：跨会话时没人知道哪一部分没有验证。
- 行业：Cinder「确定性执行优先于散文」；AGENTS.md「命令必须可执行」。
- 我们：按改动范围选验证档，见 `04-测试策略.md`。
- 判定：`.agent/tools/common/pre-push-gate.sh` 与 CI 执行；结果未给出视为未完成。

## 6. 依赖不凭记忆

（COMMON-WORK-06）库的用法以仓库现状与一手文档为准；不确定就查，不凭训练记忆写 API。等级【应该】。

- 问题：编造的方法名与配置项能通过编译，在运行期才失败。
- 行业：幻觉 API 是已知的模型失效模式；AGENTS.md 建议把可执行命令写进入口。
- 我们：查仓库现状与官方文档。
- 判定：编译、启动校验与集成测试兜底。

## 7. 报告如实

（COMMON-WORK-07）未完成、未验证、有已知风险，交付时逐项写明，不用「应该没问题」收尾。等级【应该】。

- 问题：把验证成本转移给下一个会话。
- 行业：agent 实践要求区分「已做 / 未做 / 不确定」。
- 我们：逐项写「已验证 / 未验证 / 已知风险」。
- 判定：无自动判定，靠自查。

## 8. 文件编码

（COMMON-WORK-08）仓库内所有文本文件必须是 UTF-8；禁止用系统编码的文本写入命令（`Set-Content`、`Out-File`、`>` 重定向）修改仓库文件。等级【必须】。

- 问题：Windows 中文环境下这类命令按 GBK 解码再写回，中文变成合法但错误的字符；编译、类型检查与 lint 都发现不了。
- 行业：UTF-8 是跨平台事实标准；Google、Linux 与主流工具链均以 UTF-8 为默认。
- 我们：写文件一律用带编码选择的编辑器或代理的写文件工具。
- 判定：静态分析（`check-encoding`）；不设行内豁免，需要举例时写转义序列。

## 9. 入口文件

（COMMON-WORK-09）仓库内的代理入口（如 `AGENTS.md`）：其中引用的仓库路径必须真实存在；单个入口不超过 200 行。等级【必须】。

- 问题：入口指向已删文件，读者按图索骥落空；入口膨胀后每次进场都占用上下文，挤掉真正的工作空间。
- 行业：AGENTS.md 约定——入口只放难以自行发现的信息，其余靠检索；指针指向正文，不复制正文。
- 我们：入口只写命令、红线与指针，细节下沉到正典文档。
- 判定：静态分析（`check-agents`）；指针失效即失败，超预算只提示。

## 10. 表格形态

（COMMON-WORK-10）文档中的 Markdown 表格必须对齐：列宽取该列最大显示宽度，单元格两侧各留一个空格，分隔行不带空格。等级【必须】。

- 问题：宽窄不一的表格在中英文混排下错行，读者得自己数格子。
- 行业：主流 Markdown 格式化器与代码托管平台都把表格对齐视为格式契约，由工具完成，不靠手数空格。
- 我们：提交前由格式化器统一修复，不要求手写对齐。
- 判定：提交钩子（`format-md.ps1` 自动修复，不阻断）。

## 11. 中间产物不入库

（COMMON-WORK-11）构建、检查、验证产生的中间产物不得进入版本库；仓库内只放源码、配置、规范与随源码维护的测试数据。等级【必须】。

- 问题：命令输出（`*-out.txt`）、覆盖率报告、构建目录被无过滤的 `git add -A` 一并带入后，代码库被持续污染：评审要在 diff 里人工分辨哪些是真改动；这些文件还会随每条命令重写，产生与业务无关的整文件变更。
- 行业：`.gitignore` 与「构建产物不入库」是 Maven、Gradle、npm 等工具链的默认约定；CI 另有产物清单校验。
- 我们：命令输出写到被忽略的位置（仓库外，或 `target/` 这类已忽略目录）；提交前先看 `git status` 的文件清单，不用无过滤的 `git add -A`。
- 判定：静态分析（`check-artifacts`）——扫描版本库已跟踪的文件，命中中间产物形态即失败。

## 12. AI 生成用例的附加要求

（COMMON-WORK-12）AI 产出测试时，必须在交付说明里给出三件事，缺项按未交付处理。等级【必须】。

1. 每条用例守护的规则编号或错误码。
2. 一句话说明「该用例因什么改动而失败」。
3. 未被验证的行为清单及原因（不可达、依赖未接入、缺环境），不得用通过率掩盖。

- 问题：模型会优化被给定的指标。只要求「覆盖率达到 N%」，得到的就是恰好让 N% 成立的用例；不要求它声明「哪些没验证」，盲区就会被通过率掩盖。
- 行业：公开讨论中一致的观察是——AI 生成的用例倾向断言实现细节、过度使用替身，且不会主动报告「这段行为我验证不了」，除非被明确要求。
- 我们：把来源、可证伪性与未覆盖清单写成交付物，让「不知道」必须被写出来。
- 禁止：删除或弱化既有断言来迁就实现；为让覆盖率达标而新增用例；把实现细节写成断言。
- 判定：评审（交付说明逐项给出）；静态分析（`check-test-quality`）拦恒真断言、无断言用例与缺来源说明。
