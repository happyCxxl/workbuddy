# 规则写法与模板

> 规范 = **规则 + 手段**。规则说「必须怎样」，手段保证「确实这样」。主要读者是 AI：写法按「能稳定执行」设计。
> 本文合并了「怎么写规范」与「一条规则的模板」：同一个问题，不拆两份。复制 §4 起草规则。

## 1. 一条规则要回答四件事

| 要素         | 含义                                                   | 落点                     |
|--------------|--------------------------------------------------------|--------------------------|
| 解决什么问题 | 根因层面的问题，不是表面现象                           | 正文的一句话与要点       |
| 行业怎么做   | 阿里手册 / Google / 框架官方文档，给出一手依据         | 正文的依据行             |
| 我们怎么做   | 本项目的规定，并写明依据——外部出处，或本项目决策的理由 | 正文的一句话与要点       |
| 怎么保证     | 机器检查（首选）或正反例（次选）；两者都没有就不算规则 | 文件头判定表 / 评审项    |

四件事齐备即可，不要求四段式排版；缺任何一项的条款，不得写进规范。

## 2. 准入三问

立一条规则前先过三问，任一答不上来就不立：

1. **能判定吗**：有检查器（给出复跑命令），或能挂进评审清单的某一条；
2. **不自明吗**：编译器、格式器、常识已经能保证的，不立规——规则越多，能记住的越少；
3. **有依据吗**：外部出处，或本项目发生过的事故；存量实现不作为依据。

## 3. 等级与硬约束

| 等级     | 含义           | 违反后果               |
|----------|----------------|------------------------|
| 【必须】 | 可判定的底线   | 不合规，机器或评审拦截 |
| 【应该】 | 多数场景更优   | 偏离须在交付说明写理由 |
| 【可以】 | 同等选项的默认 | 全库一致即可           |

五条硬约束：

1. **每条【必须】都要有执行者**：机器检查或可判定的正反例，二者必居其一。
2. **规范先于代码**：确需偏离，先改规范并通过评审，再改代码。
3. **只写决定，不写沿革**：依据写进规则正文，规范里不留讨论过程。
4. **篇幅克制**：单篇正文 ≤150 行；不复述别处的规则清单。
5. **依据优先外部**：阿里手册 > Google Java Style > 框架官方文档；外部无规定时由本项目决定并写明理由。

## 4. 模板

与现行正文同形：一条规则 = `（编号）一句话 + 等级标注 + 依据 + 要点`。判定写文件头的判定表（`判定 | 具体怎么判`），不在每条规则下重复；等级标注遵循「未标注默认为【必须】」（见 `java/00-总则与规则索引.md` §2）或语言目录的编号约定（Vue 只给【必须】编号）。

```markdown
（<LANG>-<域>-<序号>）一句可判定的陈述：含「禁止」「一律」「必须」的写法要能落到具体语法或文件位置。等级【必须】。

- 要点 1：细化口径，逐条可判定。
- 要点 2：边界与不适用情形；豁免写法统一见 `common/07-检查手段.md`。

依据：外部出处（阿里 §x / Google §x / 框架文档章节）或本项目决策的理由。
```

## 5. 新增、修改、删除

1. 复制 §4 起草，分配编号（语言前缀 + 序号，编号不复用）。
2. 写齐四件事；执行者落在文件头判定表（机器检查 + 复跑命令）或对应目录的评审项（每条【必须】必须有主执行者）。
3. 规范与代码分开提交：先规范、后代码。
4. 能机器化的接检查器，不能的挂进对应目录的评审项（每域上限 5 条）。
5. 删除：只改正文——本文与其他索引都不维护规则副本，序号作废、不复用。
