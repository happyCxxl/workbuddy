### 3.3 限额的语义（与我们口径最相关）

| 事实                                                                                                                                         | 出处                                                                | 对我们的意义                                                          |
|----------------------------------------------------------------------------------------------------------------------------------------------|---------------------------------------------------------------------|-----------------------------------------------------------------------|
| LiteLLM 的 `rpm`/`tpm` **默认只用于路由决策**；加 `optional_pre_call_checks: enforce_model_rate_limits` 才变硬限（超限 429 + `retry-after`） | [load_balancing](https://docs.litellm.ai/docs/proxy/load_balancing) | 与 D15（不做配额层）+ D17（保留容量占用信号）一致：限额当**路由信号** |
| TPM 硬限只能 best-effort —— 请求前不知道 token 数，只能"已超则拦 + 事后累加"                                                                 | 同上                                                                | 印证"usage 只有厂商响应才知道"，与我们的 `-1` 口径同源                |

### 3.4 跨产品共识（七条）

1. 冷却/熔断按**单个部署或模型条目**维度，不按厂商维度。
2. 冷却到期后再试一次、成功即恢复 = 半开探测（Kong `fail_timeout` 语义）。
3. fallback 链必须**显式有序、可多级**，并按**错误类型**界定触发面（429/5xx 切，400/403 不切）。
4. 策略枚举收敛为五类：加权/优先级、最低延迟、最少占用或用量、最低成本、语义相似。
5. 性能阈值**只降权不排除**；硬上限另设会拒绝请求的参数（OpenRouter：`preferred_min_throughput` 降权 vs `max_price` 拒绝）。
6. **路由原因必须可观测**：记录每次 attempt、命中分支与最终模型（Portkey 按 Trace ID 可看）。
7. 多副本下路由与限流状态需**外置共享**（LiteLLM 用 Redis）。

### 4.5 该直接抄的口径（九条）

1. 明细行存「用量 + **计价时刻单价快照 + 价格表版本**」；历史账不随新价格表回溯重算，价格变更以生效时间新增版本。
2. 流式一律以**结束回执**为准（OpenAI 最后那块带 usage 的 chunk / Bedrock `metadata` 事件）；**禁止逐块累加**（DashScope 原生逐块 usage 是**累积值**）；收不到结束回执即按"用量未知"处理。
3. 缺失用量记 **`unknown`**（可空 + 独立标记位），**不写 `-1`、不静默写 `0`**；看板显式展示"未知用量占比"。
4. 能估算就估算，但**必须打 `estimated` 标记**并进对账队列，绝不与厂商回报值混算同一指标。
5. 有用量但缺价格键时：落 0 成本 + 计数告警（照抄 `missing_pricing_key` 口径），让"少收"可见。
6. 明细默认保留 **30~90 天**、按天分区 + DROP PARTITION 回收；长期只保留「租户/user/key/model/天」的汇总。
7. 幂等键 = `request_id`（+ source/租户），去重窗口显式配置（先例：32 天）；结算以去重后汇总为准。
8. 缓存 token 拆 **cache_read / cache_write 分别计价**（read 折扣、write 原价），不并入 input；缓存单价缺失即告警。
9. **对账手册化**：对齐时间范围 → 对齐 token 分类（含 cache）→ 判定是采集缺失、公式错误还是价格表过期。

| 密钥         | `api_key`，支持 `os.environ/` 引用；DB 凭据用 `LITELLM_SALT_KEY` 加密；`GET /model/info` 返回掩码 | 渠道 `key`；**多密钥**专用接口支持按 `key_index` 逐把启停 | 只有一组密文 + 掩码（见 5.3） |
| 模型列表     | 一条 `model_name` 一个 deployment                                                                 | 渠道内 `models` + 模型重定向，可从上游拉取                | 一行一模型                    |
| 权重         | `litellm_params.weight`                                                                           | 渠道权重                                                  | 有                            |
| 优先级       | `order`，**越小越优先**                                                                           | 渠道 priority（FastGPT 越大越优先）                       | 有但**方向未定义**            |
| 限额 RPM/TPM | `rpm`/`tpm`（可 `itpm`/`otpm`），默认软性                                                         | 以额度/分组为主                                           | 厂商级 + 模型级               |
| 状态         | DB 模型可删；可关后台健康检查                                                                     | 启用 / 手动禁用 / **自动禁用**                            | 手动启停 + 生效区间           |
| 试连         | 单模型 Test Connection、Run All Checks、`GET /health` 真发一次                                    | 测试指定渠道 / 全部渠道                                   | 有（模型级）                  |
| 超时         | 网关级 `timeout`、`health_check_timeout`                                                          | 系统级                                                    | **缺**                        |
| 重试         | `num_retries`，每层各自重试                                                                       | 失败重试                                                  | 有（策略表内）                |

### 5.2 十家共识

1. **只有一个管理页**，不拆两个菜单（LiteLLM / new-api / Dify / FastGPT / RAGFlow）。
2. 只有 one-api、FastGPT 把「渠道」当一等实体；LiteLLM、Portkey 的 provider 只是模型串或字段。
3. 权重只在"一个模型挂多上游"时出现。
4. **试连是标配**（LiteLLM 单模型测试与健康检查、new-api 测试渠道、FastGPT 48h 探测、RAGFlow 保存时真发一次）。
5. 状态机普遍含**自动禁用/自动恢复**。
6. **超时与重试多为网关级全局配置**，而非逐条模型配。
7. 价格与上下文窗口是模型层**共识字段**；Langfuse 把价格放进 model definition（`match_pattern` + 按用量类型单价）。
8. 改渠道/供应商**限管理员**（Dify 仅 owner/admin；one-api Root=100 / Admin=10）。
9. 审计多为付费能力（LiteLLM 审计/SSO/RBAC 属企业版；one-api 只落管理日志）。
10. 密钥掩码：LiteLLM `GET /model/info` 明确返回掩码（与我们的掩码口径一致）。

### 5.3 「每厂商一把密钥」的核实结论（重要）

**业界普遍支持多密钥，我们的是一个有意的简化，不是行业共识**：

| 产品    | 做法                                                                                   | 出处                                                                                                                                                                             |
|---------|----------------------------------------------------------------------------------------|----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| new-api | 一个渠道挂多把 key，可按 `key_index` 逐把启停；有"所有 Key 自动禁用后无法恢复"的 issue | [多密钥接口](https://docs.newapi.pro/zh/docs/api/management/channel-management/channel-multi-key-manage-post)、[issue #7040](https://github.com/QuantumNous/new-api/issues/7040) |

| LiteLLM | 同名 `model_name` 多个 deployment 各带 api_key；另有具名 LLM Credentials 可复用        | [routing](https://docs.litellm.ai/docs/routing)、[model_management](https://docs.litellm.ai/docs/proxy/model_management)                                                         |

## 六、结论：可直接照搬 / 需改造后采用 / 明确不适用

| 类别             | 条目                                                                                                                                                                                                                                                                                                                                                                                                                                        |
|------------------|---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| **可直接照搬**   | ① 策略枚举与默认值照 LiteLLM 的 `routing_strategy` 五类，默认 `simple-shuffle`；② `order` 分层优先级语义（小值优先、每层各自重试）；③ 冷却口径 `allowed_fails` + `cooldown_time`、按**模型条目**维度；④ 半开语义（超时后再试、成功即恢复）；⑤ fallback 按错误类型分链、429/5xx 切而 400/403 不切；⑥ 阈值只降权、硬上限另设；⑦ 试连作为标配；⑧ 密钥只回掩码；⑨ 限额默认软性（只作选型信号）；⑩ 多副本状态放 Redis                            |
| **需改造后采用** | ① `usage_details`/`cost_details` 的"按用量类型字典"形态（落到我们的明细表列结构）；② `ingested > inferred` 的优先级（我们不做本地估算，需保留"未知"标记）；③ 模型定义含分档定价与 UI+API 双维护；④ OpenRouter 的"故障窗口剔除"（我们要定窗口时长）；⑤ 状态机自动禁用/自动恢复（需定恢复策略与告警）；⑥ 分组/逻辑模型名（决定"一组候选"的表达方式）；⑦ 首包超时对流式降级（需定首包超时阈值）                                                |
| **明确不适用**   | ① 引入独立网关进程（我们消费方都在本仓库，D13 已定不做）；② 语义路由 / 质量预测路由（RouteLLM、semantic-router、Not Diamond、Bedrock intelligent routing）：需要训练或额外模型，且 Bedrock 方案仅英文；③ 语义缓存（Kong semantic、Azure `llm-semantic-cache`）：需向量库与阈值调优，收益场景未验证；④ 虚拟 key/团队预算（我们无多租户计费）；⑤ 一致性哈希与会话保持（Kong `hash_on_header`、Azure session-aware）：我们暂无可保持的会话状态 |
