# 解析环节 · 功能逻辑

从「管线拿到解析上下文」到「产出解析结果与建议状态」的完整口径。页面与接口视角（卡片四态、抽屉、五个接口的字段与错误码、原文预览）见 `../../pages/解析环节/`；市面方案对照与出处见 `../../research/解析环节-开源方案调研.md`。本文件不写接口字段与页面交互。

配套流程图（浏览器打开，节点带代码溯源）：环节总览 [`02-流程图-环节总览.html`](02-流程图-环节总览.html)；PDF 三段 [`03-流程图-PDF解析器步骤.html`](03-流程图-PDF解析器步骤.html)；Office 三格式 [`04-流程图-Office解析器步骤.html`](04-流程图-Office解析器步骤.html)。

## 一、环节边界

| 项   | 值                                                                                                                                          |
|------|---------------------------------------------------------------------------------------------------------------------------------------------|
| 输入 | `ParseContext`：文件引用（`fileId` / `mimeType` / `pageCount` 回填位）、输入流、解析阈值、`fileResultId`                                    |
| 输出 | `ParseOutcome`：解析产物 `ParseResult`（`sources` + `quality` + `capabilitySnapshot`）、步骤日志清单、建议状态、`unitCount` / `failedUnits` |
| 触发 | 任务编排领取解析任务后调用 `ParsePipeline.run`（触发接口与任务状态机见页面侧文档）                                                          |
| 下游 | 组装环节消费 `ParseResult.sources`；预处理环节消费组装产物                                                                                  |
| 不做 | 不碰 DB 与对象存储（纯算法）、不剔除页眉页脚（交给预处理环节的清洗规则）、不做 OCR 与版面模型推理                                           |

`ParsePipeline` 的骨架固定，变化点在两处策略：解析器（`DocumentParserPort` 的多个实现）与信号处置（`SignalFallbackHandler` 的多个实现），两者都由 Spring 注入列表。

## 二、解析器路由

- 路由维度是 **MIME**，不是扩展名：`fileRef.mimeType` 由文件中心按 Tika 魔数识别后写入，扩展名只用于界面展示。
- `ParsePipeline` 注入全部 `DocumentParserPort`，按 `supports(mimeType)` **首个命中**取用（`ParsePipeline.run`）。
- 无命中 → 步骤 `FILE_ROUTE` 置 `FAILED`、错误文案「无匹配解析器: {mime}」，整任务以 `PARSE_FAILED` 失败，**不产生产物**。
- 命中后把 `capabilityName-capabilityVersion` 同时写进步骤日志（`FILE_ROUTE` 与 `NATIVE_PARSE`）与产物的 `capabilitySnapshot`。

**两道关卡分处两侧**：能否进入解析由文件中心的启用白名单决定（配置 `knowledge.file.enabled-formats`，默认 PDF / DOC / DOCX / XLS / XLSX），`FileFormat` 枚举本身是「Tika 真实格式识别字典」，不是白名单；进入 worker 之后按 MIME 分派解析器，`supports` 只认 MIME，不看白名单。

**启动期校验**（`ParserWhitelistChecker`）：白名单里的每种格式都要有解析器接得住，缺一个就抛异常阻断启动（漏接格式在启动期暴露，不留到解析时才落到「无匹配解析器」）；反向差异（有解析器但未进白名单）只打警告 —— 这类文件文件侧不会放行。

当前在跑的四个解析器：

| 解析器                                   | 格式          | 能力标识           |
|------------------------------------------|---------------|--------------------|
| `parser/pdf/PdfBoxDocumentParser`        | PDF           | `pdfbox-3.0.4`     |
| `parser/office/impl/DocxDocumentParser`  | DOCX          | POI 三实现共用骨架 |
| `parser/office/impl/DocDocumentParser`   | DOC（二进制） | 同上               |
| `parser/office/impl/ExcelDocumentParser` | XLS / XLSX    | 同上               |

`FileFormat` 已登记 PPT / PPTX（还有 TXT / MD / CSV），这些格式未进启用白名单、也没有对应解析器；即使放行，路由也会落到「无匹配解析器」。

## 三、五步流程

`ParsePipeline.run` 顺序固定，步骤日志用 `StepLogHelper.begin` / `finish` 记录，步骤名取 `ParseStepName`：

| 序 | 步骤（`ParseStepName`） | 做什么                                                                                        | 失败后果                                                         |
|----|-------------------------|-----------------------------------------------------------------------------------------------|------------------------------------------------------------------|
| ①  | `FILE_ROUTE`            | 取 MIME → 首个命中解析器 → 记能力版本                                                         | 无命中即整任务失败（`PARSE_FAILED`），提前返回                   |
| ②  | `NATIVE_PARSE`          | 调用 `parser.parse(context)` 拿 `ParseSource`                                                 | 抛异常即整任务失败（`PARSE_CORRUPTED`，错误信息截断 500 / 1000） |
| ③  | `QUALITY_CHECK`         | `SignalDetector.detect` 产信号 → 逐条按子类型找 `SignalFallbackHandler` 执行 → 汇总失败单元数 | 不中断：信号问题只影响建议状态与质量清单                         |
| ④  | 结果封装                | 写 `CapabilitySnapshot`（按各路能力引用回填 ocr/layout/table）；`sources` = 原生路 + ocr 路   | —                                                                |
| ⑤  | 占比门槛评估            | `evaluate` 定建议状态与错误码                                                                 | 门槛不足 → `FAILED`（产物照常产出）                              |

补充口径：

- **①②是硬失败**（无产物）；**③④⑤一定会走到结果封装**，「解析失败」也常常带着完整产物，页面能看到元素构成与告警清单。
- `QUALITY_CHECK` 步骤记 `warningCount`；当建议状态是 `FAILED` 时，把质量告警按 `code:message` 拼成摘要写进该步骤的 `error`（落 `wb_knowledge_pipeline_step_log.error`，可查询）。
- ④ 里的 `sources` 第二条是 OCR 路：`source="ocr"`、`candidateOrder=false`。接入 OCR 能力后，整页无文本且含图片的单元由该能力补出文字（逐页识别行按 `PARAGRAPH` 元素进本路，`needsOcr=false`、带页内 bbox 与置信度，逐页记「文字由能力补出」事实与 `ocr` 能力引用）；未接入能力、无可补页或某页调用失败时保留占位文案（「接入后扫描 / 图片区域文字走本路，与 native 路重叠区域由组装环节裁决」），与 native 路的重叠区域仍由组装环节裁决。
- 同一文件可多次触发解析，每次运行各自成任务与产物，旧任务与旧产物保留。

## 四、判定单元与页级指标

**判定单元**按格式折算，回填 `ParseSource.unitCount`，再由管线写进 `ParseOutcome.unitCount`：

| 格式       | 单元定义                                                                                   | 回填位置                     |
|------------|--------------------------------------------------------------------------------------------|------------------------------|
| PDF        | 每页 = 1 单元（同时回填 `fileRef.pageCount`）                                              | `PdfBoxDocumentParser.parse` |
| XLS / XLSX | 每 worksheet = 1 单元（`page` 记 sheet 序号）                                              | `ExcelDocumentParser`        |
| DOC / DOCX | 每 `officePageChars`（默认 3000）个非空白字符 = 1 单元；图片按它在正文里的位置归到所属单元 | `AbstractPoiDocumentParser`  |
| PPT / PPTX | 每张幻灯片 = 1 单元（元素 `page` 记幻灯片序号）                                            | `PptDocumentParser`          |

**Office 单元与定位两条口径分开**：单元数（`officePageChars` 折算的虚拟页、Excel 的 sheet、幻灯片的页）**只用于信号判定与成功占比**；**预览定位一律用元素 provenance 里的源序号** —— DOC / DOCX 为 `paragraph[i]`（`i` 是**源文档段落序号**：空段不产元素但仍占号，序号不错位）、Excel 为 `sheet[名]/cell[r,c]`、幻灯片为 `slide[i]/...`。虚拟页与真实排版页不做等值承诺。

**单元指标** `PageMetric` 由解析器逐单元回填，是信号判定的输入：

| 字段              | 含义                                                                             | 谁填                                |
|-------------------|----------------------------------------------------------------------------------|-------------------------------------|
| `page`            | 单元号（从 1 起；Excel 为 sheet 序号）                                           | 两侧都填                            |
| `charCount`       | 非空白字符数                                                                     | 两侧都填                            |
| `garbledRatio`    | 乱码率（不可读码点，或可打印乱码带占比达门槛时的两者较大值；分母为非空白字符数） | 两侧都填                            |
| `cidMappingRatio` | CID 映射失败率（来自「Type0 且缺 ToUnicode」字体的字符 ÷ 非空白字符数）          | PDF 填（Office 留 0）               |
| `textAreaRatio`   | 文本 bbox 面积 ÷ 页面面积                                                        | PDF 专有（Office 无页面几何，留 0） |
| `imageAreaRatio`  | 图片矩形面积之和 ÷ 页面面积                                                      | PDF 填                              |
| `vectorAreaRatio` | 矢量线段包围盒面积 ÷ 页面面积（纯矢量页与真空白页的区分口径）                    | PDF 填                              |
| `imageCount`      | 内嵌图片数                                                                       | Office 填                           |

两条图片口径**互斥回填**：PDF 只有覆盖占比、Office 只有图片张数，信号判定按单元取其中一条（判定顺序见「信号判定」一节）。

**乱码口径**（`TextUtil`）：第一层认不可读码点 —— 替换字符 `U+FFFD`、私用区、未分配码点、控制字符；全角标点与引号、假名、谚文、生僻字（CJK 扩展）、希腊与西里尔字母、数学符号、圈号与项目符号都算正常字符。第二层认**可打印乱码带**（拉丁补充区 `U+00A0–U+00FF`）：该带占比达到 `printableGarbledRateThreshold`（默认 0.3）时，乱码率取「不可读占比」与「该带占比」的较大值 —— 字体缺 Unicode 映射时错位出的 `ÿþ¤¥¦§` 由此进判据。两层分母都是非空白字符数。自然语言正文（中文、英文、带重音的西文）该带占比远低于门槛。

## 五、PDF 实现（三段）

`parser/pdf/PdfBoxDocumentParser` 只做编排：**输入**（小文件整档留内存，大于 `largeFileMinBytes` 时落临时文件后按需读取）→ **全档轻量行摘要**（`PageLines`，跨页识别要全档视野）→ **跨页识别** → **分窗装配**（每 `pageWindowSize` 页一窗，字符与 token 只在窗口内保留；页数不超过窗口时单窗装配、沿用同一份提取结果）。三段分别落在 `pdf/extract/`、`pdf/detect/`、`pdf/assemble/`，页内事实模型在 `pdf/model/`。

三段的步骤与产出见 [`03-流程图-PDF解析器步骤.html`](03-流程图-PDF解析器步骤.html)。

### 5.1 提取段（`pdf/extract/`）

`PdfPageExtractor.extractPage` 逐页产出一个 `PageContent`：

1. **字符事实**：内部 `PositionStripper`（`PDFTextStripper` 子类）走该页内容流，`writeString` 回调给出一组 `TextPosition`，逐码点转 `CharInfo`（`x` / `y` / `width` / `height` / 字号 / 字体名 / 是否粗体 / 码位）。坐标取 `getXDirAdj()` / `getYDirAdj()`：**版面坐标**（裁剪框左上原点、不含页旋转），版面判定都在这个坐标系里做。
2. **页级指标**：非空白字符数、乱码率（`TextUtil.isNonCommonChar` 判不可读码点）、图片覆盖占比（`RuleLines.imageAreaRatio`）、矢量图形覆盖率（`RuleLines.vectorAreaRatio`）。
3. **行聚合**：字符按 `y` 排序后聚类，相邻字符 `y` 差在 `lineYTolerance`（默认 2.0pt）内归为同一行，行 `y` 取累计均值。
4. **表格行带与按栏切行**：全页先按 y 聚成行带（同 y 内保持字符产出顺序），再从所有行带的 token 左起点与右边界聚出**对齐位置**（被 `tableAlignmentMinRows` 行带支持）；命中 `tableRowMinColumns` 个对齐位置的锚行、以及锚行区间内与两侧紧邻的合格行带（token 全部落在区域 x 范围内）**整行保留**，其余行带**在栏沟处的断口切行**：沿字符产出顺序走，相邻字符之间出现断口（间隙 ≥ `wordGapRatio × 字号`）或起点回跳/重叠，且下一字符已落到另一栏（按字符中心归栏）时切一刀。同排的多栏文本（含长行溢出到邻栏、字符区间重叠的情形）由此各成一行，真正横跨栏沟的连续文本（跨栏行）整带出一行；判栏口径与分栏实现共用 `PageLayoutAnalyzer.crossesAny` / `columnOf` / `columnOfCenter`。锚行下限取 3 列：只有 2 列对齐时与双栏正文无法区分，双栏正文必须保持栏内阅读顺序。
5. **阅读顺序**：交给 `PageLayoutAnalyzer.order` 重排（跨栏行分带）。
6. **行文本与词边界**：`LineTexts.lineText` 按相邻字符间隙补词间空格（间隙 > `wordGapRatio × 字号`，默认 0.15），内容流里的真实空白压成一个空格，两侧同为 CJK 时不补。词边界**只由几何算出**，不依赖提取库的词回调 —— 旋转页上回调粒度会失真（把 `Quarterly` 拆成 `Q` / `uarterly`）。**字距加宽排版的行不按词边界补空格**：相邻字符间隙达到 `characterSpacingFloorRatio × 字号`（默认 0.12）即算显著间隙，显著间隙占该行字符间隙的比例达到 `characterSpacingGapShare`（默认 0.75）即判为字距加宽（`Tc`）排版，照词边界补空格会把 `INVOICE` 拆成 `I N V O I C E`；真实空格字符在所有情况下都保留。
7. **token 分词**：字符间距超过 `0.35 × 字号` 即断词（`TOKEN_GAP_RATIO`），token 带起止 `x`；供无边框表的列聚类使用。
8. **目录行特征**：`TocLineFeature.isTocLine` 标 `tocCandidate`（行尾页码 + 点线引导符），供预处理环节判目录页。
9. **文字占比**：行级 bbox 面积累计 ÷ 页面积，行高取 `max(字符高, 字号 × 1.2)`；用行级盒子而不用字符级小盒子，稀疏页不会被低估。`PageMetric.textAreaRatio` 是 PDF 专有口径。

**坐标口径（两个坐标系，只在一处换算）**：版面判定（行聚合、分栏、页眉页脚带、贴页底、表格网格）全部在**版面坐标**里做，版面尺寸取**裁剪框**（`PdfPageGeometry.textWidth` / `textHeight`，未设裁剪框时 PDFBox 回落到媒体框）；产出元素时由 `PdfPageGeometry.toViewport` 把 bbox 换成**视口坐标** —— 与 pdf.js `getViewport({ scale: 1 })` 同一套数：旋转 90/270 时视口宽高与版面高宽互换，90° 映射 `(H − y − h, x, h, w)`、180° `(W − x − w, H − y − h, w, h)`、270° `(y, W − x − w, h, w)`。`pageDimensions` 同样给视口尺寸，组装环节按它建页时 `rotation` 恒 0 成立。

### 5.2 识别段（`pdf/detect/`）

| 类                       | 判什么                                                                                                                                                                                                                                                                                                                                                                                                   |
|--------------------------|----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| `HeaderFooterDetector`   | 页顶 / 页底带（`headerAreaRatio` / `footerAreaRatio`，默认各 0.08 页高）内的文本跨页重复（≥ `runningTextMinPages`，默认 2 页；同页重复只计一页）；页码另需「纯数字或第X页」+ 页底带 + 跨页横向位置一致（行中心 `pageNumberXTolerance` 内，默认 5pt）+ **内容空洞度**（与正上方最近正文行的空白 ≥ 行高 × `pageNumberIsolationRatio`，默认 1.5；页脚重复文本不算正文），同页页底出现多条纯数字行时不判页码 |
| `RuleLines`              | 走内容流采集横 / 竖线段（最短 3pt、单页上限 2000 条）与 `drawImage` 的图片矩形，坐标统一为左上原点；线段按相交关系聚成线框区域，区域内求列 / 行边界与**分隔线缺失矩阵**                                                                                                                                                                                                                                  |
| `TableCandidateDetector` | 行是否具备表格候选特征（多 token 且列距宽）、token 起点聚类成列、列的支持度过滤、行是否覆盖够列                                                                                                                                                                                                                                                                                                          |

### 5.3 装配段（`pdf/assemble/`）

`PdfBodyAssembler.assemble` 逐页推进：

1. **页眉页脚元素**：页眉带内命中键的行产 `HEADER`、页底带内命中页脚键或页码位置的行产 `FOOTER`，**每页各产一条**，文本取该页原行并带本页 `bbox` 与区域溯源（`pdf#top-area` / `pdf#bottom-area`）。
2. **正文行**：落在对应带内的命中行不进正文流；顺序沿用页内阅读顺序（分栏页已按栏排好）。
3. **按线框区域分段**：行中心落在某个线框区域内即归该区域，同一区域内的连续行成一段。
4. **区域内 → 线网格表格**（`RuledTableBuilder`）：求网格 → 合并格划分（向右按列分隔线缺失扩张、再向下按行分隔线缺失扩张）→ 格内文本（行中心落带 + 字符落列区间，多行按行间规则拼接）→ 产 `TABLE` 与 `TABLE_CELL`（含 `row` / `col` / `rowSpan` / `colSpan` / `bbox` / `isHeader`）；网格拟合不出来时退回文本路径。
5. **其余行 → 段落与文本表格候选**（`PdfBodyAssembler.flushTextRun` + `TextTableBuilder`）：行距超阈值或行序回跳（进下一栏 / 下一带）时结算段落与表格块；候选行连续成块后**先把续行并进上一行**（行距 ≤ `tableRowInnerGapRatio × 字号`、token 落在上一行范围内且不越过其右边界），再按**列区间**成表：边界取 token 左起点与右边界两侧的对齐线聚类，列内 token 按**中心点**归属，行支持度过滤后首尾相接；单元格文本按 token 整块归列（右对齐数字列不被列边界劈开），覆盖度按「行内 token 全部落在列上」计，稀疏格（某列为空）不影响覆盖。该路径不产 `rowSpan` / `colSpan`。**列聚类容差按块内最大字号折算**（`tableColumnToleranceRatio`，默认 0.25）：大字号行的 token 起点抖动更大，固定像素容差会把同一列拆成虚列、支持度不足而整列落空。
6. **假表与降级**：两条路径都过空白率门限；列聚类失败或空白率过高时块降级为段落，并在 `sources[].facts` 留一条 `TABLE` 事实（证据文案区分「列对齐聚类失败」与「空白率过高」）。**列对齐聚类失败**这一步先试表格结构能力（`CapabilityRegistry.table()`，默认关）：模型给出可用结构就用它出 `TABLE` 元素并记一条「能力补强」事实、把模型名与版本记进 `sources[].capabilities`；未接入或结果不可用则按上面的原口径降级，并额外记一条「能力降级」事实（原因区分未接入能力 / 区域为空 / 调用失败或结果不完整）。
7. **版面阅读顺序**：复杂页（行内相邻 token 间隙达 `layoutColumnStartTolerance × layoutSpanningGapFactor` 的行数 ≥ `layoutModelMinSpanningLines`，即提取阶段没把多栏拆开）先试版面能力（`CapabilityRegistry.layout()`，默认关）；模型给出区域与顺序就按行中心命中的区域重排正文行序并留痕（能力引用 + 补强事实），几何口径是其余所有情形的默认。
8. **图片元素**：`PdfImageEmitter.emit` 对图片矩形按面积占比过滤（低于 `imageMinAreaRatio`，默认 0.05 页面积，即 logo 与装饰小图不产元素），达门槛的按页内自上而下产 `IMAGE` 元素（`assetRef`、`needsOcr=true`、本页 `bbox`）；`OCR_IMAGE` 事实**按页聚合一条**（证据带本页张数与合计占页面积）。
9. **页内元素 ID**（`PageElementIds.assign`）：本页元素按产出顺序编号，ID = 类型前缀（`p` 段落 / `t` 表格 / `c` 单元格 / `i` 图片 / `h` 页眉 / `f` 页脚）+ 页码 + 页内序号 + 位置（bbox 左上角的整 pt），如 `t1_0_72_142`、`p1_2_72_442`；序号保证单页内唯一、同一输入可复算，表格的单元格挂在表 ID 下（`t1_0_72_142_c0_0`），同页多表的单元格不重号。产出点自身不拼 ID。
10. **溯源口径**：表与单元格由 `PageTableProvenance.assign` 在后处理里按页内表序号补路径（表 `pdf#page(n)/table[i]`、单元格 `.../table[i]/cell[r,c]`，`i` 从 0 起按产出顺序）；段落装配时写 `pdf#page(n)/chars[i..j]`，区间按页内阅读顺序累计行内字符数（行间不计分隔符），取段首行行首到段尾行行尾。产出点不写表与单元格路径。

表头判定（两条路径共用 `TextTableBuilder.detectHeaderRow`）：首行含数字单元格占比不超 `tableHeaderMaxNumericRatio`（默认 0.3），且表体含数字或首行字号明显大于表体 → `headerRow = 0`；判不出时 `headerRow` 为 `null`。

贴页底判定：表格包围盒底边进入页高 95% 以上时置 `cutAtPageBottom`，供组装环节判续表。

### 5.4 分栏与阅读顺序端口（`pdf/layout/`）

- 端口 `PageLayoutAnalyzer` 自带请求 / 响应 / 阈值类型（`Input` / `Box` / `Result.Placed` / `Options`）与切行口径静态方法（`crosses` / `crossesAny` / `columnOf`），解析器与实现共用同一判栏口径。
- 规则实现 `ProjectionPageLayoutAnalyzer`（`@Component`）：字符横向覆盖做直方图（分箱 1pt），竖直覆盖比例 ≤ `columnGutterMaxCoverage`（默认 0.25）且宽度 ≥ `columnGutterMinWidth`（默认 10pt）的横向带成候选栏沟；候选按宽度从大到小逐个试，加进去后每栏都满足 `columnMinChars`（默认 10）与 `columnMinShare`（默认 0.1）才接受，栏数上限 `columnMaxCount`（默认 4）；单页字符数低于 `columnMinPageChars`（默认 100）不进分栏判定。
- 阅读顺序：跨栏行把页面切成上下若干带，带内跨栏行按纵向在前，其余按「栏序 → 栏内纵向顺序」；未判出栏沟时保持纵向顺序。**单栏行溢出栏宽不算跨栏行**：排顺序时按行内字符中心的归属栏裁剪行盒（中心落在非主栏的字符占比 ≥ 0.3 才算真正跨栏），长行不会把页面误切成上下带。

### 6.3 单元文本与预算

- **Word 系**：`budgetElements` 按产出顺序遍历全档元素、`budgetText` 取文本（段落取自身文本；表格取自身文本 + 各单元格文本；页眉页脚元素取自身文本），按 `officePageChars`（默认 3000）个非空白码点切一个虚拟单元，余量不足一页也成单元，空文本仍算 1 个单元。**表格内容与页眉页脚内容都计入字符预算**；图片按它在正文里的位置归到所属单元。
- **Excel**：每个 worksheet 一个单元，单元文本取该 sheet 已产出的非空单元格文本。
- **图片计数**：Word 系把全档图片数记在**首个单元**（不按位置归属）；Excel 按 sheet 记图片张数。
- `PageMetric.page` 是 1 基单元序号（Word 为虚拟页序号、Excel 为 sheet 序号）；Excel 的 TABLE 元素 `page` 是 0 基 sheet 序号，两处口径不同。

## 七、信号判定

`signal/impl/SignalDetectorImpl.detect` 是唯一判定入口：入参是原生路的 `ParseSource` 与上下文，出参是 `List<Signal>`（`type` + `subtype` + `region` + `evidence` + `threshold`）。`ParseSource` 或阈值配置为空时返回空集合。

判定分两段，**先指标后事实**：

**① 指标段**（逐单元，`PageMetric` → 信号）。下表是 `else-if` 链，同一单元最多产 1 条信号，命中即跳出：

| 序 | 条件                                                                                                                             | 信号（type / subtype）                         | 结论                                                                                                                                      |
|----|----------------------------------------------------------------------------------------------------------------------------------|------------------------------------------------|-------------------------------------------------------------------------------------------------------------------------------------------|
| 1  | `charCount ≤ 0` 且含图片（`imageAreaRatio ≥ scanPageImageRatio` 或 `imageCount > 0`）                                            | `OCR_TEXT` / `SCANNED`                         | 扫描单元：计失败单元 + 登记扫描页                                                                                                         |
| 2  | `charCount ≤ 0` 且无图片，但矢量覆盖率 `≥ vectorPageMinRatio`                                                                    | `OCR_TEXT` / `VECTOR_GRAPHIC`                  | 纯矢量单元：不计失败，只从分母剔除（与空白单元同处置，告警单列）                                                                          |
| 3  | `charCount ≤ 0` 且无图片且矢量覆盖率低于门槛                                                                                     | `OCR_TEXT` / `BLANK`                           | 空白单元：不计失败，只从分母剔除                                                                                                          |
| 4  | `charCount > 0` 且（`textAreaRatio` 在 `(0, textAreaRatioThreshold)` 内，或 `imageCount > 0` 且 `charCount < scanPageMinChars`） | `OCR_IMAGE` / `IMAGE_LOW_RATIO`                | 疑似图片单元：仅告警                                                                                                                      |
| 5  | `charCount > 0` 且乱码率 `> garbledRateThreshold`                                                                                | `OCR_TEXT` / `GARBLED` 或 `CID_MAPPING_FAILED` | 乱码单元：计失败单元；字符主要来自缺 Unicode 映射的 CID 字体（`cidMappingRatio ≥ cidMappingMinRatio`）时子类型单列为 `CID_MAPPING_FAILED` |

**② 事实段**（逐条 `ParseFact` → 信号，原样透传 `region` / `evidence`）：`OCR_IMAGE` → `IMAGE_EMBEDDED`、`TABLE` → `TABLE_RULE_FAILED`、`LAYOUT` → `LAYOUT_RULE_FAILED`。事实由解析器写在 `ParseSource.facts` 里（PDF 的图片与表格降级、Office 的图片未识别），`ParseFact.type` 取 `SignalType` 枚举、为空的事实被判定器忽略。`LAYOUT` 事实当前没有产出方（枚举与 handler 标注为预留），这条子类型在主代码里没有触发路径。

`region` 口径：指标信号为 `page N`（Excel 为 sheet 序号），事实信号沿用事实自带的 region（如 `page 2 image 0`、`paragraph[3]`）。`threshold` 字段对指标信号填指标快照文案（字符数、图片口径、实测值与配置值），对事实信号填 `-`。

一处口径分工（现已显式化，见 `isSuspectImageUnit`）：第 3 条的「文字占比低」只对回填了 `textAreaRatio` 的单元生效（PDF 侧；Office 侧该字段为 0，表示口径不适用），Office 的疑似图片单元按「内嵌图片数 > 0 且字符数 < `scanPageMinChars`」判定；证据文案按命中的口径分写，落在 `Signal.threshold`。

## 八、内置降级处置

`ParsePipeline.applyFallback` 按 `SignalSubtype` 找唯一匹配的 `SignalFallbackHandler`（9 个子类型与 9 个 handler 一一对应），返回值是该信号计入的**失败单元数**。所有 handler 都往 `QualityInfo.warnings` 追加一条 `WARN` 级告警（`elementId` 为 null）。

| 子类型               | handler                           | 告警码                    | 登记清单        | 计失败单元 |
|----------------------|-----------------------------------|---------------------------|-----------------|------------|
| `SCANNED`            | `ScannedFallbackHandler`          | `SCANNED_PAGE`            | 扫描页 + 失败页 | 1          |
| `GARBLED`            | `GarbledFallbackHandler`          | `GARBLED_PAGE`            | 失败页          | 1          |
| `CID_MAPPING_FAILED` | `CidMappingFallbackHandler`       | `CID_MAPPING_FAILED_PAGE` | 失败页          | 1          |
| `BLANK`              | `BlankFallbackHandler`            | `BLANK_PAGE`              | 空白页          | 0          |
| `VECTOR_GRAPHIC`     | `VectorPageFallbackHandler`       | `VECTOR_PAGE_SUSPECTED`   | 空白页          | 0          |
| `IMAGE_LOW_RATIO`    | `ImageLowRatioFallbackHandler`    | `IMAGE_PAGE_SUSPECTED`    | —               | 0          |
| `IMAGE_EMBEDDED`     | `ImageEmbeddedFallbackHandler`    | `IMAGE_TEXT_UNRECOGNIZED` | —               | 0          |
| `TABLE_RULE_FAILED`  | `TableRuleFailedFallbackHandler`  | `TABLE_RULE_FALLBACK`     | —               | 0          |
| `LAYOUT_RULE_FAILED` | `LayoutRuleFailedFallbackHandler` | `LAYOUT_RULE_FALLBACK`    | —               | 0          |

口径与边界：

- 内置降级下失败单元数只可能是 **0 或 1**（每个失败单元最多命中一条指标信号）。
- `subtype` 为空或不是已知枚举名 → 计 0；找不到匹配 handler → 计 0（防御，不改状态）。
- 单元号由 region 反解（`FallbackSupport.parsePage` 把 `page 3` 解成 `3`）；解不出（元素级 region，如 `paragraph[3]`）时不登记清单，但仍产告警。
- `failedUnits`（整数累加）与 `quality.failedPages`（单元号列表）是两套独立口径，没有一致性校验。
- 告警文案以「第 {region} …」拼接，而 region 自带 `page ` 前缀，页级告警渲染成「第 page 3 …」。
- 降级只改产物与状态，不丢内容：表格规则失败时对应区域降级为段落，图片未识别只记录引用与图注。

## 九、成功门槛与失败语义

`ParsePipeline.evaluate` 按顺序判：

| 序 | 条件                                                                                                           | 建议状态 / 错误码                                                     |
|----|----------------------------------------------------------------------------------------------------------------|-----------------------------------------------------------------------|
| ①  | 单元数 ≤ 0                                                                                                     | `FAILED` / `PARSE_CORRUPTED`（无有效内容单元）                        |
| ②  | 内容单元 = 单元数 − 空白单元数 ≤ 0                                                                             | `FAILED` / `PARSE_CORRUPTED`（全为空白页）                            |
| ③  | 内容单元全被登记为扫描单元                                                                                     | `FAILED` / `SCANNED_UNSUPPORTED`（扫描件暂不支持）                    |
| ④  | 内容单元 ≤ `shortDocumentMaxUnits`（默认 3）且失败单元 ≤ `shortDocumentMaxFailedUnits`（默认 1）且仍有可读单元 | `SUCCESS`（无失败单元）或 `PARTIAL_SUCCESS`（短文档按坏页绝对数放行） |
| ⑤  | 成功占比 =（内容单元 − 失败单元）÷ 内容单元 ≥ `successUnitRatio`（默认 0.9）                                   | `SUCCESS`（失败单元为 0）或 `PARTIAL_SUCCESS`（有失败单元）           |
| ⑥  | 占比低于门槛                                                                                                   | `FAILED` / `RATIO_BELOW_THRESHOLD`（文案带内容单元数与失败数）        |

- **分母是内容单元**：空白单元既不算成功也不算失败，只从分母剔除；扫描单元计失败单元、参与分母。
- **短文档单独放宽**：1~3 个内容单元时比例门槛等价零容错（1 页坏就是 0%），改看坏页绝对数；坏页超过绝对数门槛时仍落占比判定。两个门槛都可配（`shortDocumentMaxUnits` 置 0 即关闭该规则）。
- **质量维度汇总**：门槛评估之后按「坏页（登记失败页）÷ 内容单元」再算一次比例，达到 `qualityBadPageRatioThreshold`（默认 0.3）时追加一条 `QUALITY_BAD_PAGE_RATIO` 告警，消息里按告警码列出各维度条数（逐条告警的语义不变，只多一层一眼可见的汇总结论）。
- `unitCount` 与 `failedUnits` 一并写进 `ParseOutcome`，页面侧的「页数 / 问题单元」口径读这两个值（见页面侧文档）。
- 占比不足时会打一条 warn 日志，带每单元的原始指标（字符数 / 乱码率 / 文字占比 / 图片口径），用来区分扫描件、乱码与文字占比三种成因。
- 硬失败（①②）之外的四类错误码都能带产物；`PARSE_FAILED` 只出现在路由阶段。

## 十、产物契约

持有关系：`ParseOutcome`（状态壳，继承 `StageOutcome`）→ `ParseResult`（写产物存储的 JSON 本体）→ `List<ParseSource>` + `QualityInfo` + `CapabilitySnapshot` + `FileReference`；`ParseSource` 向下持有元素、页级指标、事实、页面尺寸与单元数。

### 10.2 `ParseElement`（元素，24 个字段）

|-------------------------------|--------------------------|----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|

| `style`                       | Office 段落              | 段落样式名（DOCX `pStyle`，如 `Heading1`）                                                                                                                                                                           |

### 10.4 枚举口径

**`ElementType`（8 个，本环节实际产出 6 个）**：`PARAGRAPH`、`TABLE`、`TABLE_CELL`、`IMAGE`、`HEADER`、`FOOTER` 有产出；`FIGURE_CAPTION`（图注）、`LIST`（列表）保留枚举但当前不产出。标题层级（`TITLE` 类）不属本环节，归组装环节推定。

**`QualityWarningCode`（14 个）**：本环节用 10 个 —— `GARBLED_PAGE`（乱码单元，计失败）、`CID_MAPPING_FAILED_PAGE`（CID 映射失败单元，计失败）、`SCANNED_PAGE`（扫描单元，计失败）、`BLANK_PAGE`（空白单元，不计失败）、`VECTOR_PAGE_SUSPECTED`（纯矢量单元，不计失败）、`IMAGE_TEXT_UNRECOGNIZED`（图片文字未识别，仅告警）、`IMAGE_PAGE_SUSPECTED`（疑似图片单元，仅告警）、`TABLE_RULE_FALLBACK`（表格规则失败降级为段落，不计失败）、`LAYOUT_RULE_FALLBACK`（版面规则失败按原顺序输出，不计失败）、`QUALITY_BAD_PAGE_RATIO`（坏页比例达门槛时的维度汇总，仅告警）；其余 4 个（`TITLE_CANDIDATE` / `SUSPECTED_CONTINUATION` / `PROVENANCE_MISSING` / `NOISE_PAGE`）归组装环节。

**`ParseStepName`（3 个，落库取中文展示值）**：`FILE_ROUTE`「文件级路由」、`NATIVE_PARSE`「原生解析」、`QUALITY_CHECK`「质量检查」。

## 十二、能力预留与当前边界

- **模型能力现状**：`parser/capability/` 里 `CapabilityRegistry`（实现 `impl/CapabilityRegistryImpl`，按「Spring Bean 集合 × 开关」接线）、`CapabilityProperties`，以及 `LayoutProvider` / `TableStructureProvider` / `StructuredOcrProvider` 三个接口；三项能力的实现已改为经模型能力平台出口 `ModelGatewayPort.visionByCapability(...)` 出网（`impl/VisionTableStructureProvider` / `impl/VisionOcrProvider` / `impl/VisionLayoutProvider` 三个实现只做领域映射，提示词与输出约束落 `capability/prompt/CapabilityPrompts` 与 `capability/CapabilityRequests`，调用不通或结果不可用一律回落内置口径）。`knowledge.parse.capability.*` 是三项开关的前缀，厂商地址与凭据取 `knowledge.model.vendors.<厂商码>`。
- **产物能力项**：`CapabilitySnapshot` 的 `ocr` / `layout` / `table` 由各路 `ParseSource.capabilities` 汇总回填；三项能力的 provider 与路由都已落地（默认关，开关关闭或调用失败一律回落内置口径）。
- **OCR 路**：`sources` 的第二条，接入 OCR 能力后承载整页无文本且含图片单元的补齐文字；与 native 路重叠区域由组装环节裁决，本路不合并。
- **唯一实现是规则路径**：PDF 侧是投影法分栏 + 文本 / 线网格两条表格路径；Office 侧是 POI 对象模型直读。
- **未接入的格式**：PPT / PPTX（`FileFormat` 已登记，无解析器、未进白名单）。

## 十三、任务与落库边界

本环节在 worker 内是纯算法，落库与状态回写由 biz 编排完成，边界如下。

### 13.1 调用链

1. **触发**：`KnowledgeFileParseController.parse` → `ParseControlServiceImpl.parse`（过归属校验）→ `TaskTriggerSupport.trigger`：先校验存储一致性（链的数据源与当前启用的数据源不一致 → 40453），再按**执行键**（文件结果 + `PARSE` + 0 + 0）查任务 —— 已有任一状态的任务一律抛 40431（不返回既有结果），查不到才新建 `QUEUED` 任务并入队（入队失败落 `TASK_ENQUEUE_FAILED`）。`QUEUED` 补投归启动补偿与低频扫描，触发入口不做唤醒。
2. **消费**：`PipelineTaskConsumer` 常驻 dispatcher 线程用阻塞队列叫醒，按环节批量取 `QUEUED` 任务，交线程池执行，带**看门狗超时**（超时另路回写 `EXECUTOR_TIMEOUT`）。
3. **执行**：`ParseTaskRunner.run` 先 `TaskRunnerSupport.claim` 抢占（`QUEUED` → `RUNNING`，受影响行数须为 1），再读文件结果与源文件、**创建 `ParseContext`**（`fileRef` 由源文件转出，`inputStream` 在 try-with-resources 内打开），调用 `ParsePipeline.run`。
4. **收尾**：`TaskRunnerSupport.complete` 按 `outcome.suggestedStatus` 分支 —— 成功与部分成功先落产物再写任务终态；失败只落步骤日志、不落产物（`product_id` 留空）。

### 13.2 落库目标

| 目标                                 | 写入内容                                                                                                               |
|--------------------------------------|------------------------------------------------------------------------------------------------------------------------|
| 产物存储（对象存储，按内容哈希寻址） | `ParseResult` 的 JSON 本体（含 `sources` 的元素 / 页级指标 / 事实 / 单元数，`quality` 的四类清单）                     |
| `wb_knowledge_pipeline_product`      | 文件结果 ID、`stage=PARSE`、`upstream_product_id=null`（链首）、能力快照 JSON、`artifact_id`、`content_hash`、`status` |
| `wb_knowledge_pipeline_task`         | 回写 `product_id`；终态写 `status` / `error_code` / `error_msg` / `finished_at`（带 `RUNNING` 条件更新）               |
| `wb_knowledge_pipeline_step_log`     | 每个 `StepLogInfo` 一行：步骤中文名、状态、能力版本、起止时间与耗时、`warning_count`、`error`（截断 1000）             |
| `wb_file_result`                     | 解析链**只读**（取行用），没有解析状态字段可回写                                                                       |

### 13.3 状态与错误码

- `ParseOutcome.unitCount` 与 `failedUnits` 本身**不落库**：单元数经产物 JSON 的 `ParseSource.unitCount` 读回（页面统计用），失败单元清单取 `quality.failedPages`。
- 建议状态映射：`SUCCESS` / `PARTIAL_SUCCESS` → 任务成功终态；其余建议状态与错误码原样落到任务终态。
- 错误码归属：`PARSE_FAILED`（无匹配解析器；文件结果或源文件取不到；runner 兜底）、`PARSE_CORRUPTED`（解析器抛异常、读流失败、0 单元或全空白单元）、`SCANNED_UNSUPPORTED`（扫描单元数 ≥ 内容单元数）、`RATIO_BELOW_THRESHOLD`（占比不足）、`EXECUTOR_TIMEOUT`（看门狗）。
- `QUALITY_CHECK` 步骤状态恒为 `SUCCESS`：质量问题的诊断信息放在该步骤的 `error`（告警摘要）与任务级错误码上。
- 解析详情与产物内容的读取口径（告警清单、元素构成、分页过滤、原文预览）见 `../../pages/解析环节/`。
