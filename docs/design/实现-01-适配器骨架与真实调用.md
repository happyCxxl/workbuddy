# 模型能力平台 · 实现 01：适配器骨架与真实调用

**范围一句话**：把 `workbuddy-model` 的平台骨架立起来 —— 契约与端口是我们自己的，模块内部用 LangChain4j（下称 LC4j）的核心模块 `langchain4j-open-ai` 走 OpenAI 兼容协议接入 DashScope，配 `chat` 与 `embed` 两条链路，打一次真实调用跑通（含 `usage` 回填、错误码映射、超时）。

**本篇是逐文件施工口径**：类型与方法签名、配置键、错误码映射、测试用例、手工验收步骤都写到可执行粒度。设计与取舍见 [模型能力平台-方案设计.md](模型能力平台-方案设计.md)。

**边界前提（全文适用）**：契约与端口自有；**业务侧（`workbuddy-worker` / `workbuddy-biz`）看不到任何 LC4j 类型**；LC4j 类型只出现在 `workbuddy-model` 内部（`engine` / `adapter` / `invoke` / `listener` 四个包），业务侧不出现。

**入口口径（本片）**：`chat` / `vision` 只传 `vendorCode`；**模型名一处：请求体**（`ChatRequest.modelKey` / `VisionRequest.modelKey` / `EmbeddingRequest.model`）；`embed` 签名本片零改动（见 4.10）。

## 一、范围与不做

### 1.1 归属分工（谁用什么）

| 层                                             | 用什么                                                                                                                                                                                               |
|------------------------------------------------|------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| 业务侧（`workbuddy-worker` / `workbuddy-biz`） | **只用我们自己的契约**：`ChatRequest` / `VisionRequest` / `OutputSpec` / `GenerationResult` / `ModelUsage` 与端口方法；**不出现任何 LC4j 类型**                                                      |
| 平台（`workbuddy-model`）                      | 内部用 LC4j：`OpenAiChatModel` / `OpenAiEmbeddingModel`（`baseUrl` 指向 DashScope 兼容端点）、`ChatRequest` / `UserMessage` / `ImageContent` / `ResponseFormat` / `TokenUsage` / `ChatModelListener` |
| 平台对外                                       | 只有我们的契约、`ModelGatewayPort`、`ModelInvoker`、错误码                                                                                                                                           |

附注三条：

1. **同名类只在内部分流**：LC4j 的 `dev.langchain4j.model.chat.request.ChatRequest` 与我们的 `com.workbuddy.common.domain.model.ChatRequest` 同名，两者出现在同一个实现文件时用全限定名或局部别名区分；该同名不越过 `workbuddy-model` 边界。
2. **架构约束**：`workbuddy-model` 之外的模块不得出现 `dev.langchain4j` 开头的 import；该约束由依赖约束与架构测试守住（设计文档风险表「框架抽象泄漏」行）。
3. **换框架只动平台**：`engine` / `adapter` / `invoke` / `listener` 四个包是 LC4j 的全部落点（`invoke` 包按 `RetriableException` / `NonRetriableException` 与各异常类名判定，`listener` 包按 `HttpClient` / `HttpClientBuilder` SPI 计数），替换框架时契约、端口与业务侧不动，异常映射与 HTTP 层计数各一处随之调整。

### 1.2 本片做

| 项           | 内容                                                                                                                                                                                                                                                                    |

**Jackson 版本实测（本片结论）**：LC4j 1.22.0 的 `langchain4j-core` 声明 `com.fasterxml.jackson.core:jackson-databind:2.22.1`（`jackson-core` 2.22.1、`jackson-annotations` 2.22），Boot 3.2.5 的 `dependencyManagement` 把三条线的实际解析版本压到 **2.15.4**。`com.networknt:json-schema-validator:3.0.8` 传递 `tools.jackson.core:jackson-databind:3.2.1`（Jackson 3 命名空间，`tools.jackson.core:jackson-core` 3.2.1），该库类初始化阶段要读 `com.fasterxml.jackson.annotation.JsonSerializeAs`；该注解自 2.16 起才有，注解停在 2.15.4 时 `Class.forName("com.fasterxml.jackson.annotation.JsonSerializeAs")` 抛 `NoClassDefFoundError`，调 `SchemaRegistry.getSchema(...)` 直接失败。**两个命名空间并存，但共用 `com.fasterxml.jackson.annotation` 这一个包名，实测确会冲突**（注解 2.15.4 + `tools.jackson` 3.2.1 组合）。

| `ModelUsage`                         | 用量：`promptTokens` / `completionTokens` / `totalTokens`，三项都可为 null（D19）；字段与 LC4j `TokenUsage` 对齐为 `Integer`（`inputTokenCount` / `outputTokenCount` / `totalTokenCount`），未知为 null |
| `GenerationResult`                   | `chat` 与 `vision` 共用出参：`content` / `json` / `usage` / `model` / `modelVersion`                                                                                                                    |
| `domain/parse/capability/OcrRequest` | **只改 Javadoc**：预留类型、当前未被使用、平台走 `ModelGatewayPort.vision`；类定义与包名一行不动，**类本身保留**（D28）                                                                                 |

平台不定义字段名、不解释语义：`OutputSpec.schema` 由业务侧写，`GenerationResult.json` 是通用树。

**超时字段的口径**：`ChatRequest.timeoutMs` / `VisionRequest.timeoutMs` 只作契约字段保留 —— **超时只有实例级入口**（builder 的 `timeout(Duration)`，见 4.5 / 5.1），LC4j 1.22.0 的 `ChatRequest` / `ChatRequestParameters` / `ChatRequestOptions` 都没有 per-request 超时入口。

**`usage` 的映射口径**：`ModelUsage` 不是自造的 token 统计，它由 LC4j 回传的 `TokenUsage` 映射而来 —— `promptTokens` ↔ `inputTokenCount`、`completionTokens` ↔ `outputTokenCount`、`totalTokens` ↔ `totalTokenCount`，两者字段类型一致（`Integer`）；**厂商未回 usage 时整体为 null**（不是三项为 null 的空对象），回了但缺单项时缺的项留 null（D19）。映射落在**平台内部**一处（`workbuddy-model` 的 `listener/ModelUsageMapper`，适配器与监听器共用），业务侧不出现 LC4j 类型（D40）。

**目录视图契约（`MODEL-09`）**：`ModelDescriptor`（厂商归属 + 能力 + 价格 + 限额 + 状态 + 生效区间 + 向量规格段 `embedSpecs`）与 `ModelCapability`（`CHAT` / `EMBEDDING` / `OCR` / `LAYOUT` / `TABLE_STRUCTURE`）落 `common/domain/model/catalog`；库表实体 `KbModel` 与其余实体同在 `common/domain/entity`，Mapper 与库表实现留 `workbuddy-biz`（见 4.11）。**向量规格不进库表**：`dimension` / `metric` / `normalized` / `batchLimit` 由 `EmbeddingModel` 枚举承载，库表实现按模型名叠加到 `ModelDescriptor.embedSpecs`；库里声明 `EMBEDDING` 而枚举里没有的模型名，`embedSpecs` 为空、向量链路不可用；承载方式记为**待定**。

|------------------------------|-------|------------------------|
| `MODEL_MODALITY_UNSUPPORTED` | 40460 | 模型未支持该模态       |
| `MODEL_VENDOR_UNKNOWN`       | 40461 | 模型厂商未配置         |
| `MODEL_AUTH_FAILED`          | 40462 | 模型鉴权失败           |
| `MODEL_BAD_REQUEST`          | 40463 | 模型请求参数或内容被拒 |
| `MODEL_NOT_FOUND`            | 40464 | 模型不存在             |
| `MODEL_RATE_LIMITED`         | 40465 | 模型请求被限流         |
| `MODEL_TIMEOUT`              | 40466 | 模型请求超时           |
| `MODEL_SERVER_ERROR`         | 40467 | 模型服务端错误         |
| `MODEL_UNREACHABLE`          | 40468 | 模型服务不可达         |
| `MODEL_OUTPUT_INVALID`       | 40469 | 模型输出结构校验失败   |

口径四条：

1. **异常只有一种**：自造的异常类已删除，平台不新建异常类，调用失败一律抛 `KnowledgeException`（`workbuddy-common` 的统一业务异常），错误码取模型调用分区；**LC4j 异常 → 我们的错误码的映射落在 `invoke/ModelErrorClassifier`（`MODEL-05`）一处**，适配器只把 LC4j 异常原样抛出，LC4j 类型不越过适配器。
2. **"是否可降级"不在错误码里**：`ErrorCode` 只有码值与文案 —— **不带任何属性**，也没有为它加重载构造，现有常量零改动。判定归 `MODEL-05` 的 `invoke/ModelErrorClassifier`：映射与判定在同一处完成，`canFallback(Throwable)` **先看覆盖规则**（`MODEL_UNREACHABLE` / `MODEL_OUTPUT_INVALID` 归可降级），再看异常链上的 `RetriableException` / `NonRetriableException` 两个基类，逐条见第六节。
3. **detail 带定位信息**：厂商码必带，模型名能取到就带；文案是错误码自身的短语，detail 只补"哪一家、哪个模型"，排障时不必回读配置。
4. **码值分区不交叉**：十个码值连续占 40460~40469，与既有码值不重号；归属模型调用的注释写在该段之上。

**装配口径**：本片只有一个适配器实现，**不建适配器注册表**；`OpenAiCompatibleAdapter` 按仓库习惯用组件注解装配（`@Component` + 构造注入），由 `ModelInvoker` 直接持有；**适配器只持有 `ModelInstanceRegistry`**，不持有 `ModelVendorProperties`，调用时把 `vendorCode` 与请求里的模型名交给注册表取实例。**实例挑选与厂商解析归 `engine/ModelInstanceRegistry`**：未知厂商 → `MODEL_VENDOR_UNKNOWN`（40461），模型名空 → `MODEL_BAD_REQUEST`（40463）。等接入第二种协议时再加"配置里的协议字段 + 按协议选适配器"（届时才需要注册表）。

**熔断与选型都在适配器之外**：健康判定与打开保持由路由片的 `ModelCircuitBreakers`（Resilience4j 核心模块）承担，适配器只按入参发一次调用、把 LC4j 异常原样抛出（映射与判定归 `invoke/ModelErrorClassifier`，见 4.6 / 第六节）。

口径四条：

1. **职责分层**：工厂**无状态**，只按入参建实例，**不注入** `ModelVendorProperties`，也**不注入** `List<ChatModelListener>`；**厂商解析与未知厂商校验归注册表**（未知厂商 → `MODEL_VENDOR_UNKNOWN` 40461，模型名空 → `MODEL_BAD_REQUEST` 40463）。
2. **key 与构建参数都来自 vendors 配置**（D29 / D38 修订 / D41）：`vendor` 决定 `baseUrl` / `apiKey` / `timeout` / `maxRetries`，`modelKey` 决定 LC4j 的 `modelName`。
3. **懒构建 + 复用**：同 `vendorCode` + 同模型名 + 同模态只建一次实例（`computeIfAbsent` 语义），对话与向量各一张表；实例缓存在进程内，配置变更需重启生效。
4. **类型名与监听器挂载点**：LC4j 1.x 的对话接口是 `dev.langchain4j.model.chat.ChatModel`（0.x 线写作 `ChatLanguageModel`）；**挂载点都是工厂构建方法内的 builder** —— 对话模型挂 `listeners(usageRecordingListener)`，向量模型与对话模型都挂 `httpClientBuilder(new CountingHttpClientBuilder(modelCallTraceHolder))`（计数口径见 4.8）。**向量侧没有用量监听**：`OpenAiEmbeddingModel.Builder.listeners(...)` 只接受 `EmbeddingModelListener`，`ChatModelListener` 挂不上，向量侧监听随 `MODEL-07`（嵌入改造）接入。

**重试与超时口径（D38 修订 / D41，含实测）**：`timeout-ms` 映射 LC4j 的 `timeout`（**单一总超时**，不区分连接与读取，**实例级唯一入口**）；`max-retries` 映射 LC4j 的 `maxRetries` —— **LC4j 的重试开着，平台不另加重试**。实测四条：`maxRetries=0` 时失败只发 **1** 次请求；`maxRetries=2` 时发 **3** 次请求；`timeout` 取 300 毫秒能切断 1500 毫秒的慢应答并抛 `dev.langchain4j.exception.TimeoutException`；假服务收到的请求数与上下文里的 `attempts` 逐次相等（装饰器的计数点就在真实请求前）。换模型降级与熔断归路由片（`MODEL-11` 已落地：健康判定由 Resilience4j 熔断器承担，见 §10）。

**入口面（`MODEL-09` 落地后）**：`chat` 与 `embed` 都经 `ModelInvoker` —— 两个模态共用形参校验、调用上下文绑定与「异常 → 错误码」映射，可降级判定同一套；`vision` 的调用入口随 `MODEL-12`（视觉通路）接上；端口与 SPI 的方法签名按 4.10 保持。**`MODEL-11` 落地后另有两个按能力选型的入口**（`chatByCapability` / `embedByCapability`）：候选顺序由 `ModelRouter` 给出，逐个候选取熔断许可、各落一行明细，失败且可降级时换下一个；选型、熔断与容量记账都在 `route/` 包，调用器只按选型结果尝试。

**一次调用的顺序（实测）**：形参校验（厂商码空按 `MODEL_VENDOR_UNKNOWN`、入参空按 `MODEL_BAD_REQUEST`，见 4.5）→ `checkBeforeCall(OutputSpec)`（`JSON_SCHEMA` 缺 schema 在此拒绝，请求不发出）→ `ModelCallTraceHolder.bind(trace)` → 一次调用（重试与退避由 LC4j 内部完成）→ 结构校验与 `json` 回填 → 返回，`finally` 里 `ModelCallTraceHolder.clear()`。

**调用上下文的通道（实测）**：`ModelInvoker.chat` 把本次调用的 `ModelCallTrace` 绑在调用线程上 → 适配器 `chat` 建请求选项时用 `ChatRequestOptions.builder().addListenerAttribute(ModelCallTrace.ATTRIBUTE_KEY, trace).build()` 放进属性表（**未绑定时取 `ChatRequestOptions.EMPTY`**，监听器静默跳过）→ 监听器按同一个键取回 → 调用结束在 `finally` 里 `clear()`；HTTP 客户端装饰器读的是同一份线程上下文，取不到即直通。

**向量侧（`MODEL-07`）的通道是"属性表优先，取不到回退线程绑定"（实测）**：`EmbeddingModel.embed` 每次调用自建请求属性，向量请求体没有放属性的入口，属性表这条路在向量侧取不到值；`DashScopeModelProvider.embed` 改**复用调用线程已绑定的 trace**（未绑定才自建一份，并在本次调用结束时 `clear()`），监听器先按属性表取、取不到再取 `ModelCallTraceHolder.current()`。复用而非覆盖是"绑定后可观测"的关键：上层先 `bind` 再调 `embed`，三项计数与用量才落得进同一份上下文（细节见 4.8）。

**失败时的映射（实测）**：错误码经 `ModelErrorClassifier.classify` 得出，`KnowledgeException` 的 detail 形如「厂商：X，模型：Y，原因：<厂商原文>」（原文缺失时取异常类名）；适配器抛出的原始异常挂到 `cause`（用 `initCause` 挂载，未改 `KnowledgeException` 的构造签名），`canFallback(error)` 与 `canFallback(error.getCause())` 结论一致。

职责边界：

| 做                                                                                                                                                                           | 不做                                                                                                            |
|------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|-----------------------------------------------------------------------------------------------------------------|
| 取实例：把厂商码与请求里的模型名交给 `ModelInstanceRegistry`（未知厂商、空模型名由它拒绝，见 4.5）                                                                           | **不做跨模型降级**（换模型重试归目录 / 路由片）                                                                 |
| 厂商来源：`chat` / `vision` 由端口参数给定（路由片就位后由其打分结果填充）；`embed` 由 `ModelInstanceRegistry.resolveVendorCode` 按目录解析「模型 → 厂商」（见 4.10 / 4.11） | **不自行判"厂商在不在"**、不重复校验 `auth-type` 支持集、不注入厂商配置                                         |
| **一次调用**：形参校验 → 调用前结构检查 → 调用（**重试与退避由 LC4j 内部完成**）→ 结构校验与 `json` 回填（D39）→ 返回                                                        | 不做重试与退避（归 LC4j 的 `maxRetries`）                                                                       |
| 调适配器、回填 `usage` 与模型版本                                                                                                                                            | 不做熔断、在途计数、延迟 EWMA（这三样归 `route/` 包的 `ModelCircuitBreakers` 与 `RouteStateStore`，`MODEL-11`） |
| 错误映射与分类：**把 LC4j 与运行时异常映射成我们的错误码**，`canFallback(Throwable)` 覆盖规则优先、其次按两个基类当场判定（见第六节），供后续片的降级链取用                  | 不落计量、不做指标；不做缓存、不做排队                                                                          |

**重试与退避口径**：同一实例内的重试与退避**由 LC4j 承担**（`max-retries` → `maxRetries`，见 5.1），`ModelInvoker` **不另加重试**；错误分类的用途是**决定是否可降级**，判定与映射在同一处完成 —— 先看覆盖规则，再看异常链上的 `RetriableException` / `NonRetriableException`（见第六节）：可降级 = 限流 / 请求超时 / 服务端错误 / 网络不可达（含 DNS 解析失败与连接被拒）/ 输出结构校验失败，不可降级 = 未支持模态、厂商未配置、鉴权失败、参数或内容被拒、模型不存在、未识别异常；降级链在 `MODEL-11` 落地（按候选顺序换下一个模型，见第十节）。

**熔断侧的失败口径（`MODEL-11`）**：供熔断器取用的谓词是同一处的 `ModelErrorClassifier.isVendorUnhealthy(Throwable)` —— **只把厂商侧不健康的失败计入**（限流 429、5xx、超时、连接失败、DNS 不可达；鉴权失败、参数错、内容拒绝、模型不存在、输出结构校验失败按成功记），**未识别异常按 `MODEL_SERVER_ERROR` 计且计入失败**（保守口径）；它与 `canFallback` 是两条独立判据（一个看厂商侧可用性，一个看能否换模型重试），差异点各有用例覆盖（见 7.1）。

**厂商配置不进调用器**：`ModelVendorProperties` 只由 `ModelInstanceRegistry` 持有（配置解析与未知厂商校验都在那一处），调用器持有它会成为未使用字段，PMD 静态检查直接判失败。

```java
package com.workbuddy.model.validate;

@Component
public class OutputSchemaValidator {

    /** 调用前：JSON_SCHEMA 的 schema 为空白即拒绝，请求不发出（错误码 MODEL_BAD_REQUEST） */
    public void checkBeforeCall(OutputSpec output) { ... }

    /**
     * 调用后：TEXT 返回 null（不校验）；JSON_OBJECT 校"是否为合法 JSON 对象"；
     * JSON_SCHEMA 用 com.networknt:json-schema-validator 做严格 schema 校验。
     * 通过即返回解析后的对象树，供 GenerationResult.json 回填。
     */
    public Object validate(OutputSpec output, String content) { ... }
}
```

**两个入口的分工（实测签名）**：`checkBeforeCall(OutputSpec)` 落在调用前 —— `JSON_SCHEMA` 的 schema 为空白（null / 空串 / 全空白）即拒绝，请求不发出（假服务收到 **0** 次请求）；`validate(OutputSpec, String content)` 落在调用后 —— 收模型输出的**原始文本**，通过即返回解析后的对象树（`TEXT` 返回 null），`ModelInvoker` 用它回填 `GenerationResult.json`；缺 schema 的 `JSON_SCHEMA` 走到这里同样拒绝，错误码与调用前一致。

`JSON_SCHEMA` 的严格校验走 `com.networknt:json-schema-validator`（依赖口径见 2.2），校验失败抛「输出结构校验失败」错误码、**不重试**，可作降级到下一个模型的触发条件（见 6.1）。解析口径覆盖 JSON 对象与数组：`JSON_OBJECT` **取严** —— 顶层不是 JSON 对象（数组 / 标量 / 空文本）按 40469 拒绝；`JSON_SCHEMA` 的根为标量时解析器不接受（对象 / 数组支持）。schema 文本自身不合法（无法编译）按 `MODEL_BAD_REQUEST`（40463）拒绝。

口径八条：

1. **尝试次数在真实 HTTP 层计**：落点是 LC4j 的官方扩展点 `HttpClientBuilder` / `HttpClient` SPI（文档的 *Customizable HTTP Client* 一节），每次真实请求 +1 —— `attempts` = 真实 HTTP 请求次数，`retry_count = attempts − 1`。**监听器不参与计数**：LC4j 的重试在 `OpenAiChatModel.doChat` 内部由 `RetryUtils.withRetryMappingExceptions` 完成，一次 `chat` 调用只触发一次 `onRequest`，回调次数推不出真实尝试次数（实测：`max-retries=2` + 首次 500 后成功，假服务收到 2 次请求，`onRequest` 只回调 1 次）。
2. **被包装的客户端取 LC4j 默认实现**：`CountingHttpClientBuilder(ModelCallTraceHolder)` 内部用 `HttpClientBuilderLoader.loadHttpClientBuilder()` 取默认构建器（服务加载；实测解析到 `dev.langchain4j.http.client.jdk.JdkHttpClientBuilder`，构建出 `JdkHttpClient`），`connectTimeout` / `readTimeout` 的读写两个方向都转发，`build()` 出来的客户端再包一层计数器。两个构建方法各取一份构建器，超时状态不在模型实例之间串用。
3. **装饰器不改调用语义**：请求一律转给被包装客户端，返回值与异常原样透出，本层不重试、不改写异常、不吞异常；当前线程没有绑定调用上下文即静默直通（不计数、不抛错）；`executeAsync` 与 `stream` 两个入口原样转发（发起线程不在本层控制内，不计数）。重试仍归 LC4j 的 `maxRetries`。
4. **`latency_ms` 是一次逻辑调用的整段耗时**（含 LC4j 内部重试与退避等待）：`onRequest` 记首次请求的时间戳，`onResponse` / `onError` 取差值，一次逻辑调用只算一次，失败也记。另有 `lastAttemptLatencyMs` = 最近一次真实 HTTP 尝试的耗时（只在阻塞入口记录，流式入口的返回时机与事件流生命周期相关，不记）。
5. **`usage` 一条口径两处一致**：`trace.usage()` 与 `GenerationResult.usage` 同源同口径，都由 `ModelUsageMapper` 从 LC4j 的 `TokenUsage` 映射 —— 厂商未回 usage 时**整体为 null**；回了但缺单项时**缺的项留 null**（D19），两项都不做本地估算、不写 0。
6. **调用上下文的通道**：`ModelInvoker.chat` 用 `ModelCallTraceHolder.bind(trace)` 绑在调用线程上 → 适配器用 `ChatRequestOptions.builder().addListenerAttribute(ModelCallTrace.ATTRIBUTE_KEY, trace).build()` 放进请求选项属性表（**未绑定时取 `ChatRequestOptions.EMPTY`**）→ 监听器按同一个键取回 → 调用结束在 `finally` 里 `clear()`；HTTP 客户端装饰器与监听器读的是同一份上下文。本片**只回填与打日志**，明细落库归计量片。LC4j 的回调方法名与上下文类型名（`onRequest` / `onResponse` / `onError` 与 `ChatModelRequestContext` / `ChatModelResponseContext` / `ChatModelErrorContext`）以实现时该版本 Javadoc 为准。
7. **向量侧的通道是"属性表优先，取不到回退线程绑定"（实测）**：`EmbeddingModel.embed` **每次调用自建请求属性**，向量请求体没有放属性的入口，对话侧"适配器把 trace 放进属性表"这条路在向量侧不存在 —— 实测属性表里取不到 `ModelCallTrace.ATTRIBUTE_KEY`。监听器 `trace(attributes)` 按这个事实写成两段：先按属性表取，取不到再取 `ModelCallTraceHolder.current()`；两处都没有即静默跳过。`DashScopeModelProvider.embed` **复用调用线程已绑定的 trace**（同一线程上的多次 `embed` 累计在同一份上下文里），**未绑定才自建一份、并在本次调用结束时 `clear()`** —— 复用而非覆盖，是"绑定后可观测"的关键：上层先 `bind` 再调 `embed`，监听器与 HTTP 客户端装饰器读到的就是同一份上下文。`EmbeddingModelListener` 的三个回调挂在向量模型实例上（工厂的 `embeddingModel(...)` 内 `listeners(List.of(usageRecordingListener))`）。
8. **`embed` 路径可观测的四项（实测）**：`attempts`（HTTP 客户端装饰器写，向量调用同样计真实请求数）、`lastAttemptLatencyMs`（最近一次真实尝试耗时）、`latencyMs`（一次逻辑调用的整段耗时）、`usage`（用量）。**向量应答的用量只有提示词一项**：`TokenUsage` 回 `inputTokenCount`，映射后 `promptTokens` 有值，`completionTokens` / `totalTokens` 缺失留 null（D19）；厂商整段不回 usage 时 `trace.usage()` 整体为 null。嵌入侧的异常经 `ModelInvoker` 走与 `chat` 同一套错误码映射与可降级判定（`MODEL-09` 已接入）；应答缺向量数据按「输出结构校验失败」（`MODEL_OUTPUT_INVALID`，40469）拒绝，覆盖规则下归可降级）。

### 5.2 启动期校验（D35 / D37）

| 校验项                                                       | 不满足时的行为                                                                                                             |
|--------------------------------------------------------------|----------------------------------------------------------------------------------------------------------------------------|
| `vendorCode`（Map 键）非空                                   | 启动失败，消息里指出该厂商码                                                                                               |
| `auth-type` ∈ 该厂商归属适配器的 `supportedAuthTypes()`      | 启动失败，消息里指出该厂商码与其 `auth-type`                                                                               |
| `api-key` 解析不出来（空 / 未设置）                          | 启动失败，消息里指出该厂商码                                                                                               |
| `base-url` 给了就必须是合法 URL（http/https）                | 启动失败，消息里指出该厂商码                                                                                               |
| `auth-type` 落在唯一适配器 `supportedAuthTypes()` 的支持集内 | 启动失败，消息里指出该厂商码与其 `auth-type`（适配器名与 `auth-type` 一起写进消息）                                        |
| 厂商数量（**不设上限**）                                     | **放行**：当时的规则 A 数量校验已删除（见 4.10 / 4.11）；`embed` 按目录解析「模型 → 厂商」，多厂商配置与单厂商配置都能启动 |

口径四条：

1. **只校验配置里列出的厂商**：`knowledge.model.vendors` 没列的厂商不进校验，也不进运行时；
2. **缺密钥即失败**：`api-key` 解析不出来（空 / 未设置）直接终止启动，错误信息里带**厂商码**；不做"记警告继续跑"；
3. **占位符写 `${ENV_VAR:}`（带空默认）**：环境变量没设时绑定到空串，由校验器给出"该厂商码缺 api-key"的可读错误，不由 Spring 抛"占位符无法解析"；
4. **不做适配器覆盖校验**：本片只有一个适配器实现、直接注入，配置里没有协议字段，启动期不校验"厂商码能被哪个适配器覆盖"（接入第二种协议时再加这条）。

校验落在 `config/ModelVendorValidator`（`implements ApplicationRunner`，容器启动时执行 `run`，实测即为该落点），首个不通过即抛 `KnowledgeException` 终止启动；`knowledge.model.vendors` 整段缺省时厂商集合为空，校验直接放行（见口径 1）。

**厂商数量不设上限（`MODEL-09` 后的口径）**：当时的两层口径（启动期比对厂商数量 + 首次调用 `compatibleVendorCode()` 兜底）已随目录落地删除；`embed` 的厂商归属由目录按「模型 → 厂商」解析（见 4.10 / 4.11），配置里出现多个厂商不再影响启动。

## 六、错误码映射与结构校验

**落点**：**异常 → 我们的错误码的映射落在 `invoke/ModelErrorClassifier`（`MODEL-05`，由 `invoke/ModelInvoker` 在失败时调用）**；适配器层保持"原样抛出 LC4j 异常"，不自行转换。下表第 2 列是实测的异常侧落点，第 4 列是 LC4j 自身行为，第 5 列是 `canFallback(Throwable)` 的判定路径。

| 触发条件                                              | 实测异常侧落点                                                                              | 我们的错误码                          | LC4j 是否内部重试（由两个基类决定）              | 可降级判定路径（`MODEL-05`）                                           |
|-------------------------------------------------------|---------------------------------------------------------------------------------------------|---------------------------------------|--------------------------------------------------|------------------------------------------------------------------------|
| 未配置该厂商（注册表拒绝，见 4.5）                    | —                                                                                           | `MODEL_VENDOR_UNKNOWN`（40461）       | —                                                | 平台侧规则：不可降级                                                   |
| 模型名为空（注册表拒绝，见 4.5）                      | —                                                                                           | `MODEL_BAD_REQUEST`（40463）          | —                                                | 平台侧规则：不可降级                                                   |
| `JSON_SCHEMA` 缺 schema（调用前由校验器拒绝，见 6.1） | —                                                                                           | `MODEL_BAD_REQUEST`（40463）          | —                                                | 平台侧规则：不可降级                                                   |
| 适配器未实现该模态（端口 / SPI 默认实现）             | —                                                                                           | `MODEL_MODALITY_UNSUPPORTED`（40460） | —                                                | 平台侧规则：不可降级                                                   |
| 密钥无效 / 无权限（HTTP 401 / 403）                   | `AuthenticationException`                                                                   | `MODEL_AUTH_FAILED`（40462）          | 否（`NonRetriableException` 子类）               | 基类判定：不可降级                                                     |
| 触发限流（HTTP 429）                                  | `RateLimitException`                                                                        | `MODEL_RATE_LIMITED`（40465）         | 是（`RetriableException` 子类）                  | 基类判定：可降级                                                       |
| 参数错误（4xx；不含 401 / 403 / 404 / 408 / 429）     | `InvalidRequestException`                                                                   | `MODEL_BAD_REQUEST`（40463）          | 否（`NonRetriableException` 子类）               | 基类判定：不可降级                                                     |
| 内容审核拒绝                                          | `ContentFilteredException`                                                                  | `MODEL_BAD_REQUEST`（40463）          | 否（`NonRetriableException` 子类）               | 基类判定：不可降级                                                     |
| 模型不存在（HTTP 404）                                | `ModelNotFoundException`                                                                    | `MODEL_NOT_FOUND`（40464）            | 否（`NonRetriableException` 子类）               | 基类判定：不可降级                                                     |
| 服务端错误（HTTP 5xx）                                | `InternalServerException`                                                                   | `MODEL_SERVER_ERROR`（40467）         | 是（`RetriableException` 子类）                  | 基类判定：可降级                                                       |
| 响应体不是合法 JSON（200 + `not-json`）               | 实测外层 `RuntimeException`，`cause` = `com.fasterxml.jackson.core.JsonProcessingException` | `MODEL_OUTPUT_INVALID`（40469）       | 否                                               | 覆盖规则：可降级                                                       |
| 响应缺 `choices`（200 + 结构不符）                    | 实测 `InternalServerException`                                                              | `MODEL_SERVER_ERROR`（40467）         | 是（`RetriableException` 子类）                  | 基类判定：可降级                                                       |
| 超时（HTTP 408 或客户端读 / 连接超时）                | `TimeoutException`                                                                          | `MODEL_TIMEOUT`（40466）              | 是（`RetriableException` 子类）                  | 基类判定：可降级                                                       |
| DNS 解析失败                                          | `UnresolvedModelServerException`                                                            | `MODEL_UNREACHABLE`（40468）          | 否（`NonRetriableException` 子类，覆盖规则优先） | 覆盖规则：可降级                                                       |
| 连接被拒                                              | 实测外层 `RuntimeException`，`cause` = `java.net.ConnectException`                          | `MODEL_UNREACHABLE`（40468）          | 否                                               | 覆盖规则：可降级                                                       |
| 未识别异常（兜底）                                    | —（异常链上未命中已知类型）                                                                 | `MODEL_SERVER_ERROR`（40467）         | —                                                | 覆盖规则与两个基类都未命中：不可降级（**熔断侧按不健康计**，见口径 6） |
| 输出未过结构校验                                      | —（平台侧校验，LC4j 不感知）                                                                | `MODEL_OUTPUT_INVALID`（40469）       | 否                                               | 覆盖规则：可降级（可作降级触发条件）                                   |

第 2 列的 LC4j 异常都在包 `dev.langchain4j.exception` 下；标"实测外层 `RuntimeException`"的两行由包装抛出，映射按 `cause` 链上的 Jackson 解析异常与 `java.net` 连接异常归类；两行都落进覆盖规则，判定不依赖基类。

口径五条：

1. **映射集中一处**：LC4j 与运行时异常 → 我们的错误码落在 `invoke/ModelErrorClassifier`（由 `invoke/ModelInvoker` 在失败时调用，`MODEL-05`）；适配器把 LC4j 异常原样抛出，不自行转换。**LC4j 类型只出现在 `workbuddy-model` 内部（`engine` / `adapter` / `invoke` / `listener` 四个包），业务侧不出现**。映射只产出"码 + detail"，不带任何调用策略。
2. **可降级判定集中一处、且不落在错误码上**：`ErrorCode` 只是一张码值 + 文案的表，**不带任何属性**，也没有为它加重载构造。判定归 `ModelErrorClassifier.canFallback(Throwable)`：**先看覆盖规则** —— `MODEL_UNREACHABLE` 与 `MODEL_OUTPUT_INVALID` 两个码归可降级（响应不可解析、网络不可达、平台侧结构校验失败都在其中）；未命中再看**异常链**上的 `RetriableException` / `NonRetriableException`（可重试异常归可降级，不可重试异常归不可降级），链上两者都未命中归不可降级。入参取映射后的知识异常或适配器原始异常，两条路径结论一致。**同处的另一条口径是失败谓词 `isVendorUnhealthy(Throwable)`**（`MODEL-11` 供熔断器取用）：只判厂商侧可用性 —— 429 / 5xx / 超时 / 连接失败 / DNS 归不健康，鉴权、参数错、内容拒绝、模型不存在、输出结构校验失败归健康；两条判据互不推导，差异点各有用例（见 7.1）。
3. **LC4j 异常类名、包名与类层次已核实并钉进本表**：包 `dev.langchain4j.exception`；`RateLimitException` / `InternalServerException` / `TimeoutException` 是 `RetriableException` 子类，`AuthenticationException` / `InvalidRequestException`（`ContentFilteredException` 的父类）/ `ModelNotFoundException` / `UnresolvedModelServerException` 是 `NonRetriableException` 子类，`JsonException`（`JsonReadException` 的父类）直接继承 `LangChain4jException`（javap 逐个核对所得）；第 4 列由这两个基类决定，**`maxRetries` 的重试口径据此分类，平台不维护白名单**。**回调方法名与上下文类名（4.8）仍按该版本 Javadoc 核对**。**404（模型不存在）归 `MODEL_NOT_FOUND`（40464）**，与参数错、内容被拒区分开。
4. **`usage` 回填（一条口径两处一致）**：`GenerationResult.usage` 与 `trace.usage()` 由 `listener/ModelUsageMapper` 从同一份 `TokenUsage` 映射，口径逐字相同 —— 厂商未回 usage 时**整体为 null**（不是三项为 null 的空对象）；回了但缺单项时**缺的项留 null**（D19）；不做本地估算、不写 0。`model` 取响应回传值（响应缺失时回填请求模型名），`modelVersion` 该版本响应不带、留 null。
5. **重试与超时的实测记录（本片）**：`maxRetries=0` → 失败只发 **1** 次请求；`maxRetries=2` → **3** 次请求；`timeout` 取 300 毫秒 → 1500 毫秒的慢应答被切断并抛 `dev.langchain4j.exception.TimeoutException`（与本表第 2 列的超时类一致）。同一次逻辑调用里**每次真实请求各计一次尝试**：`attempts` = 真实 HTTP 请求次数（由 HTTP 客户端装饰器在请求前 +1，见 4.8），`retry_count = attempts − 1`；实测 `max-retries=0` 恒 500 → `attempts` = 1 且错误码 `MODEL_SERVER_ERROR`（40467），`max-retries=2` 先两次 500 后成功 → 假服务 3 次请求、`attempts` = 3、`retry_count` = 2。**超时只有实例级入口**：LC4j 1.22.0 的 `ChatRequest` / `ChatRequestParameters` / `ChatRequestOptions` 都没有 per-request 超时入口（逐个核对类成员所得），请求体里的 `timeoutMs` 当前不落到 LC4j。另有一条链上差异：裸 IO 超时（`java.net.http.HttpTimeoutException`）单独出现时映射到 40466，按基类判定归不可降级；实际链路上它先被转成 `dev.langchain4j.exception.TimeoutException`，结论为可降级。
6. **未识别异常的两条结论（`MODEL-11`）**：异常链上未命中已知类型的按 `MODEL_SERVER_ERROR`（40467）计，且**计入熔断失败**（保守口径）；同一条异常在 `canFallback` 上归**不可降级**（覆盖规则与两个基类都未命中）。两条判据不同 —— 熔断看厂商侧可用性、降级看能否换模型重试，`isVendorUnhealthy` 与 `canFallback` 各自给结论、互不推导。

### 6.1 结构校验口径（D39）

| 环节              | 归属                                                                                    | 口径                                                                                                                                                                                                                                                                      |
|-------------------|-----------------------------------------------------------------------------------------|---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| `OutputSpec` 翻译 | `adapter/OpenAiCompatibleAdapter`                                                       | 实测**直传成立**：`TEXT` 不带 `response_format`，`JSON_OBJECT` 带 `json_object`，`JSON_SCHEMA` 带 `json_schema{name, strict, schema}`（`JsonRawSchema` 传完整自定义 schema）；**不建提示词注入分支**；厂商差异不外溢                                                      |
| 调用前检查        | `validate/OutputSchemaValidator.checkBeforeCall`，由 `invoke/ModelInvoker` 在调用前调用 | `JSON_SCHEMA` 的 `schema` 为空白 → 抛 `MODEL_BAD_REQUEST`（40463），**请求不发出**（假服务 0 次请求）；`TEXT` / `JSON_OBJECT` / 约束缺失都放行                                                                                                                            |
| 结构校验          | `validate/OutputSchemaValidator.validate`，由 `invoke/ModelInvoker` **一处**触发        | `TEXT` 不校验（返回 null）；`JSON_OBJECT` 校**是否为合法 JSON 对象**（数组 / 标量 / 空文本按 40469 拒绝）；`JSON_SCHEMA` 用 `com.networknt:json-schema-validator` 做**严格 schema 校验**（"是否满足 schema"）；通过即返回对象树供 `json` 回填；**默认开启**；适配器不复做 |
| 校验失败          | 视为失败                                                                                | **不重试**（平台侧校验，LC4j 不感知），抛「输出结构校验失败」错误码（40469）；按第六节的覆盖规则归可降级，**可作降级到下一个模型的触发条件**，降级链归后续片                                                                                                              |

三类输出：`TEXT` 不做结构校验；`JSON_OBJECT` 校**是否为合法 JSON 对象**（取严：顶层是数组或标量即拒绝，按 40469）；`JSON_SCHEMA` 用 `com.networknt:json-schema-validator` 做**严格 JSON Schema 校验**（依赖版本由根 pom 的属性单点钉定，实测解析为 3.0.8，见 2.1 / 2.2），根为标量时该库的解析器不接受（**对象 / 数组支持**）。`JSON_SCHEMA` 的 `schema` 为空白时在发出请求前失败，抛 `MODEL_BAD_REQUEST`（40463），消息里指出缺 schema；schema 文本自身无法编译同样归 40463。校验失败抛「输出结构校验失败」错误码、**不重试**、可作降级触发条件。

## 八、验收步骤

1. `mvn -o verify` 通过（含 checkstyle / PMD / CPD / SpotBugs）。
2. `node tools/check-comments.mjs` 与 `node tools/check-encoding.mjs` 通过。
3. **错误码面核验**：`../../workbuddy-model/.../gateway/` 下只剩 `ModelGatewayPort`，没有自造异常类；十个模型调用码值在 `ErrorCode` 内，只有码值与文案，单测逐个断言通过。

5. 在部署环境变量里配真 `DASHSCOPE_API_KEY`，跑 smoke 用例，贴出真实 `content` 与 `usage`。
6. 把 `api-key` 配成一个无效值启一次，确认启动失败且消息里指出是 `dashscope`。
7. 调未覆盖模态的默认实现，确认得到「模型未支持该模态」错误码（40460；端口 / SPI 默认方法，`MODEL-12` 后 `DashScopeModelProvider` 已覆盖 `vision` 真实通路）。
8. 架构约束核验：`workbuddy-model` 之外的模块 grep 不到 `dev.langchain4j` 引用（或由架构测试断言）。
9. 依赖面核验：`mvn -o dependency:tree` 里没有 `langchain4j-community-*`，只有 `langchain4j-open-ai`、`langchain4j-core` 与 `com.networknt:json-schema-validator`（版本与根 `pom.xml` 的属性一致）。
10. 适配器面核验：`adapter` 包里只有一个实现类，`ModelAdapter` 上 grep 不到 `vendorCode` / `protocol` 方法，也没有 `AdapterRegistry`。
11. `embed` 厂商解析核验（目录解析）：往 `kb_model` 补一行（`dashscope` + `text-embedding-v4`，启用）后调一次 `embed`，确认按目录命中该厂商；配**两个**厂商时**启动不再失败**（厂商数量不设上限）；目录未收录的模型名在厂商数 ≠ 1 时报 `MODEL_VENDOR_UNKNOWN`（40461），配置里只有一个厂商时兜底用该厂商；同名多命中报 `MODEL_NOT_FOUND`（40464）。
12. **`kb_model` 的库上验证（待核）**：仓库无 DB 测试基建，本项登记为待核 —— 人工在 MySQL 上执行一次 `init.sql`（只建表、无种子行），核对目录查询可跑通且走 `idx_status_capabilities`。
