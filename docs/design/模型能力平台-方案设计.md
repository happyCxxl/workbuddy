# 模型能力平台 · 要做什么、怎么做、技术方案

**一句话**：把「多厂商模型接入」收敛成 `workbuddy-model` 的**唯一出口**，让每次模型调用的用量与成本可见（厂商没回 usage 就记 `NULL` + 未知标记），并按**容量占用 / 健康 / 延迟**三信号全自动切换模型；配套一个**模型管理页面**维护厂商接入、密钥、价格与限额。

**本文只做设计与取舍，不含实现改动。** 讨论定稿后按第九节批次实施。

**阅读顺序**：一（要做什么）→ 二（现状核对）→ 三（目标架构）→ 四（数据模型）→ 五（用量与成本口径）→ 六（路由与流量切换）→ 七（治理与限流）→ 八（管理页面）→ 九（落地路径与验收）→ 十（风险）→ 十一（待决策）→ 十二（变更记录）。

## 一、要做什么

### 1.1 目标（G 编号供讨论逐条确认）

| #  | 目标                   | 达成标志                                                                                                                                                                  |
|----|------------------------|---------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| G1 | 多厂商、多模型统一接入 | 新增一个厂商只改配置与目录数据，Java 侧只加一个适配器；业务模块不出现任何厂商 SDK 类型                                                                                    |
| G2 | 出口唯一               | 全仓库只有 `ModelGatewayPort` 一条出网调用路径（含解析环节的表格结构 / 版面 / OCR）                                                                                       |
| G3 | 每次调用成本可见       | 每次模型调用在 `wb_model_call_log` 落一行，带 tokens、单价快照、成本、延迟、路由原因；厂商未回 usage 时 tokens 与成本记 **NULL + `usage_unknown` 标记**（见 D19）         |
| G4 | 按流量自动切换模型     | 依据**容量占用 / 健康 / 延迟**三个信号**全自动**选型（打分制、容量优先、带熔断与 slow start），每次调用可解释（`route_reason`）；参数在配置文件，不做人工优先级/灰度/回滚 |
| G5 | 模型管理页面           | 模型（能力 / 价格 / 限额 / 状态）可在页面维护，含连通性测试与用量成本概览；**厂商连接与密钥在配置里，页面不涉及**（D29）                                                  |

### 1.2 明确不做（非目标）

| 不做                             | 说明                                                                                              |
|----------------------------------|---------------------------------------------------------------------------------------------------|
| 不在本仓库部署模型权重与推理服务 | 推理服务在仓库外，本方案只做接入、治理与计量                                                      |
| 不做提示词工程平台与 RAG 平台    | 只留接入点，方案内不设计                                                                          |
| 不做对外计费结算                 | 只做内部成本可见与告警，不做发票、对账、退款                                                      |
| **不做配额层**                   | 不做租户/团队限流、不做预扣与拦截（已定 D15）；用量只用于**可见与告警**                           |
| **不做日聚合表**                 | 看板与告警直接查明细表（已定 D16），等明细量级上来再评估                                          |
| 不引入独立 AI 网关               | 保留「以后可把厂商级限流与统计下沉到网关」的边界，当前消费方都在本仓库内                          |
| 不做本地 token 估算              | 已确认不引入分词器库；无 usage 即记 **NULL + `usage_unknown = 1`**（口径见第五节）                |
| 不做平台级复杂计量               | 用量分类字典、价格表版本与对账、幂等去重、分档定价、缓存读写拆分、分区与保留期作业一律不做（D20） |
| **不做人工优先级 / 权重**        | 分流全自动，由打分算法决定（D23）；`wb_model` 不带 `priority` / `weight` 字段                     |
| **不做灰度 / 回滚 / 策略表**     | 无多策略、无影子模式、无版本化回滚，路由参数放 `config/workbuddy-model.yml`（D23 / D24）          |

## 三、目标架构

### 3.1 分层

```
消费方：EmbedPipeline（已合规） / SearchServiceImpl（已合规） / 解析侧三能力（P0 并入）
        │  只依赖 Port
        ▼
knowledge-model
  ├─ ModelCatalogPort    能力 × 厂商 × 模型 × 价格 × 限额 × 启停（DB + 缓存 + 变更刷新）
  ├─ ModelGatewayPort    唯一出口（按模态分方法）：chat / embed / vision
  ├─ ModelRouter         硬闸门 → 三信号打分（β 容量 1.0 / 延迟 0.5，平局 P2C）→ 降级链
  │                      └─ RouteStateStore（进程内：在途计数 / 延迟 EWMA / RPM 与 TPM 窗口；多副本再换 Redis）
  │                      └─ ModelCircuitBreakers（进程内 Resilience4j 注册表：健康判定、打开保持、slow start）
  ├─ 治理装饰器链        凭据 → 并发排队（可选）→ 缓存 → 超时与 LC4j 重试 → 熔断 → 路由 → 适配器调用 → 计量 → 指标
  └─ 计量落点            wb_model_call_log（含 route_reason / fallback_from / 未知用量标记）
        │
        ▼
  适配器（OpenAI 兼容协议一个实现，多厂商共用；接第二种协议时再按协议分化，不按能力）
        │
        ▼
厂商 API 与仓库外的推理服务（仓库外部署）
```

### 3.2 组件职责

| 组件                    | 职责                                                                                                                                                                                                                                                                                                                                        | 不做什么                                                   |
|-------------------------|---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|------------------------------------------------------------|
| `ModelCatalogPort`      | 提供可用模型清单、能力匹配、价格、限额、启停状态；变更后可刷新                                                                                                                                                                                                                                                                              | 不发起调用                                                 |
| `ModelRouter`           | 按**三信号打分**（容量占用 / 健康 / 延迟）选出本次调用用哪个**模型**，健康状态取自熔断器（见 §7.3）、恢复爬升段按比例放行，写 `route_reason`                                                                                                                                                                                                | 不直接调用厂商；不做人工优先级与灰度                       |
| `ModelGatewayPort`      | 对外唯一入口，按**模态**分方法（`chat` / `embed` / `vision`），统一 `usage` / 错误码                                                                                                                                                                                                                                                        | 不感知业务语义；不做选型与记账                             |
| `ModelInvoker`          | 一次真实调用：按**模态**分派请求构造与响应解析，回填 `usage` 与模型版本；**错误分类**（异常 → 错误码落在 `invoke/ModelErrorClassifier` 一处，`canFallback(Throwable)` **覆盖规则优先**、其次按异常链上的 `RetriableException` / `NonRetriableException`，**决定是否可降级**）与**结构校验**（一处实现，D39）；同一实例内的重试与退避归 LC4j | 不选模型、不做跨模型降级与记账                             |
| `ModelInstanceRegistry` | 按**厂商 + 模型名**缓存 LC4j 实例（懒构建、命中复用）；实例构建参数取 vendors 配置                                                                                                                                                                                                                                                          | 不发请求、不落明细                                         |
| 适配器                  | OpenAI 兼容协议**一个实现、多厂商共用**（把 `vendorCode` 与模型名交给 `ModelInstanceRegistry` 取 LC4j 实例）：统一请求翻译成厂商调用（LangChain4j）；**LC4j 异常原样抛出，映射成错误码归 `ModelErrorClassifier`**                                                                                                                           | 不按能力拆类；**本片不建适配器注册表**（唯一实现直接注入） |
| 治理装饰器              | 并发/排队（可选）、缓存、超时与 LC4j 重试、熔断（**健康判定由 Resilience4j 熔断器承担**：`resilience4j-circuitbreaker` **2.1.0**，**只引核心模块、不引 spring-boot3 starter**）、计量                                                                                                                                                       | 不做模型选型、不做配额拦截                                 |
| 计量                    | 落 `wb_model_call_log` 明细（同记 `capability` 与 `model`），按时间范围查询（不做日聚合表）                                                                                                                                                                                                                                                 | 不做实时拦截（本方案无配额层）                             |

**能力与模型两轴口径见 4.2（D26）**。

### 3.3 依赖方向（D1：**暂缓，先按单副本进程内状态落地**）

| 选项                   | 做法                                                                                                                                                       | 优点                                                                                                    | 代价                                               |
|------------------------|------------------------------------------------------------------------------------------------------------------------------------------------------------|---------------------------------------------------------------------------------------------------------|----------------------------------------------------|
| **当前默认（本轮定）** | 路由状态（在途计数 / 延迟 EWMA / RPM 与 TPM 窗口）与熔断状态（`ModelCircuitBreakers` 的进程内注册表）放**进程内**，治理链与适配器都在 `workbuddy-model` 内 | 依赖方向不动、不引 Redis、单副本语义最简单（`workbuddy-model` 保持只依赖 `common` + `starter` + `web`） | 多副本部署时各副本状态不共享（各自熔断、各自计数） |
| A（多副本时可选）      | `workbuddy-model` 依赖 `workbuddy-infra`，直接用 Redis 与令牌桶                                                                                            | 落地快，治理链与适配器同模块                                                                            | model 变重，infra 与 model 边界模糊                |
| B（多副本时可选）      | 治理装饰器放 `workbuddy-infra`（或独立模块），依赖 `workbuddy-model` 的 Port 接口；`RouteStateStore` 换 Redis 实现                                         | 依赖方向干净（infra → model 接口），业务只依赖 model                                                    | 多一次装配，需定义治理所需的最小接口               |

口径：**单副本部署下不做 A/B 的取舍**；`RouteStateStore` 只暴露「记在途 / 记一次调用结果 / 取占用与延迟读数」最小方法，将来换 Redis 实现不需要动 `ModelRouter` 与业务。

### 3.4 与解析环节的衔接

| 解析能力     | 统一出口方法  | 请求契约（现有）                      | 响应契约（现有）                                                     |
|--------------|---------------|---------------------------------------|----------------------------------------------------------------------|
| 表格结构识别 | `vision(...)` | `TableRegion`（页码 + bbox + 文本）   | `TableResult`（行列 + 每格 row/col span + bbox + 置信度 + 模型版本） |
| 版面分析     | `vision(...)` | `PageImage`（页码 + 尺寸 + DPI）      | `LayoutResult`（区域分类 + 阅读顺序 + 模型版本）                     |
| 结构化 OCR   | `vision(...)` | `OcrRegion`（页码 + bbox + imageRef） | `StructuredOcrResult`（逐行文本 + bbox + 置信度 + 模型版本）         |

口径不变的三件事：**只在规则路径判不出结果时才调用能力**、**几何 / 规则口径始终是默认**、**调不通即回落并留痕**。

**领域结构留在解析侧**：`TableResult` / `LayoutResult` / `StructuredOcrResult` 这类强结构化类型是业务语言，**不进入平台契约**；解析侧通过 `VisionRequest` 携带"图像/区域 + 提示词 + 输出约束（`OutputSpec`）"，拿到原始文本或 JSON 后**由解析侧自己映射**成这些领域类型。平台不定义字段名、不解释语义。

**契约去重（P0 要一并处理）**：common 的 `domain/parse/capability` 包里有 12 个类型，其中 `OcrRequest` 是**空壳**（注释写着它应是 `ModelGatewayPort.structuredOcr` 的入参，该端口方法目前并不存在），`ProviderContext` 同为占位；实际在用且字段完整的是上表三组。

**契约的家与端口入参口径（已定 D27：口径 C）**：三组解析领域契约**不搬**，留在 `common/domain/parse/capability`；平台只新增 `chat` / `vision` 的通用契约与 `OutputSpec`；`domain/embed` 保持不动。

| 项                  | 处置                                                                                                                                                                                                                                    |
|---------------------|-----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| 留在原处            | 三组解析领域契约整体留在 `domain/parse/capability`：`TableRegion` / `TableResult`、`PageImage` / `LayoutResult`、`OcrRegion` / `StructuredOcrResult`，以及 `TableCell`、`LayoutRegion`、`OcrLine`、`ProviderContext`、`CapabilityUsage` |
| 平台新增            | `chat` / `vision` 的通用契约与 `OutputSpec`（见 4.3），全部是模态语言，不含任何字段名或业务语义                                                                                                                                         |
| `domain/embed` 契约 | 保持不动（`EmbeddingRequest` / `EmbeddingResult` 原样），`EmbedPipeline` / `SearchServiceImpl` 与两个测试不受影响                                                                                                                       |
| 未决                | `OcrRequest` 空壳**本轮不动**，处置延后到实现阶段（D28）；P0 验收里登记为已知未决项，避免被当成端口入参                                                                                                                                 |

**净改动面**：解析侧只新增映射代码（`VisionRequest` → 厂商请求、原始返回 → 领域类型），平台不引业务类型；契约文件不移动，无 import 变化，**不动任何运行逻辑**。

**能力访问层不在解析侧**：worker 只负责"何时调（三条信号路由）、结果怎么用（装配与回退）、开关（`ocr-enabled` / `layout-enabled` / `table-enabled` 保留在解析侧）"；`knowledge.parse.capability.sidecar-base-url` 配置键已删除，地址取 `knowledge.model.vendors.<code>.base-url`（D33）。

## 四、数据模型

表名沿用 `wb_` 前缀；字段类型按 MySQL 8 约定（时间 `datetime`，金额 `decimal(18,6)`，token `bigint`）。

**定稿口径（D11 / D12 / D13）**：每厂商一把密钥、不按租户区分密钥、不引入代理与多环境不同地址 → **只需一张 `wb_model` 表**（厂商连接与密钥在配置里，见 4.1 / D29）；页面上**只有一个入口**（厂商**只能从配置里已有的清单中选**，页面不能新建），厂商接入不单独占菜单。

### 4.1 厂商连接（`config/workbuddy-model.yml` 配置项，**不建表**）

**口径（D29）**：密钥与 `base_url` **写在配置里**，库与页面都不涉及密钥 —— 于是"厂商"不再是库里的实体，只剩配置里的一个键；**没有厂商级限额**（D30），容量判断只看模型行上的限额。

```yaml
knowledge:
  model:
    vendors:
      dashscope:
        base-url: ""                      # 留空 = 用适配器内置的官方地址
        auth-type: BEARER                 # 当前只有 BEARER 一个取值
        api-key: ${DASHSCOPE_API_KEY:}    # 带空默认的占位；真实值走环境变量；密钥永不进库、永不回显
        timeout-ms: 60000                 # 单一总超时（毫秒）；留空取默认 60000
        max-retries:                      # 留空 = 用 LC4j 默认
      self-ocr:
        base-url: http://10.0.0.12:8080
        auth-type: BEARER
        api-key: ${SELF_OCR_TOKEN:}
```

| 项                  | 口径                                                                                                                                                                                                                                                                                                         |
|---------------------|--------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| 厂商标识            | 配置里的键（如 `dashscope`）就是 `wb_model.vendor_code` 的取值；**保存模型时校验"该键必须存在于配置"**，配错立即报错而不是运行期才炸                                                                                                                                                                         |
| `auth-type` 取值    | **只有 `BEARER`**（枚举先收窄，D37）；需要签名鉴权的厂商在接入时再加取值                                                                                                                                                                                                                                     |
| `timeout-ms`        | 单一总超时（毫秒）；**留空取默认 60000**，映射 LC4j 的 `timeout`，**不区分连接超时与读取超时**；将来若必须区分，改用自定义 HTTP 客户端，**配置名不再变**（D38 修订 / D41）                                                                                                                                   |
| `max-retries`       | 同一实例内的重试次数；**可留空 = 用 LC4j 默认**，映射 LC4j 的 `maxRetries`（D41）                                                                                                                                                                                                                            |
| 启动期校验（D35）   | **只校验配置里列出的厂商**，没列出的不校验；`api-key` 解析不出来（空 / 未设置）→ **启动失败**，错误信息里带**厂商码**；`auth-type` 必须落在该厂商适配器 `supportedAuthTypes()` 的支持集内，不支持即失败；占位符写法 `api-key: ${ENV_VAR:}`（带空默认），由校验器给出可读错误，不由 Spring 报"占位符无法解析" |
| 仓库默认配置（D35） | 默认 `config/workbuddy-model.yml` **不放**带密钥占位的示例厂商（示例只写在文档与部署配置里），本地与 CI 无密钥也能启动                                                                                                                                                                                       |
| 密钥轮换 / 改地址   | 改环境变量或配置 → 重启生效（不能热改，已如实计入代价）                                                                                                                                                                                                                                                      |
| 配置变更留痕        | 走 git 历史与代码评审；密钥的真实值只在部署环境的变量里                                                                                                                                                                                                                                                      |

**厂商码与目录的关系**：`wb_model.vendor_code` 的取值必须出现在 `knowledge.model.vendors` 里（保存模型时校验，配错立即报错，不是运行期才发现）；`embed` 的厂商归属由目录按「模型 → 厂商」解析（见 4.2 / 4.10 与 v21 行），配置里出现多个厂商不再构成启动期的阻塞。

### 4.2 `wb_model`（模型）

| 字段                                         | 类型                                | 说明                                                                            |
|----------------------------------------------|-------------------------------------|---------------------------------------------------------------------------------|
| `id` / `vendor_code` / `model_key`           | bigint / varchar(64) / varchar(128) | `model_key` 为厂商侧模型名                                                      |
| `display_name`                               | varchar(128)                        | 页面展示名                                                                      |
| `capabilities`                               | varchar(255)                        | 多值，逗号分隔，取值见 4.6                                                      |
| `context_window`                             | int                                 | 上下文窗口（可空）                                                              |
| `price_in_per_m` / `price_out_per_m`         | decimal(18,6)                       | 每百万 token 单价（可空）；对应能力 `CHAT`                                      |
| `price_image_per_page`                       | decimal(18,6)                       | 图像按页单价（可空）；对应能力 `OCR` / `LAYOUT` / `TABLE_STRUCTURE`             |
| `price_per_thousand_calls`                   | decimal(18,6)                       | 嵌入按千次单价（可空）；对应能力 `EMBEDDING`                                    |
| `currency`                                   | varchar(8)                          | `CNY` / `USD`                                                                   |
| `rpm_limit` / `tpm_limit`                    | int                                 | **唯一的限额来源**（无厂商级限额，D30）；两者都留空则该模型不参与"容量占用"判断 |
| `status` / `effective_from` / `effective_to` | varchar(16) / datetime / datetime   | 启停与生效区间                                                                  |

唯一键：`(vendor_code, model_key)`；索引：`status, capabilities`。

**没有 `priority` / `weight` 字段**（已定 D23）：分流全自动，由打分算法按容量占用与延迟决定，不做人工优先级或权重。

**`capabilities` 是多值（D26）**：一个模型可以声明多个能力（例如一个多模态模型同时提供 `OCR,TABLE_STRUCTURE,LAYOUT`）。于是"一个模型出现在多个能力的候选集里"是正常形态；由此三条口径必须遵守：① 候选集**按能力**筛；② 熔断状态 / 在途计数 / 延迟 EWMA / RPM·TPM 占用**按模型**算（多能力共享同一份，避免"在 OCR 上已熔断、表格能力还在打它"，也避免限额被按能力重复计数）；③ 适配器**按厂商/协议**分，不按能力拆类。明细里同时记 `capability`，用于按能力看成本；状态与限额仍按模型算。

**向量规格不进本表（口径，v21）**：`wb_model` 不含 `dimension` / `metric` / `normalized` / `batch_limit` 四类列；向量元数据由 `workbuddy-common` 的 `EmbeddingModel` 枚举承载，biz 侧的库表实现 `DbModelCatalog` 按模型名把枚举里的规格叠加到 `ModelDescriptor.embedSpecs` 上。**已知限制**：库里声明 `EMBEDDING` 而枚举里没有的模型名，其 `embedSpecs` 为空，在向量编码链路上不可用。**承载方式记为待定**：接入清单确定后再定「规格进表还是继续进枚举」。

**厂商码必须在配置里**：`vendor_code` 的取值必须出现在 `knowledge.model.vendors` 里（见 4.1）；表中出现配置里没有的厂商码时，嵌入调用在解析厂商处明确失败（`MODEL_VENDOR_UNKNOWN`，40461）。

**初始为空的行为（口径，v21）**：`wb_model` 初始为空（脚本只建表、不带种子行）。此时：① 嵌入调用在解析厂商处报「模型厂商未配置」（`MODEL_VENDOR_UNKNOWN`，40461）—— 目录未收录该模型且配置里的厂商数 ≠ 1；② 嵌入策略保存校验按目录判「模型不存在」而拒绝；③ `EmbedPipeline` 的前置校验按 `EmbeddingModel` 枚举判「模型不存在或未启用」而拒绝。接入某个模型前先往 `wb_model` 补一行（页面或手工 SQL）。

**SQL 验证边界（待核，v21）**：仓库没有 DB 测试基建，`wb_model` 的 DDL 与目录查询**未在真实 MySQL 上执行验证**；`DbModelCatalog` 的单测为 Mockito 打桩 + `getSqlSegment()` 片段断言（断言条件里出现 `status` / `effective_from` / `effective_to` / `ORDER BY` 等片段），不覆盖真实 SQL 语法与索引命中。登记为待核项：人工在库上执行一次 `init.sql` 并核对查询，**不引入 H2 等新依赖**。

### 4.3 平台侧通用契约（`common/domain/model`，**模态语言**）

平台契约只有模态语言，与业务结构无关；三组解析领域契约留在 `domain/parse/capability`（D27），`domain/embed` 契约保持不动。

**契约与端口自有**：契约与端口都是我们自己的，**业务侧不出现 LC4j 类型**；LC4j 类型只在 `workbuddy-model` 内部使用（`engine` / `adapter` / `invoke` / `listener` 四个包，按 OpenAI 兼容协议接入 DashScope 等厂商）。

| 契约               | 字段                                                                                                     | 说明                                                                                                        |
|--------------------|----------------------------------------------------------------------------------------------------------|-------------------------------------------------------------------------------------------------------------|
| `ChatRequest`      | 模型名 + 消息列表 + `OutputSpec` + 超时                                                                  | 对话模态入参；**超时只有实例级入口**（`vendors.<code>.timeout-ms`，见 4.1），契约里的超时字段当前不落到框架 |
| `VisionRequest`    | 模型名 + 图像/区域引用 + 提示词 + `OutputSpec` + 超时                                                    | 视觉模态入参（表格结构 / 版面 / OCR 三项都走这一个）；超时口径与 `ChatRequest` 一致                         |
| `OutputSpec`       | `format` = `TEXT` / `JSON_OBJECT` / `JSON_SCHEMA`；`schema` 为 JSON Schema 文本，仅 `JSON_SCHEMA` 时必填 | 输出约束；**schema 由业务侧写**，平台不定义字段名                                                           |
| `GenerationResult` | `content`（原始文本）、`json`（解析后的通用树，可空）、`usage`、`model`、`modelVersion`                  | `chat` 与 `vision` 共用出参                                                                                 |

**翻译归适配器（D39）**：把 `OutputSpec` 翻成厂商参数 —— 能直传 `json_schema` 就直传，不能就注入提示词附 schema；**厂商差异只落在适配器**。

**结构校验归平台一处（D39）**：校验落在 `validate/OutputSchemaValidator`，由 `ModelInvoker` 统一触发、默认开启 —— 发出请求前 `checkBeforeCall(OutputSpec)` 拒绝缺 schema 的 `JSON_SCHEMA`（错误码 40463，请求不发出），返回后 `validate(OutputSpec, content)` 校验并回填 `GenerationResult.json`；校验不通过按失败处理（**不重试**，可作为降级到下一个模型的触发条件）。三类输出的校验口径：

| `OutputSpec.format` | 校验口径                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
|---------------------|----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| `TEXT`              | **不校验**                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| `JSON_OBJECT`       | 校**是否为合法 JSON 对象**（取严：顶层是数组或标量按 40469 拒绝）                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| `JSON_SCHEMA`       | 用 `com.networknt:json-schema-validator` 做**严格 JSON Schema 校验**（"是否满足 schema"）；依赖版本由根 `pom.xml` 的属性单点钉定，**不写死**，实测解析 **3.0.8**；其传递的 `tools.jackson.*` 3.2.1 类初始化要读 `com.fasterxml.jackson.annotation.JsonSerializeAs`，注解停在 Boot 管理的 2.15.4 时抛 `NoClassDefFoundError`，已按方案 A 把注解单点钉到 **2.22**（`jackson-databind` / `jackson-core` 保持 2.15.4），实测影响面与回退方式见 `实现-01-适配器骨架与真实调用.md` 的 2.2；根为标量时该库解析器不接受（**对象 / 数组支持**） |

校验失败一律抛「输出结构校验失败」**错误码**（`ErrorCode` 内，只有码值与文案 —— **不带任何属性**），**不重试**，可作降级到下一个模型的触发条件；「是否可降级」由调用器的 `canFallback(Throwable)` 给出，覆盖规则（`MODEL_UNREACHABLE` / `MODEL_OUTPUT_INVALID`）优先、其次按异常链上的两个基类判定（见 §3.2 / §7.3）。

平台**不定义字段名、不解释语义**。

**目录视图契约（v21）**：`ModelDescriptor`（厂商归属 + 能力 + 价格 + 限额 + 状态 + 生效区间 + 向量规格段 `embedSpecs`）与 `ModelCapability`（`CHAT` / `EMBEDDING` / `OCR` / `LAYOUT` / `TABLE_STRUCTURE`）落 `common/domain/model/catalog`；库表实体 `WbModel` 与其余实体同在 `common/domain/entity`，Mapper 与库表实现 `DbModelCatalog` 留在 `workbuddy-biz`。端口 `ModelCatalogPort` 在 `workbuddy-model`，三个查询入口：按能力列候选、按厂商码 + 模型名精确取、按模型名取唯一启用模型。

### 4.4 路由参数（`config/workbuddy-model.yml` 配置项，**不建表**）

**不建 `wb_model_route_policy` 表**（已定 D23/D24）：只有一套全自动算法，没有多策略、没有灰度、没有版本回滚，因此路由参数放配置：

| 配置项（`knowledge.model.route.*`）            | 默认       | 含义                                                                                                                                     |
|------------------------------------------------|------------|------------------------------------------------------------------------------------------------------------------------------------------|
| `beta-capacity`                                | 1.0        | 容量占用权重（已定 D21：容量优先）                                                                                                       |
| `beta-latency`                                 | 0.5        | 延迟权重（0 = 只看容量）                                                                                                                 |
| `latency-window-seconds`                       | 300        | 延迟 EWMA 的滑动窗口                                                                                                                     |
| `capacity-trigger-ratio`                       | 0.8        | 占用率超过该值（0.8 = 80%）即视为"接近上限"，参与扣分                                                                                    |
| `error-trigger-ratio` / `error-window-seconds` | 0.05 / 60  | 失败率阈值（0.05 → 5%）与熔断时间窗（60s）：映射 `failureRateThreshold` 与 `slidingWindowSize`（D7 的阈值口径已由 v23 收口到熔断器参数） |
| `cooldown-seconds`                             | 60         | 熔断打开后的保持时长：映射 `waitDurationInOpenState`（可参考厂商 `Retry-After`）                                                         |
| `slow-start-seconds`                           | 45         | OPEN → HALF_OPEN 之后的放行比例爬升时长（已定 D22）                                                                                      |
| `max-retry`                                    | **已作废** | 重试归 LC4j（实例级），**做不到按能力分**（D38 修订 / D41）                                                                              |

**配置表里列出的键都必须有消费方**：没有读写入口的键不进本表，也不留在配置类里。`threshold-window-seconds`（阈值窗口 30s）与 `min-dwell-seconds`（最小驻留 120s）两行随 v23 删除 —— 防抖由熔断器的时间窗（`error-window-seconds`）与打开保持（`cooldown-seconds`）承担，切换最小驻留没有消费方（D31 的数值口径同步收窄）。

**重试口径**：同一模型实例内的重试与退避**归 LC4j**（`vendors.<code>.max-retries` → `maxRetries`）；平台保留**换模型降级**（LC4j 不做换模）、**熔断**、`Retry-After` 解析与**观测**；`route.max-retry` 与自研退避**作废**（见 D38 修订 / D41）。

### 4.5 `wb_model_call_log`（调用明细，一次模型调用一行）

**口径（已定 D19 / D20）**：只记录**调用费用与基本用量**，够用即止 —— 不搞用量分类字典、不做成本对账流程、不做幂等去重窗口、不做分区分档定价；缺 usage 一律 **NULL + `usage_unknown = 1`**（不写 `-1`、不写 0、不做本地估算）。

**未知用量的判定（口径，v22）**：两种情形都按未知记 —— ① 厂商**未回 usage**；② 厂商**回了 usage 但三项计数全空**。两者都写 `usage_unknown = 1`，三项 token 与 `cost` 记 NULL。厂商明确回了 0 的才是**确实为零**，按 0 写（D19，未知与零不混用）。

表格结构 / 版面 / OCR 若接的是外部服务，其 token 与 `cost` 在计费单位确定前**一律记 NULL + `usage_unknown = 1`**（D34）。

| 字段                                                                          | 类型                                             | 说明                                                                                                                                                                                                                       |
|-------------------------------------------------------------------------------|--------------------------------------------------|----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| `id` / `trace_id`                                                             | bigint / varchar(64)                             | `trace_id` 关联业务链路                                                                                                                                                                                                    |
| `tenant_id` / `biz_type` / `biz_id`                                           | bigint / varchar(32) / varchar(64)               | 业务归属（解析任务 / 问答会话…）                                                                                                                                                                                           |
| `capability` / `vendor` / `model` / `model_version`                           | varchar                                          | 能力与**实际**使用的模型（别名漂移以响应回传为准）                                                                                                                                                                         |
| `prompt_tokens` / `completion_tokens` / `total_tokens`                        | bigint（**可空**）                               | 厂商未回 usage 或三项计数全空时为 **NULL**，并置 `usage_unknown = 1`；确实为零写 0                                                                                                                                         |
| `usage_unknown`                                                               | tinyint                                          | 1 = 本次用量未知（查询与看板据此算"未知占比"）                                                                                                                                                                             |
| `unit_price_in` / `unit_price_out` / `currency`                               | decimal(18,6) / decimal(18,6) / varchar(8)       | 计价时用的单价（**每百万 token 单价**，留档即可，一行成本可复算）                                                                                                                                                          |
| `cost`                                                                        | decimal(18,6)（**可空**）                        | **调用费用**；用量未知或单价缺失时为 NULL；**只对 `CHAT` 落金额**，`EMBEDDING` 的 token 照记而本列留空                                                                                                                     |
| `latency_ms` / `retry_count` / `fallback_from` / `route_reason` / `cache_hit` | int / int / varchar(128) / varchar(32) / tinyint | 延迟（**一次逻辑调用的整段耗时**，含 LC4j 内部重试与退避等待）、重试（**由 HTTP 客户端 SPI 在真实 HTTP 层计数**，每次真实请求 +1，`retry_count` = 尝试次数 − 1；监听器不参与计数）、从哪个模型降级、路由原因、是否命中缓存 |
| `status` / `error_code`                                                       | varchar(16) / varchar(64)                        | `SUCCESS` / `FAILED` / `TIMEOUT` / `RATE_LIMITED` / `CIRCUIT_OPEN`                                                                                                                                                         |
| `create_time`                                                                 | datetime(3)                                      | 调用时间 = 明细写入时刻，紧随调用结束（公共字段口径，与其余表一致）                                                                                                                                                        |

索引：`(tenant_id, create_time)`、`(capability, model, create_time)`、`trace_id`，另有 `del_flag` 单列索引（与 `wb_model` 一致）。

**公共字段五件套（口径，v22）**：本表保留公共五件套 —— 逻辑删除标记 `del_flag` 与审计四件（`create_by` / `create_time` / `update_by` / `update_time`），与 `wb_model` 同类；**不采用** `wb_knowledge_pipeline_task` 那类 append-only 机器表的极简风格（那种表只留 `create_time`）。读查询自带 `del_flag = '0'`（逻辑删除由 MyBatis-Plus 的 `@TableLogic` 在 SQL 层补上），明细查询与概览聚合都不用手写该条件。

**实体落点（v22）**：库表实体 `WbModelCallLog` 统一放 `../../workbuddy-common/domain/entity`（与 `WbModel` 及其余实体同处），Mapper `WbModelCallLogMapper` 与库表实现 `DbModelCallLogService` 留 `workbuddy-biz`；端口 `ModelCallLogPort` 与明细组装 `ModelCallLogRecorder` 在 `workbuddy-model`，入参 / 出参类型（`ModelCallLogEntry` / `ModelCallLogQuery` / `ModelCallLogView` / `ModelCallLogSummary`）落 `common/domain/model/calllog`。**MyBatis 实体不进 `workbuddy-model` 签名**（与 §4.3 的 v21 契约同口径）。

**成本口径（v22）**：本片**只对 `CHAT` 计算 token 费用** —— `cost = prompt_tokens × unit_price_in / 1e6 + completion_tokens × unit_price_out / 1e6`，其中 `unit_price_in` / `unit_price_out` 是**每百万 token 单价**（取 `wb_model` 的 `price_in_per_m` / `price_out_per_m`）。三档留空：① `EMBEDDING` 的 token **照记**而 `cost` **留空**（本表没有「按千次」单价列，落一个折算不出的金额会让一行成本无法复算）；② `OCR` / `LAYOUT` / `TABLE_STRUCTURE` 按 D34 强制 NULL + `usage_unknown = 1`；③ 目录里没有该模型或价格缺失时 `cost` 留空（不做本地估算）。单价随行留档（`unit_price_in` / `unit_price_out` / `currency`），调价不追溯历史行。**嵌入与图像成本要进明细，需要补列或改公式，已登记为待定**（见待办清单第六节）。

**落库边界（v22）**：**形参校验**（厂商码空 / 入参空 / 模型名空）与**调用前结构检查**（`JSON_SCHEMA` 缺 schema）拦下的失败**不落行** —— 那一次请求没有发出。**调用已发起而被注册表 / 适配器即拒的失败仍落一行**（未知厂商、未知模型、鉴权失败、限流、超时、输出结构校验失败等都算），此时 `retry_count` 可能为 0（真实请求数为 0）、`latency_ms` 为 NULL。成功调用同样落一行，模型与版本取响应回传值（缺失回落到请求里的模型名）。

**本片留空字段（v22）**：`trace_id` / `tenant_id` / `biz_type` / `biz_id` / `route_reason` / `fallback_from` 当前写 NULL，`cache_hit` 恒 0；字段与字典（`RouteReason` / `CallStatus`）已经建好，等编排片与路由片接入后由同一份上下文补齐。

**能力字典差异（待定，v22）**：§4.6 的字典含 `RERANK` / `IMAGE`，`common` 的 `ModelCapability` 只有 `CHAT` / `EMBEDDING` / `OCR` / `LAYOUT` / `TABLE_STRUCTURE` 五项 —— 两个取值当前没有落地点，遇到再议（登记见待办清单第六节）。

> **不做日聚合表（已定 D16）**：看板、成本趋势与告警**直接查本表**（限定时间范围 + 走上面的索引）。
> **不做**（调研建议但按业务需要不采纳，逐条见第十一节「调研结论采纳情况」）：用量分类字典、价格表版本与生效时间、成本对账流程、幂等键与去重窗口、分档定价、缓存读写分别计价、推理/音频单列计价、明细分区与保留期作业。等真实量级或计费诉求出现再评估。
> **一条保留的细节**：流式一律以**结束回执**为准（禁止逐块累加 token）。

## 五、用量与成本口径

### 5.1 数据源

| 优先级        | 来源                 | 说明                                                                              |
|---------------|----------------------|-----------------------------------------------------------------------------------|
| 1（唯一权威） | **厂商响应的 usage** | 随调用返回，`inputTokenCount` / `outputTokenCount`（LangChain4j 的 `TokenUsage`） |
| —             | 网关统计             | 不引网关（已定 D13）                                                              |
| —             | 本地估算             | **明确不做**（不引入分词器库；调研显示业界多有估算，我们按业务需要放弃）          |

### 5.2 缺 usage 的处理（已定 D19）

- `prompt_tokens` / `completion_tokens` / `total_tokens` 与 `cost` 全部记 **NULL**，同时置 `usage_unknown = 1`；
- **未知的判定面（v22）**：除"厂商未回 usage"外，"**回了 usage 但三项计数全空**"同样按未知记 —— 三项 token 与 `cost` 都写 NULL 并置 `usage_unknown = 1`；厂商明确回了 0 的按**确实为零**写 0，两者不混用；
- `NULL` 让 `SUM` / `AVG` 天然跳过未知行，不需要在每条查询里写哨兵判断（这是改掉 `-1` 的理由）；
- 页面与接口如实展示「未知占比」，不允许静默按 0 拉低均值；
- 未知占比如异常升高（某厂商改协议、流式不回 usage）要进告警（见 5.6）。

### 5.3 查询口径（直接查明细表）

```sql
-- NULL 行自动被聚合跳过，未知条数单独计数
SELECT SUM(total_tokens) AS tokens_known,
       SUM(cost)         AS cost_known,
       SUM(CASE WHEN usage_unknown = 1 THEN 1 ELSE 0 END) AS unknown_calls,
       COUNT(*)          AS calls
FROM wb_model_call_log
WHERE create_time >= ? AND create_time < ?
  AND del_flag = '0';
```

查询必须限定时间范围并走 `(tenant_id, create_time)` / `(capability, model, create_time)` 索引；读查询自带 `del_flag = '0'`。

### 5.4 成本公式

**只有第一条公式在本片落金额（v22）**，另两条是目标口径、当前不落金额（留空策略见下）：

```
cost = prompt_tokens × unit_price_in / 1e6
     + completion_tokens × unit_price_out / 1e6        （token 口径：只对 CHAT 生效）
cost = image_units × price_image_per_page              （图像 / 版面 / OCR 按页，当前不落金额）
cost = calls / 1000 × price_per_thousand_calls         （嵌入等按千次，当前不落金额）
```

`unit_price_in` / `unit_price_out` 是**每百万 token 单价**（取 `wb_model` 的 `price_in_per_m` / `price_out_per_m`）。

- **只对 `CHAT` 算 token 费用**：`prompt_tokens` × 输入单价 + `completion_tokens` × 输出单价；单价取自 `wb_model`，**调用时把用到的单价写入明细**（留档，一行成本可复算）；调价不追溯历史行；
- **`EMBEDDING` 的 token 照记而 `cost` 留空**：明细表没有「按千次」单价列，落一个折算不出的金额会让一行成本无法复算；三项 token 照常记录，`usage_unknown = 0`；
- **`OCR` / `LAYOUT` / `TABLE_STRUCTURE` 按 D34 强制未知**：计费单位未定，三项 token 与 `cost` 一律 NULL + `usage_unknown = 1`；
- **目录里没有该模型或价格缺失**：`cost` 留空（单价快照与成本同进同退），不做本地估算；
- **待定（v22）**：嵌入与图像成本要进明细，需要**补列**（例如「按千次单价」/「按页单价」）或改公式口径，登记见待办清单第六节；
- 币种随明细存；精度：金额 `decimal(18,6)`，展示 4 位小数；
- **不做**分档定价（长上下文/批次价）与缓存读写分别计价 —— 业务上目前用不到（见第十一节）。

### 5.5 特殊形态的计量规则

| 形态            | 规则                                                                                                                                                                                                                                                                                     |
|-----------------|------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| 流式            | 以**结束回执**里的 usage 为准；不回 usage → NULL + `usage_unknown = 1`                                                                                                                                                                                                                   |
| 工具调用 / 多轮 | **按模型调用计数**，一次业务请求可能落多行（用 `trace_id` + `biz_id` 串起来）                                                                                                                                                                                                            |
| 重试            | 每次调用各落一行（延迟 = 一次逻辑调用的整段耗时，含内部重试与退避等待）；`retry_count` 由 HTTP 客户端 SPI 在真实 HTTP 层计数（每次真实请求 +1，尝试次数 − 1），`fallback_from` 记录从哪个模型降级                                                                                        |
| 缓存命中        | 落一行，`cache_hit = 1`，tokens 记 `0`（确实为零），`cost = 0`                                                                                                                                                                                                                           |
| 失败调用        | **请求已发出**的失败仍落一行（含超时、限流、输出结构校验失败）；形参校验（厂商码空 / 入参空 / 模型名空）与调用前结构检查（`JSON_SCHEMA` 缺 schema）拦下的失败**不落行**，那一次请求没有发出；调用已发起而被注册表 / 适配器即拒的失败落一行，`retry_count` 可能为 0、`latency_ms` 为 NULL |
| 图像 / 嵌入类   | 不折算成 token 计价：图像三项（`OCR` / `LAYOUT` / `TABLE_STRUCTURE`）按 D34 记 NULL + `usage_unknown = 1`；嵌入的 token 照记而 `cost` 留空（明细表暂无「按千次」单价列）                                                                                                                 |

### 5.6 告警项（查明细表，只告警不拦截）

| 告警           | 阈值示例                            |
|----------------|-------------------------------------|
| 成本突增       | 日成本环比 ≥ 50% 且绝对值超阈值     |
| 单模型成本异常 | 某模型日成本占总量 ≥ 60% 且环比翻倍 |
| 未知占比       | `usage_unknown = 1` 的比例 ≥ 5%     |

| 缓存命中下滑   | 命中率环比下降 ≥ 20%                |

## 六、路由与流量切换

**口径（已定 D21~D24）**：只做一件事 —— **按「容量占用 / 健康 / 延迟」三个信号自动切换**。全自动，**没有人工优先级、没有权重、没有灰度、没有策略版本**；阈值与权重系数放 `config/workbuddy-model.yml`，**不建路由策略表、管理页不加路由策略视图**。

### 6.1 三个信号与采集点

**维度（D26）**：三个信号全部**按模型**采集与存放 —— 熔断状态、在途计数、延迟 EWMA、RPM/TPM 占用都是模型级一份；一个模型声明了多个能力时，这些状态在多个能力间**共享**（不做"模型 × 能力"各算一份，否则限额会被重复计数、健康也会不一致）。

| 信号     | 采集点                                   | 说明                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
|----------|------------------------------------------|----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| 容量占用 | 进程内调用计数（RPM / TPM / 在途请求数） | 对比**模型行上的限额**（`wb_model.rpm_limit` / `tpm_limit`，**可留空**）；占用率 = `max(RPM 窗口计数 ÷ rpm_limit, TPM 窗口 token ÷ tpm_limit)`，**限额留空即该项记 0、不参与判断**；token 取厂商 usage，缺时按**请求文本长度 ÷ 3** 粗估 —— **粗估只进占用窗口，不落明细、不算成本**（明细仍按 D19 记 NULL + `usage_unknown = 1`）；**在途请求数当前只作模型级实时读数与观测，未作闸门**（目录无并发上限字段），若要作闸门需给目录加字段（登记在待办清单的待定区）                                                                |
| 健康     | 熔断器的失败率统计                       | **健康判定由 Resilience4j 熔断器承担**（`resilience4j-circuitbreaker` **2.1.0**，**只引核心模块、不引 spring-boot3 starter**）：`failureRateThreshold ← error-trigger-ratio`（5%）、时间窗 `← error-window-seconds`（60s）、`minimumNumberOfCalls = 10`、`waitDurationInOpenState ← cooldown-seconds`（60s）、半开放行 1 次、自动转半开；**只把厂商侧不健康的失败计入**（429 / 5xx / 超时 / 连接失败 / DNS；鉴权、参数错、内容拒绝、模型不存在、输出结构校验失败不计）；**被熔断拒绝不算失败**（取许可失败即跳过该候选，不自激） |
| 延迟     | 每次调用的耗时，按滑动窗口算 EWMA        | 窗口可配（默认 5 分钟）；用 EWMA 而非 P95，避免样本少时抖动                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |

**容量接线**：每次真实调用结束后（`ModelInvoker.runByCapability`）写入占用窗口；取许可失败被 `continue` 的候选没有发出请求，不写占用。

无配额层（D15），故**不设"预算/配额"信号**；成本只用于告警与看板，不参与选型。

### 6.2 硬闸门（先剔除，不参与打分）

**候选集按能力筛**：先取"该能力的启用模型"，再逐个过闸门 —— 该模型启用 ∧ 能力匹配 ∧ **其厂商在配置里已配密钥** ∧ 未熔断（向熔断器取一次许可并当场归还：打开期间拒绝，**被拒绝不算失败**，半开探测名额也不会被没被调用的候选用掉）∧ 在生效区间内 ∧ **该模型**占用未超上限（在途请求数不作闸门，见 6.1）。恢复爬升段的候选另按当前放行比例抽样（见 6.5 的 slow start）。

**候选集为空**（目录初始为空，或该能力没有启用模型）时没有可用候选：嵌入调用在解析厂商处报「模型厂商未配置」（`MODEL_VENDOR_UNKNOWN`，40461），嵌入策略保存校验与 `EmbedPipeline` 前置校验同样拒绝（见 4.2）。

### 6.3 打分与选型（全自动，容量优先）

对**全部剩余候选**逐个打分（借鉴 vLLM Production Stack 的归一化两项打分，出处见调研文档第三节）；候选是"该能力的启用模型"里过闸门的那批，而**占用率与延迟都取自模型级状态**（D26）：

```
relativeLoad(i)    = (占用率(i)    − 候选集均值) / max(1, 候选集均值)
relativeLatency(i) = (EWMA延迟(i)  − 候选集均值) / max(1, 候选集均值)
score(i) = − ( β_capacity × relativeLoad(i) + β_latency × relativeLatency(i) )     ← 取最高分
```

**符号与配置项的对应**：`β_capacity` 对应 `beta-capacity`，`β_latency` 对应 `beta-latency`。

| 参数            | 默认                                                  | 含义                                                  |
|-----------------|-------------------------------------------------------|-------------------------------------------------------|
| `beta-capacity` | **1.0**                                               | 容量优先（已定 D21）：占用越高扣分越重                |
| `beta-latency`  | **0.5**                                               | 延迟作次级因素；调大则更看重速度，调到 0 等于只看占用 |
| 平局处理        | 并列候选 > 2 时在**并列集合内**随机取 2 个再比（P2C） | 避免所有请求同时涌向同一个"最闲"模型（羊群效应）      |

两个量都按**候选集自身均值归一化**（+1.0 = 高于均值一倍），同一组 β 在不同规模下含义一致，不必随部署调参。

**量纲**：归一化时**延迟按秒**参与（占用率是 0~1 的比例量，毫秒量纲会让延迟项压过容量项）。β 1.0 : 0.5 的"容量优先"是**阈值内**的口径：空闲者延迟高出约 **1.5 秒**以上时会翻到快而忙的那个 —— 占用 80% / 延迟 100ms 对占用 8% / 延迟 3s 这组读数即翻面（`ModelRouterTest` 里 900ms 仍按容量优先、3s 翻面两条用例夹住这条界线）。

### 6.4 降级链与触发面

- 选中的模型调用失败 → 按**候选排序**依次试下一个；全部失败则回落到**规则路径**（解析环节既有口径：表格降级为段落、版面按几何顺序、OCR 不补文字）；
- 触发面明确：**429、5xx、超时、连接失败切；400/403/参数错误、内容审核拒绝不切**（按错误类型分链，对齐 LiteLLM 的三类 fallback / Portkey 的状态码白名单）；
- 每次调用各落一行明细，`retry_count` 由 HTTP 客户端 SPI 在真实 HTTP 层计数（每次真实请求 +1，尝试次数 − 1）、`fallback_from` 记从哪个模型降级。

### 6.5 防抖与恢复

| 机制                       | 口径                                                                                                                                            |
|----------------------------|-------------------------------------------------------------------------------------------------------------------------------------------------|
| 失败率窗口                 | 熔断器按 `error-window-seconds`（默认 60s，`TIME_BASED` 滑动窗口）统计失败率，窗口内不足 `minimumNumberOfCalls`（10）不判越线                   |
| 打开保持                   | 失败率越线即打开，打开期间该模型不进候选；保持 `cooldown-seconds`（默认 60s，可参考厂商 `Retry-After`）；**按模型条目维度**，不按厂商           |
| 重试与退避                 | 同一实例内的重试与退避**归 LC4j**（`max-retries`）；平台负责**换模型降级**与**熔断**（保持时长可参考厂商 `Retry-After`）                        |
| 半开                       | 打开保持到期**自动转入半开**（`automaticTransitionFromOpenToHalfOpenEnabled`），**放行 1 次**探测请求；成功即关闭并进恢复爬升段，失败即重新打开 |
| **Slow start**（已定 D22） | 由 **OPEN → HALF_OPEN 的流转**驱动：探测成功后 **45s 内放行比例 0.2 → 1.0** 线性爬升（`slow-start-seconds`，不引入人工权重，D23）               |
| 抖动告警                   | 单位时间内切换次数超阈值即告警（见 5.6）                                                                                                        |

**没有独立的"阈值窗口"与"最小驻留"参数**：防抖由失败率窗口与打开保持两段时长承担（v23 删除两个失效键，见 4.4）。

### 6.6 决策粒度与粘性

| 场景                      | 粒度                 | 理由                                                                       |
|---------------------------|----------------------|----------------------------------------------------------------------------|
| 解析（表格 / 版面 / OCR） | **每次模型调用**决策 | 打分是逐次调用算的；同一页的多次调用**不锁定**同一模型（当前口径，见 D25） |
| 对话                      | 按会话               | 中途换模型会影响回答风格与缓存命中，仅以降级形式切换                       |
| 批处理任务                | 按任务归属统计       | 成本与失败重跑按任务维度                                                   |

### 6.7 可观测（硬要求）

每次调用写 `route_reason`（见 4.6 字典，如 `CAPACITY_HIGH` / `LATENCY_HIGH` / `UNHEALTHY` / `FALLBACK_FROM` / `SLOW_START` / `OK`）、`fallback_from`、`retry_count`；页面提供「按原因统计切换次数」。**没有 route_reason，自动切换出问题就查不出来**。

**两个取值的落点**：`UNHEALTHY` 落在**可降级的失败当次**那一行（该次失败即换模型的依据；最后一跳失败同样带它）；`SLOW_START` 覆盖半开探测与恢复爬升段这两段放行。被硬闸门剔除的候选没有发出请求，不产生明细行。

### 6.8 与缓存、一致性的相互影响

- 换模型会降低缓存命中（缓存键含 `model` 与 `model_version`），成本核算要能体现；
- 解析结果质量可能随模型变化，`CapabilitySnapshot` 已记录每页模型版本，可回溯「同一文档两次解析结果不同」；
- 同一份文档**允许逐页换模型**（打分逐次调用生效），但**同一页的同一能力只调用一次**，不做页内重试换模型以外的切换。

## 七、治理与限流

### 7.1 装饰器顺序（固定顺序，推理与排障都依赖它）

```
凭据解析 → 并发/排队（可选）→ 缓存查询 → 超时与 LC4j 重试
→ 熔断(Resilience4j) → 路由选型 → 适配器调用 → 计量落库 → 指标
```

说明：**本方案没有配额层**（已定 D15），装饰器链无"配额校验"这一步；路由在缓存之后（避免为即将命中的请求做无谓选型），计量在最后且**失败路径同样落库**。

**路由状态放哪（已定 D24 的延伸）**：熔断状态（`ModelCircuitBreakers` 持有的进程内注册表）、在途计数、延迟 EWMA **先放进程内**（`RouteStateStore` 接口 + 内存实现），**不为此把 Redis 引进 `workbuddy-model`**；接口留着，多副本部署时换 Redis 实现即可 —— 这也把依赖方向那个待决问题（3.3 的 A/B）暂时绕开。

### 7.2 限流：只做"模型限额感知"，不做配额拦截

| 项                                  | 口径                                                                                                                                   |
|-------------------------------------|----------------------------------------------------------------------------------------------------------------------------------------|
| 模型限额（RPM / TPM）               | **唯一来源是模型行**（`wb_model.rpm_limit` / `tpm_limit`），**可留空**；用途是避免把 key 打封并在占用高时触发切换（无厂商级限额，D30） |
| 触发限流时的行为                    | 收到 429 → `RATE_LIMITED` 落明细 + **计入熔断失败**（该模型按失败率转向打开）→ 路由按降级链切换；不做主动拦截                          |
| 要不要主动限速                      | 本期不做。若以后需要，复用已有 Bucket4j + Redis（不必新增组件）                                                                        |
| 配额层（租户/团队限额、预扣、拦截） | **明确不做**                                                                                                                           |

### 7.3 熔断与重试

- 熔断维度：**模型条目**（对齐 LiteLLM/Kong 的部署维度，不按厂商 —— 同厂商不同模型健康度不同）；**健康判定由 Resilience4j 熔断器承担**：引入 `resilience4j-circuitbreaker` **2.1.0**，**只引核心模块、不引 spring-boot3 starter**（仓库现有 Bucket4j 与 Actuator，无同类实现，也不新增别的治理组件）。参数映射：`failureRateThreshold ← error-trigger-ratio`（0.05 → 5%）、时间窗 `slidingWindowSize ← error-window-seconds`（60s，`TIME_BASED`）、`minimumNumberOfCalls = 10`、`waitDurationInOpenState ← cooldown-seconds`（60s）、`permittedNumberOfCallsInHalfOpenState = 1`、`automaticTransitionFromOpenToHalfOpenEnabled = true`；**只把厂商侧不健康的失败计入**（谓词 `ModelErrorClassifier.isVendorUnhealthy`：429 / 5xx / 超时 / 连接失败 / DNS；鉴权、参数错、内容拒绝、模型不存在、输出结构校验失败按成功记）；**被熔断拒绝不算失败**（取许可失败即跳过该候选，不自激）；**slow start（D22）由 OPEN → HALF_OPEN 的流转驱动**，45s 内放行比例 0.2 → 1.0；
- 可降级判定归调用器（`ModelInvoker.canFallback(Throwable)`）：映射与判定同在 `invoke/ModelErrorClassifier` 一处完成 —— **覆盖规则优先**（`MODEL_UNREACHABLE` / `MODEL_OUTPUT_INVALID` 归可降级，含网络不可达与平台侧结构校验失败），未命中再按异常链上的 `RetriableException` / `NonRetriableException` 判定；判定结果里可降级的是超时、连接失败、429、5xx、结构校验失败，**不可降级**的是参数错误、内容审核拒绝、鉴权失败、模型不存在。**未识别异常按 `MODEL_SERVER_ERROR` 计，并计入熔断失败**（保守口径），与 `canFallback` 的"不可降级"并存 —— 两者判据不同：一个看厂商侧可用性，一个看能否换模型重试；
- 同一实例内的重试与退避**归 LC4j**（`max-retries` → `maxRetries`）；平台负责**换模型降级**与**熔断**（打开保持时长可参考厂商 `Retry-After`）；
- 指标复用已接入的 Actuator（端点与认证口径见 §2）。

### 7.4 并发与排队

交互请求与批处理（解析）分队列；解析任务优先级低于交互；队列满时批处理延后重试（不阻塞交互）。

## 八、管理页面

**交互口径（定稿，D29）**：主列表就是**模型清单**，「新增模型」一个抽屉跑完。**页面不涉及密钥与地址** —— 厂商下拉的选项来自前端枚举（与配置 `knowledge.model.vendors` 的键一致，只读，不能新建）；密钥轮换与改地址走配置 + 重启。**没有「接入配置」tab，也没有任何密钥界面**。

### 8.1 接口清单（前缀 `/model`，对所有登录用户开放）

**路径口径（v25，2026-10-15 补注）**：前缀是 `/model`，**不带 `api` 段** —— 仓库既有 Controller 一律不带 `api` 段，`web` 的 `http.ts` 里 `baseURL` 是空串。模型用量的两个只读接口写作 `GET /model/usage/summary` 与 `GET /model/usage/calls`。`/model` 前缀下同时挂着页面路由（`/model/manager` 与 `/model/usage`），接口一律带子路径，Vite 开发代理按 `^/model/` 与 Accept 头区分导航与接口。

**权限口径（v25）**：模型管理页面与六个接口**对所有登录用户开放**，不是管理员专项 —— 两个 Controller 的方法上都不标 `AdminOnly`，侧栏菜单项与路由也不带 `adminOnly` / `meta.adminOnly`；未登录仍由全局登录校验拦住（`anyRequest().authenticated()` → `40101`）。审计照旧：价格与模型的变更写业务审计（§8.3）。

**厂商口径（v25）**：**厂商不是被管理实体** —— 前端枚举承载候选与展示名，必须与 `knowledge.model.vendors` 配置保持一致；页面**不显示密钥状态**，密钥与地址只在配置与部署环境变量里。

| 方法             | 路径                   | 用途                                                                              |
|------------------|------------------------|-----------------------------------------------------------------------------------|
| GET / POST / PUT | `/models`              | 模型维护（厂商、能力、价格、限额、状态）—— 保存时校验 `vendor_code` 在配置中存在  |

| GET              | `/model/usage/calls`   | 调用明细查询（按租户 / 能力 / 模型 / 路由原因 / 状态 + 时间范围）；按调用时间倒序 |

说明：不提供 `/credentials`（密钥不在库、页面不涉及）、不提供 `/route-policies`（路由参数在 `config/workbuddy-model.yml`，D24）、不提供厂商的增删改（厂商是配置里的一个键与前端枚举，不是库里的实体）。`/calls` 支持 `limit`（默认 500、上限 2000），`/summary` 忽略该参数。

### 调研结论采纳情况（调研见 `docs/research/模型能力平台-市面产品调研.md`）

**原则**：调研归调研，方案贴合自身业务 —— 只有能解决我们真实问题的才采纳。

| 调研项                                                        | 处置                         | 理由                                                                                   |
|---------------------------------------------------------------|------------------------------|----------------------------------------------------------------------------------------|
| R1 策略枚举与默认值对齐 LiteLLM                               | **不适用（口径已变）**       | 我们不做策略枚举，改为三信号打分（D21~D23）                                            |
| R6 降级链按错误类型分链、429/5xx 切而 400/403 不切            | **采纳**                     | 直接决定降级是否会误伤（参数错误重试无意义）                                           |
| R7 冷却与熔断按**模型条目**维度                               | **采纳**                     | 修正原设计按厂商维度（同厂商不同模型健康度不同）                                       |
| R9 冷却时长参考厂商 `Retry-After`                             | **采纳**                     | 一个字段的成本，减少无谓重试                                                           |
| R12 多副本冷却/用量状态放 Redis                               | **暂不采纳**                 | 先单副本、状态放进程内（`RouteStateStore` 内存实现），多副本再换 Redis                 |
| R21 流式以结束回执为准、禁止逐块累加                          | **采纳（只留这一句）**       | DashScope 原生逐块是累积值，累加会重复计费                                             |
| — 归一化两项打分（vLLM Load Aware Routing，见调研文档第三节） | **采纳（本轮新增）**         | 正是"快但忙 vs 慢但闲"的现成解法：按候选集均值归一化、单一 β 权衡                      |
| — P2C 平局随机（Envoy least request）                         | **采纳（本轮新增）**         | 候选 > 2 时避免所有请求涌向同一个"最闲"模型（羊群效应）                                |
| — slow start（Envoy）                                         | **采纳（本轮新增）**         | 恢复/新上线模型逐步放量，D22                                                           |
