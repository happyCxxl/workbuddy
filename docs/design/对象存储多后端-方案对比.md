# 对象存储多后端 · 现状、目标态与方案对比

一句话：`file-center.storage-type` 在 minio 与 local 之间切换后，另一侧的任务与产物在页面上照旧可见、内容却读不到；每新增一种存储类型，这个问题会再复制一份。本文档只做现状核对、目标态定义与备选方案对比，**不含实现改动**。

阅读顺序：一（问题）→ 二（现状）→ 三（根因）→ 六（方案对比）→ 七（两个数据源下的全流程示例）→ 八（落地路径）→ 十（验收口径）。

> 第七节的 `file-center` seed/回落配置与运行期补行属于改造前方案；当前实现已移除该配置，数据源由 `../../workbuddy-biz/src/main/resources/sql/init.sql` 维护，表为空或没有可用当前行时启动失败。

## 一、问题

### 1.1 现象

| 层       | 现状                                                                                                                               |
|----------|------------------------------------------------------------------------------------------------------------------------------------|
| 元数据   | 任务、产物行、切片集合、向量集合、血缘只有 MySQL 一份，与存储后端无关，会一直存在、一直被页面列出来，状态仍是 `SUCCESS` / `ACTIVE` |
| 对象本体 | 按 `file-center.storage-type` 分区，两种后端互不相通                                                                               |
| 二者之间 | 没有「这条记录属于哪个后端」的字段：读路径解析物理位置时只能依据当前配置                                                           |

结果：页面展示的是**两座孤岛记录的并集**，当前进程只读得到其中一座；另一侧的记录状态正常、卡片正常，内容却是空的。新增第三种存储类型后孤岛变三座，并集里的死记录只会更多。

### 1.2 目标态（已确认口径）

| # | 口径                                                                                                                                    |
|---|-----------------------------------------------------------------------------------------------------------------------------------------|
| 1 | 存储类型只决定「字节落在哪」，不决定「谁能看见、谁能用」：所有任务与产物在页面上统一展示、统一可读                                      |
| 2 | 页面必须**标出**存储类型，且只标在执行链页面的文件栏：徽标由原始文件的记录决定，一链一徽标                                              |
| 3 | 同一条处理链的所有环节产物**必须落在同一个数据源实例上**，不允许分散；读取按记录里的数据源 ID 定位后端，与当前启用项无关                |
| 4 | 切换数据源即改 `wb_storage_source` 里 `is_current` 的那一行；落在另一个数据源上的任务**不允许继续执行**，把当前启用切回该数据源才能继续 |

### 1.3 失败时的实际表现

读路径共 7 处，失败表现分两类：**静默留空**（页面看不出异常）与**硬失败**（有错误提示）。静默那一类是「看起来能用、实际用不了」的直接来源。

| 读口                                       | 位置                                                                                                               | 失败表现                                                                                                          |
|--------------------------------------------|--------------------------------------------------------------------------------------------------------------------|-------------------------------------------------------------------------------------------------------------------|
| 阶段产物内容（解析详情与执行链内容区共用） | `StageContentQueryServiceImpl.stageContent`                                                                        | **静默**：catch 后 `items` 置空、`total=0`，`latest` 仍为 true → 页面显示「这次运行有产物」、内容空白、**不报错** |
| 组装详情（统计 / 告警 / 大纲 / 文档）      | `StructureControlServiceImpl.readDocument`                                                                         | **静默**：catch 后返回 null，统计与告警留空                                                                       |
| 预处理详情（统计 / 视图元素）              | `PreprocessControlServiceImpl.readView`                                                                            | **静默**：catch 后返回 null，统计与元素留空                                                                       |
| 原文件字节（原文预览 / 下载）              | `FileServiceImpl.download` → `FileStorage.open`                                                                    | 硬失败：抛 `SYSTEM_ERROR`（40500），页面提示「系统异常，请稍后重试」或拿到错误响应                                |
| 头像                                       | `AvatarController.read`                                                                                            | 按「没有头像」处理，页面回落姓名首字                                                                              |
| 索引装配 / 统计                            | `IndexRowAssembler`、`StatsSupport`                                                                                | 硬失败：装配或统计中断                                                                                            |
| 执行器读上游产物                           | `ParseTaskRunner`（读源文件）、`StructureTaskRunner`、`PreprocessTaskRunner`、`ChunkTaskRunner`、`EmbedTaskRunner` | 硬失败：任务落 `FAILED`，错误码是通用 `SYSTEM_ERROR`，看不出真实原因                                              |

两类表现的共同点：错误信息里只有 sha256 或 fileId，读不出「换过后端」这一层。

## 二、现状

本节描述改造前的实现状态，作为方案取舍的依据；改造后的类名、配置与接口以代码与第八节为准。

### 2.1 存储抽象与装配

| 事项       | 现状                                                                                                                                                                                       |
|------------|--------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| 端口       | `StorageProvider` 只有 `put` / `get` / `exists`，**无 list、无 delete**                                                                                                                    |
| 实现       | `MinioStorageProvider`（S3 兼容对象存储）、`LocalStorageProvider`（本地磁盘，bucket 当子目录，布局 `{local-root}/{bucket}/{key}`）                                                         |
| 装配       | 两者用 `@ConditionalOnProperty(name = "file-center.storage-type", ...)` **互斥装配**，minio 侧 `matchIfMissing = true`（不配该键时默认走 MinIO）；容器里**永远只有一个** `StorageProvider` |
| 桶         | minio 侧由 `MinioClientConfig.minioClient` 启动时确保 `files` / `artifacts` 存在；local 侧目录在写入时按需创建                                                                             |
| 本地根目录 | 由数据源行的 `config_json.rootDir` 决定；旧默认 `./data/file-center` 按进程工作目录解析，IDE、jar、容器三种启动方式可能落到不同目录                                                        |
| 写入三处   | `MinioFileStorage.putFile`（上传文件）、`AbstractFileStorage.putObject`（阶段产物，内容寻址）、`AvatarController.upload`（头像）                                                           |
| 读取       | 全部经 `StorageProvider.get(bucket, key)`；除上传文件取档案里的 bucket 外，其余桶名都在调用时从配置现取                                                                                    |

### 2.2 对象引用的落库点

| 业务     | 表 / 字段                                                       | 存的是什么                                      | 桶名来源                     | 后端来源       |
|----------|-----------------------------------------------------------------|-------------------------------------------------|------------------------------|----------------|
| 上传文件 | `wb_file_object.bucket` + `object_key`                          | 桶名 + fileId                                   | 建档时写入 `file-bucket`     | 读时按当前配置 |
| 阶段产物 | `wb_knowledge_pipeline_product.artifact_id`（= `content_hash`） | 只有 sha256                                     | **读时**取 `artifact-bucket` | 读时按当前配置 |
| 切片集合 | `wb_knowledge_chunk_set.artifact_id`                            | 只有 sha256                                     | 同上                         | 读时按当前配置 |
| 向量集合 | `wb_knowledge_embedding_set.artifact_id`                        | 只有 sha256                                     | 同上                         | 读时按当前配置 |
| 头像     | `wb_user.avatar`                                                | 相对 key（`avatar/{userId}/{随机段}.{扩展名}`） | **读时**取 `file-bucket`     | 读时按当前配置 |

物理位置需要四元组「后端类型 + （endpoint 或 local-root）+ 桶 + key」，落库的只有最后两段的一部分，**「后端」这一维没有落库**。上传文件是唯一把桶名写进档案的一处，其余两处连桶名都靠读时取配置。

### 2.3 现有文案已声明这个行为

| 位置                                                          | 原文口径                                                     |
|---------------------------------------------------------------|--------------------------------------------------------------|
| `application.yml` 的 `file-center` 段注释                     | 「两种后端的对象不互通，切换后旧对象需手工复制过去才能读到」 |
| 数据源行 `config_json` 的存储参数                             | 「已写入的对象不会自动迁移，切换后旧对象在新后端里读不到」   |
| `../../workbuddy-biz/src/main/resources/sql/README.md` 第五节 | 重建库必须同时清空对象存储，不然新库会指向旧产物             |

「切换后旧对象不可用」是当前**已知并声明**的行为，本议题要改的正是这条声明。

## 三、根因

| # | 根因                  | 说明                                                             | 可单独验证的现象                                                    |
|---|-----------------------|------------------------------------------------------------------|---------------------------------------------------------------------|
| 1 | 记录里没有后端标识    | 读路径唯一的选路依据是全局配置，与「这条记录当初写在哪」无关     | 只改 `artifact-bucket` 的名字也能让产物读不到（不换后端同样复现）   |
| 2 | provider 单例装配     | 进程无法同时访问两个后端，既读不到另一侧，也无法就地搬运         | 写不出「把 minio 对象搬到 local」的工具（端口也没有 list / delete） |
| 3 | 端口能力不足          | 无 list 就枚举不出待迁移对象；无 delete 就清不掉孤儿对象         | 迁移只能借外部工具（MinIO 控制台或文件系统复制）                    |
| 4 | 读失败被静默吞掉      | 页面把「读不到」呈现成「内容为空」，与「本来就没有产物」无从区分 | 见 1.3 表前三行                                                     |
| 5 | local-root 是相对路径 | 同一份配置在不同工作目录下解析出不同物理目录                     | 用 IDE 与 jar 分别启动，local 那侧时有时无                          |

根因 1 是主因：**记录里带上后端标识后，读路径即可按记录路由，切换配置不再使旧记录失效**。根因 2、3 决定「能否并存与迁移」，4、5 决定问题是否容易被察觉与排查。

## 四、目标态与不变量

| 类别     | 内容                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
|----------|------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| 不变量   | 产物 append-only，修复不改历史产物本体；产物按 sha256 内容寻址，同内容跨后端天然一致；**数据源 ID、存储类型码与桶名必须与对象 key 一起落库**；读路径不得依据「当前启用的数据源」决定去哪取                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| 配置语义 | `storage-type` 从「唯一后端」收窄为「**当前启用的数据源**」，取值是代码侧 `StorageType` 枚举的字符串码（`minio` / `local`）；每种类型一段配置（`file-center.minio.*` / `file-center.local.*`），**没有启用清单**——当前启用的数据源在启动时探活并确保桶存在，其余数据源按需创建、首次读到才连接，启动日志按配置推导打印「当前启用 = MinIO；另可用 = 本地」。`local-root` 按绝对路径解析并打日志。**当前启用的数据源是全局的**：不按知识库或按用户分别绑定；将来若要按知识库选，绑定粒度与门禁基准一起改。**身份是数据源实例**：`wb_storage_source` 一行一个实例，同一种类型可以有多行；对象记录落 `storage_source_id`（用户表是 `avatar_storage_source_id`），同一行保留存储类型码与桶名，读取按记录里的数据源 ID 定位后端，类型码用于展示与降级。数据源行由 `init.sql` 或库内 SQL 维护；表为空或没有可用当前行时启动失败，运行期不按配置补行。 |
| 命名     | `MinioFileStorage` 名字带 Minio，实际继承 `AbstractFileStorage` 并使用注入的 provider，**local 下同样生效**，名不副实，批次 1 改名为 `DefaultFileStorage`                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| 文案     | 2.3 的三处声明改写为「多后端并存、按记录路由」的口径                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| 同类问题 | 向量库与检索后端同族（元数据一份、实体按后端分区）：接入时按同一模式——记录带后端标识、按记录路由、拒绝跨后端续跑                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |

### 5.1 可借鉴结论

1. **「字段有了、读路径不按字段路由」等于字段无用**：Dify 已经把 `storage_type` 落库，但读路径全部走启动时固定的进程内单例，该列只在迁移命令里被改写一次。本项目的读路径（文件下载、阶段产物、头像）必须**按记录挑 provider 实例**；只加列不改读路径，问题依旧。
2. **标识列存稳定字符串，不存整数序号**：Dify 用 `s3` / `local` / `opendal` 这类字符串枚举；RAGFlow 定义了整数枚举却只用于健康检查显示，实体里没有该列。本项目直接把 `minio` / `local` 写进记录，页面拿它做类型徽标。
3. **把定位键真正落库，路由就不需要额外的映射表**：Onyx 在记录上存 `bucket_name` + `object_key` 并建联合索引，RAGFlow 用 `location` + 桶名两列。本项目上传表已是 `bucket` + `object_key` 形态，同一模式补到阶段产物表与头像表即可；产物的 sha256 保留为内容寻址键，桶名、存储类型码与数据源 ID 一起落库。
4. **切换后端做成可重复运行的迁移命令 + 字段改写，而不是读时猜后端**：Dify 的迁移带 `--dry-run` / `--force`，**对象全部搬完并校验后才改写记录的标识**，迁移失败先拦住改库；迁移期间靠「老后端回退」兜底，比让读路径试探可靠。
5. **要留回滚余地就用 Onyx 的双写三件套**：写 / 删同时打新老两个后端、读在主库 miss 时回退老库、老库靠一个退休标记对象让所有进程自动停写，配套 `--replay` 把写失败的对象补回老库。本项目「同一处理链产物不跨存储类型」的约束正好适合**按处理链整体迁移 + 迁移完成前双读**，而不是按对象粒度混存。
6. **对外一律走应用自身的下载接口**：Dify 只在 Cloud + S3 才给预签名直链，RAGFlow 的预签名能力在生产代码零调用，Onyx 用流式响应。本项目已经遵循这条（`/files/{fileId}`、`/user/avatar/{userId}`），页面只需额外标注记录的存储类型。
7. **没有 list 的端口会挡住迁移**：Dify 迁移依赖 `scan()`、Onyx 依赖 `list_files_by_prefix`、RAGFlow 接口有 `ListObjects`。`StorageProvider` 长期只有 put / get / exists 的话，后端切换只能靠源侧另有清单；迁移前要先补一个受控的列举能力。

未核实项：Dify 迁移命令的 CLI 顶层名未逐字验证；RAGFlow 的 `StorageType.String()` 是否写库未找到证据；LightRAG「无跨后端迁移工具」是遍历 `main` 未找到后的结论，未见官方「不支持」声明。

## 六、方案对比

### 6.1 备选方案

**方案 A：记录带后端标识 + 多后端路由**

- 做法：三类对象记录各加「存储后端标识」与「桶名」两列（不建统一引用表）；`StorageProvider` 由「单 Bean」改为「带标识的注册表」，读取按记录里的标识选 provider；`storage-type` 退化为「新对象写哪」。
- 覆盖根因：1、2、4、5；根因 3（端口缺 list / delete）只在需要搬运既有对象时有影响——开发期无存量数据，不涉及。
- 风险：触碰存储读写主链路与五处对象引用点（上传文件、阶段产物、切片集合、向量集合、头像）。
- 规模：中等。
- 当前取值：取 A 的「登记 + 路由」部分；C 的迁移与自检等到有存量数据时再补。

**方案 B：只统一引用格式（存 URI）**

- 做法：把 `bucket` + `key` 合并成 `minio://bucket/key`、`local://bucket/key` 之类的 URI。
- 覆盖根因：只覆盖根因 1 的形式部分——URI 里没有 endpoint 与 local-root，配置一改仍然失效；而且取别的后端仍需多后端装配，根因 2、3 不动。
- 定位：不作为独立方案；「引用写成什么形式」可并入方案 A。

**方案 C：只加迁移与自检（运维兜底）**

- 做法：端口补 list / delete，增加「从后端 X 全量复制到后端 Y」的命令与启动自检（抽查产物可读性）。
- 覆盖根因：3；根因 1、2 不动——切换后仍不能并存，仍是「搬完才能用」。
- 定位：**有存量数据时**才需要；开发期无存量数据，本议题不涉及。

**方案 D：A + C**

结构上按记录路由，运维上提供迁移与自检；存量数据用迁移命令一次搬清，或按需惰性搬。开发期取 A，不取 D。

## 七、两个数据源下的全流程示例

配置（把现有扁平键改成按类型分段，去掉 `backends` 之类的清单）：

```yaml
file-center:
  storage-type: minio          # seed 后哪一行是当前启用（StorageType 枚举的字符串码），启动时探活并确保桶存在
  minio:
    endpoint: http://localhost:9000
    access-key: minioadmin
    secret-key: minioadmin
    file-bucket: files
    artifact-bucket: artifacts
  local:
    root: ./data/file-center   # 校验为绝对路径
    file-bucket: files
    artifact-bucket: artifacts
```

装配规则：**当前启用的数据源在启动时探活（连不上直接启动失败、顺带确保桶存在）；其余数据源按需创建，首次读到才连接**——只跑 local 的开发环境不会被 MinIO 拖死。启动日志按配置推导打印「当前启用 = MinIO；另可用 = 本地」，不需要人手维护清单。桶名放在各自那段即可：桶名已随记录落库，以后改名不会让旧对象失效。

一条链的数据（上传 `产品手册.pdf`，走完解析 → 组装 → 切片；数据源 ID `2001` 是 MinIO 那一行，`2002` 是本地磁盘那一行）：

## 八、落地路径

两批上线，批次 1 内部不可再拆：**读路径按记录取数依赖写入时已落数据源 ID**。

| 批次         | 内容                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                | 改动面                                                     | 验收                                 |
|--------------|---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|------------------------------------------------------------|--------------------------------------|
| 1 登记与路由 | 四张表加 `storage_source_id` 与 `storage_type`（`wb_file_object`、`wb_knowledge_pipeline_product`、`wb_knowledge_chunk_set`、`wb_knowledge_embedding_set`），产物类三张另加 `bucket`，`wb_user` 加数据源 ID 与类型、桶三列；新增 `StorageType` 枚举与 `ObjectRef`；`StorageProvider` 从 `@ConditionalOnProperty` 互斥装配改为**按类型注册**（当前启用的数据源启动探活、其余按需创建）；新增 `StorageRouter`；三处写入路径落齐全套定位键；读路径按记录取数（产物、源文件、头像、各详情与统计、索引装配、五个执行器） | `init.sql` 与四个实体；存储模块四个类；biz 十个读口        | 切换当前启用的数据源后旧产物仍能打开 |
| 2 守卫与徽标 | 触发环节前校验本链源文件所在数据源与当前启用的数据源一致（40453）；读失败明确报错（40454 / 40455）；文件结果列表响应带 `storageType`，执行链页面的文件栏加类型徽标、触发入口置灰                                                                                                                                                                                                                                                                                                                                    | biz 五个环节触发接口与文件结果列表；前端执行链页面的文件栏 | 见第十节                             |

守卫的校验口径：**门禁只设在会写对象产物的五个环节**（解析 → 向量化）。基准取**本链源文件所在的数据源 ID**（`wb_file_object.storage_source_id`），与当前启用的数据源不一致即拒绝；一条链的产物落在同一个数据源上，由这道门禁保证，无需给任务另加「数据源」字段。知识库级的索引构建（`BUILD_INDEX`）**不设跨数据源门禁**：它只读各链产物、产物落在向量库，读路径按记录路由即可，同一知识库里并存两个数据源的链仍能构建索引。

同一道校验还要放在**产物写入口**（`ProductPersistence.persist`）：触发时校验过、执行时当前启用已切换的旧任务（排队补投后才执行到）在写产物那一步被拒并落 `FAILED`，链不会分裂到两个数据源。种子数据在复用的档案所属数据源与当前启用的数据源不一致时跳过产物写入并记一行日志，避免开发便利数据把应用启动带崩。

**页面热切换存储数据源（已实施）**：口径为旧链**拒绝继续执行**（不改"跟随链快照"），产物依然可读、切回原启用数据源后可继续。

- 记录身份是数据源：新增 `wb_storage_source`（`name` 唯一 + `storage_type` + `config_json` + `is_current` + `status` + 最近一次探测结论与时间 + 逻辑删除标记与留痕字段），一行一个实例，同一种类型可以有多行。对象记录落 `storage_source_id`（`wb_file_object`、`wb_knowledge_pipeline_product`、`wb_knowledge_chunk_set`、`wb_knowledge_embedding_set` 四张表，用户表是 `avatar_storage_source_id`），`storage_type` 保留作展示与读路径降级。`is_current` 全表至多一行，由「先清后置」维持。
- 值来源与生效方式：当前启用读 `wb_storage_source` 里 `is_current` 那一行；数据源行由 `../../workbuddy-biz/src/main/resources/sql/init.sql` 或库内 SQL 维护，表为空或没有可用当前行时启动失败。`StorageRouter` 持有当前启用的数据源 ID，`markCurrent` 先取后端（建桶或建根目录）再替换；触发守卫与写入口守卫都读它。启动初始化在 `StorageSourceServiceImpl` 的 `@PostConstruct`：启用的行注册定义，只探活当前启用那一行——当前启用是 local 时不连 MinIO。
- 接口（三个都仅管理员，前缀 `/system/storage-sources`）：`GET /system/storage-sources`（列举未删除的数据源行，含完整 `params`、运行时接入标记与最近一次探测结论）、`POST /{id}/current/preview`（只算影响面，不落库、不切换、不探活）、`POST /{id}/current`（探活通过后先清后置 `is_current` 并替换运行时的当前启用）。目标已停用抛 40458；`id` 查不到抛 40457；参数不齐抛 40001；探活失败抛 40459；类型码值无法识别抛 40455。参数里的密钥入库并随 `params` 完整返回（三个接口都标了 `@AdminOnly`），服务端日志只打参数名与数据源名。`currentType` 在预览里是切换前的值、在切换响应里是切换后的值。
- 页面：一级「系统设置」（`/settings`，所有登录用户可见）：页内按卡片分区、各卡片自己判权限，当前的「存储源」卡只管理员渲染，非管理员看到页标题与一行空态；卡片统一固定宽高（`width: 275px` / `height: 305px`），卡片容器换行排布，新增卡片复用同一组尺寸；卡内只有「存储源下拉 + 启用按钮」与「当前启用信息块」（名称、类型、参数与状态四态），启用走「预览影响面 → 确认启用」两步。页面只列举与启用：新增、编辑、停用、删除与连接测试都没有入口，数据源由 `init.sql` 或库内 SQL 维护。

开发期不做迁移、双写与回退（第五节 Dify / Onyx 的做法已记录在案，等到有存量数据时再取）；端口也不加 `delete` / `list`，孤儿对象（例如换头像后留下的旧对象）由既有的「重建库时清空对象存储」约定兜底（见 `../../workbuddy-biz/src/main/resources/sql/README.md` 第五节）。

开工前库表与对象存储一并重建：新列直接写进 `init.sql`，不写 ALTER 迁移脚本。

## 十、验收口径

### 10.1 开工前的复现步骤

开工前先跑一遍，确认根因成立；全程不改代码：

1. `cd docker` 后 `docker compose up -d`（起 MySQL / Redis / MinIO）。
2. 确认 `wb_storage_source` 当前启用行是 MinIO，`mvn verify -DskipTests`，然后 `java -jar knowledge-biz\target\knowledge-biz-5.1.0.jar`。
3. `web/` 下 `pnpm dev`，登录后进入一个知识库，上传一份文档并触发解析。
4. 打开该文件结果的解析详情，确认内容可见（记下此刻内容非空）。
5. 停后端，把 `wb_storage_source` 的当前启用切到本地行，重启。**不要动数据库里的对象记录，也不要重新上传**。
6. 回到同一页面，记录实际现象。预期：任务卡片与历史记录照常显示、状态仍为成功；解析详情与内容区为空且不报错；原文预览与下载失败；再触发「组装」会落 `FAILED`（`SYSTEM_ERROR`）。
7. 反向（可选）：切回 minio，对 local 期间新产生的任务重复第 4~6 步，现象对调。

第 6 步的现象与预期一致，即说明根因 1、2、4 成立；若与实际观察不符，以实际观察为准并回填本文档。
