# 接口逻辑

本文件写「后端拿到请求之后到底做了什么」。涉及的表是 `wb_file_result`（文件结果）、`wb_knowledge_pipeline_task`（环节任务）、`wb_knowledge_pipeline_product`（产物）与 `wb_knowledge_base`（归属），字段定义见 `../知识库列表/03-接口逻辑.md`；通用机制（错误码分段、鉴权、分页）见 `../../README.md` 的「全局约定」章。

## Controller 划分

| Controller                     | 管什么                                                                                           |
|--------------------------------|--------------------------------------------------------------------------------------------------|
| `KnowledgeFileParseController` | 解析环节专属：触发解析 `POST /{fileResultId}/parse`、解析详情 `GET /{fileResultId}/parse-detail` |
| `KnowledgeFileStageController` | **各环节共用**的产物内容 `GET /{fileResultId}/stage-content`（白名单五环节同一入口）             |
| `KnowledgeLineageController`            | 血缘 `GET /{fileResultId}/lineage`（执行链整体，不属解析环节）                                   |

三者都以 `/file-results` 为类级前缀，方法级路径互不重叠。

## 归属校验（所有按 `fileResultId` 直取的接口）

入口是 `FileResultAccessGuard`，由各服务在**服务层入口**调用（`require(fileResultId)` 或 `check(fileResult)`）：

1. 先定登录上下文：`KnowledgeBaseRules.visibleOwnerId(user)`，**无登录一律拒绝**（40101），不退化成「不过滤」；
2. 按 `fileResultId` 取文件结果；取不到即拒绝；
3. 文件结果自身没有归属列，归属经 `wb_file_result.knowledge_base_id` 反查知识库：`knowledgeBaseDbService.getActiveById` → `KnowledgeBaseRules.checkAccessible`；
4. 管理员放行；普通用户仅限自己创建的库（`user_id` 与本人一致，`user_id` 为空的存量数据对普通用户不可见）。

**错误码口径**：越权与「不存在」统一返回 **40401**，不把别人的 ID 变成可探测的信息；未登录返回 40101。守卫**不改变**各服务原有的 `FILE_RESULT_NOT_FOUND`(40432) 判空语义 —— 记录不存在仍是 40432，只有越权才落到 40401。

覆盖范围：`/file-results/{fileResultId}/...` 前缀的 12 个接口（解析触发 / 解析详情 / 产物内容 / 血缘，以及组装、预处理、切片、向量化各自的触发与详情）。

## `POST /file-results/{id}/parse`

`KnowledgeFileParseController.parse` → `ParseControlServiceImpl.parse` → `TaskTriggerSupport.trigger(…, "解析")`：

1. 按 `fileResultId` 取文件结果，取不到抛 **40432**；过归属校验；
2. **存储一致性校验**（`TaskTriggerSupport.trigger` 的第一行，五个环节共用 `ChainStorageSupport.requireStorageMatch`）：链的源文件所在数据源与当前启用的数据源不一致 → **40453**，消息「该任务属于 MinIO，当前启用的是本地，无法继续执行」；判定细节与豁免情形见 `../组装环节/03-接口逻辑.md`；
3. 按**执行键**查任务：解析是链路起点，没有上游也没有策略，执行键就是「文件结果 + `PARSE` + 0 + 0」（两个 0 哨兵分别表示"没有上游"与"该环节无策略"），一份文件结果只解析一次：
   - **查到**（任何状态，含执行中）→ 抛 **40431**，消息「解析任务已创建（taskId=…，状态 …），请勿重复触发」，**不返回既有结果**；
   - **查不到** → 新建一条 `QUEUED` 任务（`upstream_product_id` / `strategy_version_id` 都写 0 哨兵）并入队；
4. **入队写不进队列时**（Redis 故障）该新任务立刻落 `FAILED`（`TASK_ENQUEUE_FAILED`，文案"任务入队失败，请重试"）并把异常继续抛出（触发未成功）——库里不留"排不上队"的 QUEUED 任务。

解析环节的接口**不接受** `strategyVersionId` 与 `upstreamProductId`（链路起点没有上游，本环节也没有策略；多传的参数被忽略）。

**失败即终局，不允许原地重跑**：要把同一份文件再解析一次，走**重新提交文件**这条路 —— 同一份文件重复提交会产生新的 `file_result`（`wb_source_file` 复用），新 `file_result` 就是新的执行键，于是出现第二条解析运行，旧任务与旧产物一律保留。

**滞留兜底**：入库未入队、或入队后没被消费的任务由 `TaskStartupCompensator` 兜住——启动补偿一次（补投创建时间早于 5 分钟的 `QUEUED`）+ 低频周期扫描（`knowledge.task.low-freq-sweep-enabled`，**默认开启、间隔 1 分钟**，多实例用 Redis 锁防重）；同时把 `RUNNING` 超时的孤儿任务置 `FAILED`(`EXECUTOR_TIMEOUT`)。补投完全归补偿器，触发入口不再承担唤醒。

**服务停机**：先停领批 → 给在跑任务最多 `knowledge.task.shutdown-wait`（默认 30s）完成 → 到点中断并把仍未结束的任务显式置 `FAILED(TASK_SHUTDOWN_INTERRUPTED)`（条件更新，runner 已写终态则不覆盖）；`kill -9`/断电等硬停不做任何收尾，仍由启动时的 RUNNING 孤儿恢复兜底。两个池是具名 `ThreadPoolTaskExecutor` bean（`taskWatchdogExecutor` / `taskRunnerExecutor`），上面那句"最多等 `knowledge.task.shutdown-wait`"就落在它们的 `awaitTerminationSeconds` 上；环节超时取值同样按归一化环节名查（`knowledge.task.timeout.*`）。Spring Boot 自动给这两个池打点 `executor.*` 指标；`/actuator/health` 与 `/actuator/metrics` 当前都免认证（本地排查用，对外暴露前请自行收紧），端点暴露范围由 `management.endpoints.web.exposure.include=health,metrics` 决定。

## `GET /file-results/{id}/parse-detail`

`ParseControlServiceImpl.parseDetail`：

1. 取文件结果（40432）→ 归属校验；
2. `TaskDetailSupport.resolveTask` 解析目标任务：传了 `taskId` 用它，并校验它属于该文件该环节（否则 **40001**）；不传取该环节最新任务；
3. 组装 `ParseDetailVO`：任务状态、起止时间、错误码与说明、子步骤列表；
4. 按 `task.productId` 取该次运行的产物（历史任务同样可展示自己的产物），产物存在时读产物本体汇总：
   - `warnings` 取产物的质量告警清单；
   - `parseStats` 与 `parseSummary` 由 `ParseStatsSupport` 生成（见下）。

### 解析统计汇总（`ParseStatsSupport`）

执行树的解析节点与解析详情**共用同一份口径**，两处展示不会走偏。纯读取，不落库、不改产物。

| 方法                                        | 做什么                                                                                                                                                                                                                                                                       |
|---------------------------------------------|------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| `readArtifact(fileStorage, artifactId)`     | 读产物本体；产物引用为空、对象读不到、JSON 解析失败**一律返回 null**（不抛异常，详情照常返回）                                                                                                                                                                               |
| `stats(startedAt, finishedAt, parseResult)` | 元素构成按顶层元素类型归类：正文 = `PARAGRAPH` + `LIST` + `FIGURE_CAPTION`，表格 = `TABLE`，图片 = `IMAGE`，页眉页脚 = `HEADER` + `FOOTER`；页数优先取解析器回填的判定单元数、缺失回落文件引用的页数；问题单元取质量清单去重升序后的**数量与始末单元号**；耗时由起止时间相减 |
| `summary(errorMsg, stats, status)`          | 结论文案（见下表）                                                                                                                                                                                                                                                           |

`summary` 的分支：

| 状态                                              | 结论                                                                   |
|---------------------------------------------------|------------------------------------------------------------------------|
| `FAILED`                                          | `errorMsg`，为空时「解析失败」                                         |
| `SUCCESS` / `PARTIAL_SUCCESS`，且统计缺失         | **空**（产物不可读时不陈述结论 —— 「无异常」的断言只在统计到手时成立） |
| `SUCCESS` / `PARTIAL_SUCCESS`，问题单元数为空或 0 | 「无异常」                                                             |
| `SUCCESS` / `PARTIAL_SUCCESS`，有问题单元         | `N 单元未解析出内容（第 a–b）`                                         |
| 其余（`QUEUED` / `RUNNING`）                      | 空                                                                     |

## 解析产物口径（元素类型与判定）

产物元素来自解析器（PDF 走 `PdfBoxDocumentParser`，Office 走 POI 三个解析器），下面写**产物里字段的语义与判定口径**，判定细节在 worker 侧。

### 元素类型与正文流

| 类型                   | 产出时机                                                                       | 是否进正文流                             |
|------------------------|--------------------------------------------------------------------------------|------------------------------------------|
| `PARAGRAPH`            | 正文行按行距聚合                                                               | 是                                       |
| `TABLE` / `TABLE_CELL` | 表格候选块（见下）                                                             | 是                                       |
| `HEADER` / `FOOTER`    | 页眉页脚带内的跨页重复文本、页码行                                             | **否**（不进正文流，元素本身留在产物里） |
| `IMAGE`                | 图片引用：Office 逐个内嵌图片；PDF 产出**占页面积 ≥ 5%** 的图片（带本页 bbox） | 是                                       |

图片元素统一带 `needsOcr=true` 与来源溯源（PDF 为 `pdf#page(n)/image[i]`，Office 为 `office#...`）；`OCR_IMAGE` 事实**聚合产出**（PDF 按页一条、DOCX 按段一条、DOC 整档一条，证据带张数）→ 告警码 `IMAGE_TEXT_UNRECOGNIZED`（仅告警，不计失败单元）。PDF 的图片元素按页内自上而下追加在本页正文之后，位置靠 `bbox` 与溯源还原；面积门槛由 `imageMinAreaRatio`（默认 0.05，Docling 位图阈值口径）控制，logo 与装饰小图不产元素。

### 表格识别的两条路径

1. **线框路径**（有边框表）：页面矢量线段按相交关系聚成线框区域，区域内线条求列 / 行边界，格内文本按「行中心落带 + 字符落列区间」归属；分隔线缺失处合并为跨格，产出 `rowSpan` / `colSpan`；`rows` / `cols` 取网格行列数。
2. **文本路径**（无边框表）：连续的多 token 候选行成块，token 起点聚类成列并做**支持度过滤**（一列需被足够比例的行支持），行内按「行左边界 + 内部列起点 + 行右边界」切格；该路径不产 `rowSpan` / `colSpan`。
3. **假表门限**：两条路径都要求网格非空单元格占比不低于门槛。
4. **表头判定**：首行含数字占比不超上限且表体含数字，或首行字号明显大于表体 → `headerRow = 0`；判不出时 `headerRow` 为 **null**（无表头，跨页续表合并时不跳行）。
5. **降级留痕**：规则失败或空白率过高时，块降级为段落，并在产物 `sources[].facts` 里留一条 `TABLE` 事实，证据文案区分「列对齐聚类失败」与「空白率过高」。

参与判定的阈值集中在 `ParseProperties`（`knowledge.parse` 前缀）：线覆盖比例、列支持度比例、列聚类容差比例（按块内最大字号折算）、空白网格占比门槛、表头首行含数字占比上限。

### Office 表格的取值与合并

- **Excel（XLS / XLSX）**：单元格取值走 `DataFormatter`，普通格按单元格显示格式输出（日期、百分比、千分位与界面上看到的一致）；**公式格先求值**，求值不可用（例如 `WEBSERVICE` 这类 POI 未实现的函数）时**回落到文件里的缓存值**，两者都拿不到才留空 —— 产出的单元格文本不会出现 `SUM(...)` 这类公式串。合并区域只在左上角单元格产元素并记 `rowSpan` / `colSpan`，区域内其余坐标不产元素。
- **DOCX**：行内列号按 `w:gridSpan` **推进**（横向合并格在 OOXML 里只对应一个 `w:tc`，其后仍是真实单元格），合并格之后的单元格照常产出、列号不错位；`cols` 取各行 `gridSpan` 之和的最大值。纵向合并按 `w:vMerge` 处理：`restart` 格产元素并回填 `rowSpan`，同列的 `continue` 格不产元素。
- 两条路径都把 `sheetName` / `row` / `col` / `rowSpan` / `colSpan` / `isHeader` 透出到 `extra`（口径见下文 stage-content 一节）。

### 分栏与阅读顺序

- **判定**：页内字符的横向覆盖做成直方图，其中**竖直覆盖比例低（≤ 0.25）、宽度够（≥ 10pt）**的横向带算栏沟；每栏还要满足最小字符占比（10%）与最小字符数（10），单页字符太少（< 100）时不做分栏。候选栏沟按宽度从大到小逐个试，加进去不会造出过细的栏才接受 —— 行尾参差形成的窄带不会当成栏沟。
- **切行**：字符先按 y 聚类（同 y 内保持产出顺序），再**在栏沟处的断口切行** —— 相邻字符之间出现断口（间隙达词间间隙口径）或起点回跳/重叠、且下一字符已落到另一栏（按字符中心归栏）时切一刀；同排的多栏文本（含长行溢出到邻栏、字符区间重叠）各成一行，**横跨栏沟的连续文本整行保留为跨栏行**（章标题、摘要标题这类排版）。
- **阅读顺序**：跨栏行把页面切成上下若干带，带内跨栏行在前，其余按「栏序 → 栏内纵向顺序」排列；没有跨栏行时就是「左栏整列 → 中间栏整列 → 右栏整列」。单栏行溢出栏宽不算跨栏行（排顺序时按行盒归属栏裁剪），长行不会把页面误切成上下带。
- **段落与表格不跨栏**：行序回跳（进入下一栏或下一带）时结算段落与表格块，于是双栏正文不会被拼成一段，也不会被判成一张两列表。
- **单栏页**（未判出栏沟）保持纵向顺序，与不分栏时一致。
- 阈值在 `ParseProperties`（`knowledge.parse` 前缀）：栏沟最小宽度、栏沟最大竖直覆盖比例、每栏最小字符占比、每栏最少字符数、单页最少字符数、最大栏数。
- 能力位：分栏与阅读顺序走 `PageLayoutAnalyzer` 端口（规则实现 `ProjectionPageLayoutAnalyzer`），页面几何事实由解析器组装，端口只依赖 JDK。

### 页眉页脚与页码

- 判定依据是「页顶 / 页底区域内的文本 + 跨页重复」：同一文本在 **≥ `runningTextMinPages`（默认 2）个不同页**的对应带内出现才判页眉 / 页脚；同一页重复出现只计一页。
- **页码**需同时满足四条：文本形态为纯数字（可带 `-` / `—`）或「第X页」、位于页底带、在 ≥ `pageNumberMinPages`（默认 2）页的页底带内**横向位置一致**（行中心相差 `pageNumberXTolerance` 内，默认 5pt）、且**内容空洞**——与该行正上方最近的正文行之间留有 ≥ 行高 × `pageNumberIsolationRatio`（默认 1.5）的空白。同一页页底带内出现多条纯数字行时**不判页码**；紧贴正文的页底数字行按正文处理，不进页码候选。
- **每页各产一条** `HEADER` / `FOOTER` 元素：文本取该页原行、带本页 `page` 与 `bbox`；处置交给预处理环节的 `HeaderFooterRule`（`KEEP` / `MARK` / `EXCLUDE`），解析环节不做剔除。
- 正文流只剔除**落在对应带内**的命中行；页眉带之外的同一文本行仍进正文。

### 单元判定与成功门槛

**判定单元**按格式折算（对齐 Azure 文档智能的页单位口径）：PDF 每页 = 1 单元；Excel（XLS / XLSX）每 worksheet = 1 单元；Word（DOC / DOCX）每 `officePageChars`（默认 3000）个非空白字符 = 1 单元，图片无页归属、统一记在首个单元。

单元指标（`PageMetric`）由解析器逐单元回填：非空白字符数、乱码率、CID 映射失败率（PDF 专有）、文字占比（PDF 专有）、矢量覆盖率（PDF 专有）、图片口径 —— **PDF 填图片覆盖占比**（图片矩形面积之和 ÷ 页面面积）与矢量覆盖占比（线段包围盒面积 ÷ 页面面积），**Office 填内嵌图片数**，两条图片口径互斥回填。乱码率认两类码点：不可读码点，以及占比达 30% 的可打印乱码带（拉丁补充区，字体缺 Unicode 映射时错位出的 `ÿþ¤` 落在这里）。信号判定按"先便宜后贵"逐单元取**首个命中**：

| 顺序 | 条件                                              | 结论                                                                                                                                    |
|------|---------------------------------------------------|-----------------------------------------------------------------------------------------------------------------------------------------|
| ①    | 整单元无文本（0 字符）且按图片口径判为含图片      | **扫描单元**：`SCANNED` → 计失败单元，登记扫描页                                                                                        |
| ②    | 整单元无文本且无图片，但矢量覆盖率 ≥ 5%           | **纯矢量单元**：`VECTOR_GRAPHIC` → 不计失败、登记空白页（告警码 `VECTOR_PAGE_SUSPECTED` 与真空白区分）                                  |
| ③    | 整单元无文本且无图片且矢量覆盖低于门槛            | **空白单元**：`BLANK` → 不计失败，登记空白页                                                                                            |
| ④    | 文字占比 < 5%，或（文字极少 < 50 字且有内嵌图片） | **疑似图片单元**：`IMAGE_LOW_RATIO` → 仅告警，不计失败                                                                                  |
| ⑤    | 乱码率 > 20%                                      | **乱码单元**：`GARBLED`；字符主要来自缺 Unicode 映射的 CID 字体（≥ 30%）时子类型单列 `CID_MAPPING_FAILED`；两者都计失败单元、登记失败页 |

"整单元无文本 + 含图片"落到扫描单元，于是 Office 的纯图文档（整档只有图片的 Word、只放图的 sheet）不再恒判成功。

**乱码口径**（`TextUtil`）：只认**不可读码点** —— 替换字符 `U+FFFD`、私用区、未分配码点、控制字符；全角标点与引号、假名、谚文、生僻字（CJK 扩展）、希腊/西里尔字母、数学符号、圈号与项目符号都算正常字符。分母为**非空白**字符数。已知盲区：字体缺 ToUnicode 时错位出的可打印 ASCII 垃圾码点合法，不在本判据覆盖内。

**成功门槛**（`ParsePipeline.evaluate`）：

1. 单元数为 0 → `PARSE_CORRUPTED`；
2. **内容单元** = 单元数 − 空白单元数；内容单元为 0（整篇空白）→ `PARSE_CORRUPTED`；
3. 内容单元全为扫描单元 → `SCANNED_UNSUPPORTED`；
4. 成功占比 = （内容单元 − 失败单元）÷ 内容单元；≥ `successUnitRatio`（默认 0.9）→ `SUCCESS`（无失败）或 `PARTIAL_SUCCESS`（有失败）；低于门槛 → `RATIO_BELOW_THRESHOLD`。

空白单元既不算成功也不算失败，只从分母里剔除；产物新增 `quality.blankPages`，新增告警码 `BLANK_PAGE`。判定阈值（`scanPageImageRatio`、`officePageChars` 等）集中在 `ParseProperties`。

### 统计口径（`ParseStatsSupport`）

- 页眉页脚 = `HEADER` + `FOOTER` 元素条数，**按页计数**（每页最多各一条）；
- 表格 = `TABLE` 元素数；正文 = `PARAGRAPH` + `LIST` + `FIGURE_CAPTION`；图片 = `IMAGE`；
- 页数、问题单元与耗时口径见上表。

## `GET /file-results/{id}/stage-content`

`StageContentQueryServiceImpl.stageContent`：

1. 取文件结果（40432）→ 归属校验；
2. 环节白名单校验：`stage` 为空或不在 `PARSE`/`STRUCTURE`/`PREPROCESS`/`CHUNK`/`EMBED` 内 → **40001**；
3. 解析目标任务（口径同解析详情）；
4. 归一参数：`docPage` 非正数或空 → 不做页过滤；`page` 非正数或空 → 第 1 页；`limit` 空或非正 → 默认上限 200，超过上限 1000 按 1000 截断；
5. 按 `task.productId` 取产物；无任务 / 无产物 / 无 `artifactId` 时直接返回空结果（`latest=false`，`items` 空）；
6. **过滤先于分页**：先按 `docPage` 把元素收窄到该文档页，再切片取当前页 —— 于是 `total` 与 `truncated` 都是「该页元素」口径；
7. `truncated` = 这一页之后还有内容。**判定不能写成 `page × limit < total`**：最后一页不满时（5 条按每页 2 条取第 3 页只回 1 条）`3 × 2 = 6` 不小于 5，会把「已到末页」报成还有内容；正确口径是「已取到的位移是否到达总数」；
8. 产物读取抛异常时记日志、返回空列表并把 `total` 置 0（不把异常抛给页面）。

### 文档页过滤的类型口径

元素页码在产物里是 `Integer`，而 HTTP 请求里的 `docPage` 是大整数（`Long`）—— 跨类型比较**永远不相等**，过滤会静默失效。读取侧统一按 `Long` 比较（Controller 里把 `Integer` 归一为 `Long`）。

### `extra` 里 Office 锚点的透出

`putOfficeAnchor` 把产物里的定位事实按非空并入 `extra`：`style`（Word 段落样式）、`sheetName`（工作表名）、`row` / `col`（单元格坐标，0 基）、`rowSpan` / `colSpan`（合并跨度）、`isHeader`。**产物结构与解析逻辑未变**，读取侧多给这几个字段。

其中 `row` / `col` / `rowSpan` / `colSpan` / `isHeader` 只出现在 `TABLE_CELL` 上，而条目只下发顶层元素 —— 这五个字段在解析环节当前取不到，单元格内容改由下一节下发。

### 表格单元格明细的下发

`parseExtra` 在元素带 `cells` 时（`TABLE` 内嵌单元格）把整份明细序列化进 `extra.cells`：**单元格数、文本与行列全部原样下发，不做截断**，前端按 `row` / `col` 渲染成网格。口径与预处理环节的 `extra.cells` 一致；代价是大表会让单条条目的响应体明显变大（`limit` 只约束条目数，不约束单条内的单元格数）。

## `GET /files/{fileId}`

`FileController.download`（`workbuddy-biz` 的 `com.workbuddy.biz.controller.file`，落在接口层）→ `FileServiceImpl.download`（`workbuddy-file`）：按 `fileId` 取文件元数据 → 设置 `Content-Disposition: attachment`（文件名按 UTF-8 编码）→ 流式写回字节。

- 该路径**不在放行名单**，要 `Authorization` 头；
- 接口直出字节、没有 `R` 信封；**业务失败时仍以 HTTP 200 + JSON 错误信封应答**，前端据 `Content-Type` 识别；
- 文件中心的对象 key 与 `wb_file_result` 的源文件引用是两套 ID，`/files/{fileId}` 认的是**文件对象 ID**（`FileResultVO.fileId`）。

## 错误码

| code  | 语义                                                   |
|-------|--------------------------------------------------------|
| 40001 | 参数错误：环节不在白名单、`taskId` 不属于该文件该环节  |
| 40101 | 未认证或令牌无效：无登录上下文                         |
| 40401 | 知识库不存在 / **越权访问**（两者响应一致）            |
| 40431 | 已有同执行键的任务（任何状态都拒），请勿重复触发       |
| 40432 | 文件结果不存在                                         |
| 40453 | 链的源文件所在数据源与当前启用的数据源不一致，触发被拒 |
| 40500 | 系统异常兜底                                           |
