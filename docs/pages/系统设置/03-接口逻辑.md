# 接口逻辑

本文件写「后端拿到请求之后到底做了什么」。入口是 `StorageSourceController`，业务编排全在 `StorageSourceServiceImpl`，运行时的持有与探活在 `StorageRouter`，链与当前启用的比对在 `ChainStorageSupport`。通用机制（错误码分段、鉴权、公共字段填充）见 `../../README.md` 的「全局约定」章。

## 一、生效值与数据源

| 概念             | 取值来源                                                                                                                                                            |
|------------------|---------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| 当前启用的数据源 | `StorageRouter` 持有的 `currentSourceId`，由启动初始化与设为当前接口标记                                                                                            |
| 数据源行         | `kb_storage_source`：一行一个实例，连接参数落在 `config_json`，`status` 决定启动时是否注册进运行时                                                                  |
| 新对象写到哪     | `StorageRouter.writer()` 与 `currentFileBucket()` / `currentArtifactBucket()`：都取当前启用那一行的定义与参数                                                       |
| 读取按什么       | 记录里的 `storage_source_id` → `StorageRouter.of(sourceId)`；桶名取自记录                                                                                           |
| 配置文件         | `file-center.minio.*` / `file-center.local.*` 只在数据源表为空时作 seed 来源、在表里没有可用行时作回落注册；`file-center.storage-type` 指明 seed 后哪一行是当前启用 |
| 存储类型码值     | `kb_storage_source.storage_type` 与各对象记录的 `storage_type`：展示（`storageTypeName`）与读路径降级用                                                             |

三条边界：

- **库里的类型码值认不出时报 `40455`，不静默换成别的类型**：`StorageSourceServiceImpl.defOf` 认不出的行不能设为当前。
- **行上的 `is_current` 与进程内的当前启用是两件事**：前者是持久值，后者由 `StorageRouter` 持有，两者由设为当前接口在同一事务附近一起改。
- **`config/workbuddy-file.yml` 的 `file-center` 段不在写入路径上**：页面的写动作只落 `kb_storage_source` 的 `is_current` 与这次探测的结论两列，配置文件始终不动；数据源行本身由 seed 或库内 SQL 维护。

## 二、启动初始化

`StorageSourceServiceImpl.initialize` 带 `@PostConstruct`：

1. 取全部未删除的行；**一行都没有时按 `FileCenterDefaults.seedDefs` 落两行**：名称 `MinIO`（类型 `minio`，参数取 `file-center.minio.*`）与名称 `本地磁盘`（类型 `local`，参数取 `file-center.local.*`），主键由 `IdWorker.getId()` 生成且落库与注册共用同一个 ID，状态 `ENABLED`，`is_current` 给 `file-center.storage-type` 指明的类型那一行（码值非法时 `FileCenterConfig.defaultType` 抛 `40500`，启动失败）。参数里的空白值在建定义时就被 `StorageSourceDef.normalize` 丢掉。
2. 状态为启用的行逐条经 `registerRow` 注册进 `StorageRouter`：注册只登记定义（主键、名称、类型、参数），**不建连接、不建桶**；类型码值认不出的行告警跳过，不拦住启动。
3. 在启用行里取第一条 `is_current = 1` 且类型码值可识别的行作为当前启用，分两条分支：
   - **取到**：`markCurrentWithProbe` 调 `StorageRouter.markCurrent` 取该行的后端并初始化（MinIO 建文件桶与产物桶、本地建存储根目录），成功后回写 `last_probe_ok = 1` 与 `last_probe_at`；探活失败先回写 `last_probe_ok = 0` 再把异常抛出，**应用启动失败**。
   - **取不到**（一行都没启用、或没有一行被标为当前启用、或标了但类型码值认不出）：`registerFallback` 按 `file-center.storage-type` 组装一条内置定义注册并标记为当前启用，这条定义**不落库**，它的 ID 不出现在清单里；这一步同样探活，并打一行告警。

启动期只探活**当前启用那一行**：当前启用是 `local` 时不去连 MinIO，其余启用行按需连接（切到它或读到它才建后端）。写入侧的探活只剩设为当前一处：`switchCurrent` 注册目标定义之后探活一次，不通过就整体不落库。

## 三、列表

`GET /system/storage-sources`（`list`）：取未删除的行（主键升序）逐条转 `StorageSourceVO`，**不做实时探测**。`registered` 读 `StorageRouter.registered(id)`，`probeOk` / `probeAt` 读行上的 `last_probe_ok` / `last_probe_at`，`configured` 由 `StorageSourceDef.missingKeys` 按库里已存值算，`params` 是这一行 `config_json` 解析后的全部参数。

这一条只读，不写库、不探活、不动运行时；页面按它取下拉候选与「当前启用」信息块的全部字段。

## 四、预览：只算影响面

`POST /system/storage-sources/{id}/current/preview`（`previewCurrent`）：

1. `requireSwitchable(id)`：`requireRow`（`40457`）→ 行状态不是 `ENABLED` 时回 `40458`（「<名称>」已停用，请先启用再切换）→ `defOf(row)` 组装定义并 `requireParamsComplete`（类型码值认不出 `40455`、参数缺项 `40001`）；
2. `countImpact(id)` 统计影响面（见第六节）；
3. 装响应：目标三项、当前启用的三项（读 `StorageRouter.currentSourceId`）与两个计数，`message` 形如「切换后属于 <切换前的当前启用名称> 的 N 个排队中、M 个执行中任务不可继续执行」。

**不落库、不切换、不探活**：预览不动 `kb_storage_source`、不动运行时的当前启用、不建后端。

## 五、设为当前启用

`POST /system/storage-sources/{id}/current`（`switchCurrent`）带 `@Transactional(rollbackFor = Exception.class)`：

1. `requireSwitchable(id)`，同预览；
2. 目标就是运行时当前启用项时直接返回：两个计数为 0，`message` 是「当前启用的已经是 <名称>」，不落库、不探活、不审计；
3. `countImpact(id)` 统计影响面；
4. `defOf(target)` → `register(def)`（换定义、丢弃缓存提供者）→ `probe(def)` 探活，失败回 `40459`，库与运行时都不动；
5. **先清后置**：`clearCurrent()` 清掉全表的 `is_current`，再 `markCurrent(id)` 把目标行置为当前启用，两次更新在同一事务内，随后 `recordProbe(id, true, now)` 回写这次探测结论；
6. 审计 `STORAGE_SWITCH`，对象类型 `STORAGE_SOURCE`、对象 ID 是目标数据源 ID，前摘要「当前启用 <切换前的名称>」、后摘要「当前启用 <目标名称>；不可继续执行的任务：排队中 N 个、执行中 M 个」；
7. `StorageRouter.markCurrent(id)`：取目标后端（此刻已注册、已探活）并替换进程内的当前启用，这一步之后新上传与新任务写目标数据源；
8. 装响应：目标三项、切换后的当前三项（等于目标）、影响面沿用第 3 步那一份，再补 `switchedSourceId` 与文案。

第 5、6 步在同一事务内：落库或审计任一步抛错整体回滚，`kb_storage_source` 不留半截状态；**第 7 步排在审计之后**，审计写失败时库值回滚、进程内的当前启用仍停在切换前的数据源。`is_current` 在库上没有唯一约束，靠第 5 步的两次更新维持「全表至多一行」。

## 六、影响面统计

`countImpact` 由预览与切换共用，统计「属于其他数据源且未落终态的任务」：

1. `KbPipelineTaskDbService.listByStatuses` 按 `QUEUED` 与 `RUNNING` 一次取回所有未落终态的任务；
2. 任务的 `fileResultId` 去重后交给 `ChainStorageSupport.chainSourceIdsOf` 取链的数据源 ID：「`kb_file_result` 按 ID 集合查一次 → `kb_source_file` 按来源文件 ID 集合查一次 → 文件档案按 `fileId` 集合一次取回」，拼成「文件结果 ID → 数据源 ID」。**一次扫描三条语句**，与任务数无关；`fileResultId` 为空、集合为空都直接跳过，不生成 `IN ()`；
3. 逐条比对：链的数据源 ID 取不到（链路缺环、档案行缺失、档案没记数据源）或等于目标数据源的不计入；不同则按状态分别累加，`QUEUED` 进 `queuedCount`、`RUNNING` 进 `runningCount`。

口径上的两处：库里没有「按数据源」的任务索引，取数走「按状态全捞 + 逐条比对」；目标就是当前启用项时两个数字都是 0。

## 七、探测结论缓存

`last_probe_ok` / `last_probe_at` 是全表唯一一份连接状态，**只有两条回写路径**：

1. **启动初始化**：`markCurrentWithProbe` 探活当前启用那一行，成功写 `true`、失败先写 `false` 再把异常抛出（`recordProbeQuietly` 包住写库，写不进去只告警，不改判定）；
2. **设为当前**：`switchCurrent` 第 5 步在探活通过之后写 `true` 与当前时间。

清单接口只读这两列，页面据此渲染状态行的四态，`probeOk` 为 `null` 表示这一行还没被探过。库内 SQL 改坏了某一行的参数，页面上的状态行仍显示上一次的结论，直到该行下一次被设为当前或下一次重启探活。

## 八、密钥的返回与日志

- **入库**：`config_json` 原样存参数值，含 `minio` 的 `accessKey` / `secretKey`（列宽 2048）；`local` 没有密钥类参数。
- **完整返回**：`StorageSourceVO.params` 装的就是 `paramsOf(row)` 的全部参数，密钥类参数照常下发，接口与页面上都不做遮蔽；密钥值只出现在接口响应与页面参数行上，三个接口各自标着 `@AdminOnly`，仅有管理员能取到这份响应。
- **日志不落值**：服务端日志只打参数名与数据源名，不打参数值；`requireParamsComplete` 报缺项时逐个列出的是参数名。
- **参数名的口径**：`minio` 取 `endpoint` / `accessKey` / `secretKey` / `fileBucket` / `artifactBucket`；`local` 取 `rootDir` / `fileDir` / `artifactDir`，必填项的划分在 `StorageSourceDef` 里。

## 九、读取与写入的路由

| 路径                    | 取哪个后端                                                  | 桶名来源                                                              |
|-------------------------|-------------------------------------------------------------|-----------------------------------------------------------------------|
| 新上传、新产物、新头像  | `StorageRouter.writer()` = 当前启用的数据源                 | 当前启用那一行的参数（`currentFileBucket` / `currentArtifactBucket`） |
| 读已有对象              | 记录里的 `storage_source_id` → `StorageRouter.of(sourceId)` | 记录里的桶名，不由定义回填                                            |
| 记录里的 `storage_type` | 展示（类型徽标、`storageTypeName`）与读路径降级             | —                                                                     |

注册表按数据源 ID 存定义，未注册的 ID 回 `40455`，**不回落成当前启用的数据源**。写入时记录同时落 `storage_source_id` 与 `storage_type`（`DefaultFileStorage.putFile`、`AbstractFileStorage.putObject` / `putRaw` 返回的 `ObjectRef` 带 `sourceId` 与 `type` 两项）。

## 十、门禁与「切回即可继续」

数据源只决定**新上传与新任务**写到哪里，已有产物按记录里的数据源 ID 读，读路径不受切换影响。写路径有两道同一份判定的门禁，都调 `ChainStorageSupport.requireStorageMatch(fileResultId)`：

| 入口                     | 位置                                  | 拦住什么                                                      |
|--------------------------|---------------------------------------|---------------------------------------------------------------|
| 环节触发（五个环节共用） | `TaskTriggerSupport.trigger` 的第一行 | 手动触发被拒，`40453`，消息带链的数据源名与当前启用的数据源名 |
| 产物落库（各执行器共用） | `ProductPersistence.persist` 的第一行 | 排队补投后才执行到的任务在写产物那一步被拒，任务落 `FAILED`   |

第二道是排队与执行之间发生切换时的兜底：触发时一致、执行时已切走，产物不会写到另一个数据源上。任务失败时的错误码由 `TaskRunnerSupport.failureCode` 归口，数据源不一致（异常自身是 `40453`）写成**任务级** `TASK_STORAGE_MISMATCH`，其余情况用该环节的兜底码。

判定取「链的数据源 ID」与「当前启用的数据源 ID」两侧，**任一侧取不到都不算不一致**（链路缺环、`fileId` 为空、档案未记数据源、当前没有启用的数据源 → 放行），把这类情况交给读取阶段报更明确的码。

**知识库级索引构建不走 `ProductPersistence.persist`**，不带这道门禁：索引产物写给向量引擎，不落在文件服务的写入后端上。把当前启用切回链所属的那个数据源后，被拒的环节触发恢复正常；已经落 `FAILED` 的任务属终局，要接着跑得按**新的执行键**发起（换上游产物或换策略版本，解析环节则重新提交文件）。

## 十一、涉及的表

| 表                                                     | 用途                                                                                                                                                           |
|--------------------------------------------------------|----------------------------------------------------------------------------------------------------------------------------------------------------------------|
| `kb_storage_source`                                    | 数据源本体：`name`（唯一）/ `storage_type` / `config_json` / `is_current` / `status` / `last_probe_ok` / `last_probe_at` / `del_flag` 与创建人时间、更新人时间 |
| `kb_pipeline_task`                                     | 影响面统计：按状态取未落终态的任务，再按链的数据源 ID 比对                                                                                                     |
| `kb_audit_log`                                         | 切换留痕：动作 `STORAGE_SWITCH`，对象类型 `STORAGE_SOURCE`，对象 ID 是目标数据源 ID                                                                            |
| `kb_file_result` / `kb_source_file` / `kb_file_object` | 链的数据源来源：文件档案记数据源 ID，「文件结果 → 来源文件 → 文件档案」三段批量取回                                                                            |
| `kb_system_setting`                                    | 键值形态的设置表留在库里，本页的读写都不碰它                                                                                                                   |

表结构定义见 `../../../workbuddy-biz/src/main/resources/sql/README.md` 与同目录的 `init.sql`。
