# 接口逻辑

本文件写「后端拿到请求之后到底做了什么」。涉及的表是 `wb_user`，字段定义见 `../登录认证/03-接口逻辑.md`，此处不复述；通用机制（错误码分段、鉴权、令牌版本）见 `../../README.md` 的「全局约定」章。

## `GET /user/profile`

`UserController.getUserProfile` → `UserServiceImpl.getUserProfile`：

1. 取当前登录用户主键（`SecurityUtil`，无认证上下文即 40101），按主键查库。
2. 查不到抛 **40105**；查到则转 `UserVO`（不含密码）返回，外层 `R.ok`。

## `PUT /user/profile`

`UserController.updateProfile` → `UserServiceImpl.updateProfile`：

1. 同上取主键、查库、查不到抛 40105。
2. 先按**当前值**生成审计前摘要（角色 + 状态），再写入：
   - `displayName` 原样落库（非空与长度由 `ProfileUpdateRequest` 的参数校验保证）；
   - `email` / `phone` 走 `StrUtil.trimToNull`——**只有空白的输入按 `null` 存**，避免库里留下 `" "` 这种"看着填了、实际是空白"的值。
3. `WbUserDbService.updateById` 落库（`update_time` 由自动填充更新）。
4. 审计落一条 `USER_UPDATE`，带前后摘要。
5. **改资料不动令牌版本**，保存后无需换令牌，其他设备也不受影响。

## `PUT /user/password`

`UserController.changePassword` → `UserServiceImpl.changePassword`：

1. 取当前登录用户主键（同上），按主键查库，查不到抛 40105。
2. `PasswordEncoder.matches(当前密码, 库中哈希)` 不符则抛 **40110**。
3. 新密码再与库中哈希比对一次，相同则抛 40001（自定义消息「新密码不能与当前密码相同」）。
4. 新密码 BCrypt 编码落库，并**递增 `token_version`**——该账号此前签发的令牌（含本次请求用的那张）全部失效。
5. 用新版本**补签一张令牌**随响应返回，当前会话无需重新登录；补签沿用**本会话剩余时长**（下限 1 小时），既不延长也不缩短会话。
6. 审计落一条 `USER_PASSWORD_CHANGE`（中文名「修改密码」），**前后摘要都为空**：不落任何密码相关内容。

## 头像三个接口

库里存的是**对象 key**（`avatar/{userId}/{随机段}.{扩展名}`）**与数据源 ID、存储类型码、桶名**，不是 URL —— 绝对地址与部署拓扑（容器内的主机名、桶权限、会过期的预签名地址）耦合。对外一律由 `AvatarUrlUtil.readUrl` 换成 `/user/avatar/{id}?v={版本段}`。

1. **上传**（`AvatarController.upload`）：校验大小与文件头 → 生成新 key → `FileStorage.putRaw(key, …)` 写入当前启用的数据源 → `wb_user` 的 `avatar` / `avatar_storage_source_id` / `avatar_storage_type` / `avatar_bucket` 四列落库（数据源 ID 记下这份头像落在哪个实例，类型码随行保留用于展示）→ 返回新地址。每次上传换新 key，路径不可变、可长缓存，也就不存在"换了头像还在用旧图"。
2. **移除**（`remove`）：`avatar` / `avatar_storage_source_id` / `avatar_storage_type` / `avatar_bucket` 四列一并清空。**已上传的对象不删除** —— `StorageProvider` 只有 `put`/`get`/`exists`，没有删除能力；头像文件很小，留待将来加清理。
3. **读取**（`read`）：查 `wb_user` 的 `avatar` / `avatar_storage_source_id` / `avatar_storage_type` / `avatar_bucket` 四列 → 未设置、用户不存在、四列不完整或对象读不到都回 `404` → 四列齐全时按记录里的**数据源 ID** 定位后端取流（`FileStorage.getObject`），按扩展名给 `Content-Type`；记录里的数据源不是当前启用项也能读到。
4. 类型按**魔数**判定（PNG `89 50 4E 47`、JPEG `FF D8 FF`、WebP `RIFF….WEBP`），不信任客户端给的 Content-Type。
5. 登录（`AuthServiceImpl`）与资料接口（`UserServiceImpl.toUserVO`）都会把 key 换成地址下发，壳与横幅拿到的是**可直接渲染**的路径。

**头像三个接口都不受存储门禁约束**：门禁只设在会写对象产物的五个环节，比对「链的源文件所在数据源」与「当前启用的数据源」，不一致即 **40453**；头像的上传、读取、移除都不经过这道校验，切换数据源后旧头像照旧显示。

## 关于「更新时间」的全局口径

`update_time` / `update_by` 由 `KnowledgeMetaObjectHandler.updateFill` 填充，它**必须覆盖写**（本项目重写了 `fillStrategy`）：MyBatis-Plus 默认的 `fillStrategy` 与 `strictUpdateFill` 一样是"**有值不覆盖**"，而项目里主流写法是"先查出来改几个字段再 `updateById`" —— 实体自带库里的旧值，默认策略会把旧值原样写回 SET 子句：UPDATE 执行成功、时间不动；显式赋值还会让 DDL 上的 `ON UPDATE CURRENT_TIMESTAMP` 失效。**这条对所有实体生效**，不只用户资料。

## 审计动作

| 动作                   | 触发   | 摘要                             |
|------------------------|--------|----------------------------------|
| `USER_UPDATE`          | 改资料 | 前后摘要（角色 + 状态）          |
| `USER_PASSWORD_CHANGE` | 改密   | 前后都为空，不落任何密码相关内容 |
