# 接口逻辑

本文件写「后端拿到请求之后到底做了什么」。涉及的表是 `wb_file_result`（文件结果）、`wb_knowledge_pipeline_task`（环节任务）与 `wb_knowledge_pipeline_product`（产物），字段定义见 `../知识库列表/03-接口逻辑.md`；通用机制（错误码分段、鉴权、分页、归属校验）见 `../../README.md` 的「全局约定」章与 `../解析环节/03-接口逻辑.md`，本页不复述。

## Controller 划分

| Controller                         | 管什么                                                                                                   |
|------------------------------------|----------------------------------------------------------------------------------------------------------|
| `KnowledgeFileStructureController` | 组装环节专属：触发组装 `POST /{fileResultId}/structure`、组装详情 `GET /{fileResultId}/structure-detail` |
| `KnowledgeFileStageController`     | **各环节共用**的产物内容 `GET /{fileResultId}/stage-content`（白名单五环节同一入口）                     |

两者都以 `/file-results` 为类级前缀。归属校验（`FileResultAccessGuard`）与解析环节同源，覆盖 `/file-results/{fileResultId}/...` 前缀的全部接口。

## `POST /file-results/{id}/structure`

`KnowledgeFileStructureController.structure` → `StructureControlServiceImpl.structure`：

1. 按 `fileResultId` 取文件结果，取不到抛 **40432**；过归属校验；
2. 解析上游解析产物 `requireParseProduct`：`upstreamProductId` 必填，未给 → **40436**；按它取产物并校验存在、环节为 `PARSE`、且属于该文件结果（任一不满足 → **40432**）；**下游门禁**：该产物的产出任务必须是 `SUCCESS` 或 `PARTIAL_SUCCESS`（`UpstreamProductGate`），否则 **40439**「上游产物来自未成功的运行（状态 X），请重新触发上游环节」——`PARTIAL_SUCCESS` 放行并记一条 warn，挡的是「任务 FAILED 但产物已写入」的孤儿产物；
3. 任务行缺该引用（历史任务或异常造的任务）→ 执行期落 `FAILED`(`TASK_UPSTREAM_MISSING`)；
4. **存储一致性校验**（`TaskTriggerSupport.trigger` 的第一行，五个环节共用 `ChainStorageSupport.requireStorageMatch`）：链的源文件所在数据源与当前启用的数据源不一致 → **40453**，消息「该任务属于 MinIO，当前启用的是本地，无法继续执行」（两侧取数据源显示名，名称取不到时回落存储类型显示名）；把当前启用切回该数据源即可继续。档案行缺失、档案没记数据源 ID、当前没有启用的数据源时都不拦，交给读取阶段报更明确的错误码。产物写入前还会再校验一次（同一道校验下沉到 `ProductPersistence.persist`）：排队补投、切换数据源之后才执行到的任务，会在写产物那一步被拒，任务落 `FAILED`(`TASK_STORAGE_MISMATCH`)。
5. `TaskTriggerSupport.trigger(…, "组装")`：按**执行键**（文件结果 + `STRUCTURE` + 上游解析产物 ID + 0；组装无策略，策略位写 0 哨兵）查任务——**查到就抛 40431**（消息「组装任务已创建（taskId=…，状态 …），请勿重复触发」，不因任务状态分流、也不返回既有结果），**查不到**才新建一条 `QUEUED` 任务（`upstream_product_id` 记下这次选定的解析产物、`strategy_version_id` 写 0）并入队；**入队写不进队列时**（Redis 故障）该新任务立刻落 `FAILED`（`TASK_ENQUEUE_FAILED`，文案"任务入队失败，请重试"）并把异常继续抛出（触发未成功）——库里不留"排不上队"的 QUEUED 任务。

**旧任务与旧产物一律保留**：同一份文件的多次组装各自独立，血缘上表现为同一份文件上的多条组装运行。**失败即终局，不允许原地重跑**：想再组装一次，就换上游解析产物（从另一张解析卡片发起）——执行键不同即新链路；从同一张解析卡片反复触发只会拿到 40431。

**滞留兜底**：入库未入队、或入队后没被消费的任务由 `TaskStartupCompensator` 兜住——启动补偿一次（补投创建时间早于 5 分钟的 `QUEUED`）+ 低频周期扫描（`knowledge.task.low-freq-sweep-enabled`，**默认开启、间隔 1 分钟**，多实例用 Redis 锁防重）；同时把 `RUNNING` 超时的孤儿任务置 `FAILED`(`EXECUTOR_TIMEOUT`)。单条任务的滞留上限约为 5 分钟门槛 + 1 分钟周期；**补投完全归补偿器**，触发入口不做唤醒。

**服务停机**：先停领批 → 给在跑任务最多 `knowledge.task.shutdown-wait`（默认 30s）完成 → 到点中断并把仍未结束的任务显式置 `FAILED(TASK_SHUTDOWN_INTERRUPTED)`（条件更新，runner 已写终态则不覆盖）；`kill -9`/断电等硬停不做任何收尾，仍由启动时的 RUNNING 孤儿恢复兜底。两个池是具名 `ThreadPoolTaskExecutor` bean（`taskWatchdogExecutor` / `taskRunnerExecutor`），上面那句"最多等 `knowledge.task.shutdown-wait`"就落在它们的 `awaitTerminationSeconds` 上；环节超时取值同样按归一化环节名查（`knowledge.task.timeout.*`）。Spring Boot 自动给这两个池打点 `executor.*` 指标；`/actuator/health` 免认证；`/actuator/metrics` 需携带登录凭证（`SecurityConfig` 默认拒绝），端点暴露范围由 `management.endpoints.web.exposure.include=health,metrics` 决定。

## `GET /file-results/{id}/structure-detail`

`StructureControlServiceImpl.structureDetail`：

1. 取文件结果（40432）→ 归属校验；
2. `TaskDetailSupport.resolveTask` 解析目标任务：传了 `taskId` 用它，并校验它属于该文件该环节（不属于则 **40001**）；不传取该环节最新任务；
3. `detailSupport.withTask` 填公共字段：任务状态、起止时间、错误码与说明、子步骤列表；
4. 按 `task.productId` 取该次运行的产物（历史任务同样可展示自己的产物）：有产物则填 `artifactId` / `contentHash` / `capabilitySnapshot`，并读产物本体汇总 `summary`（元素 / 标题 / 段落 / 表格 / 图片 / 关系 / 冲突 / 告警计数）、`warnings`（质量告警文案）、`conflicts`（主路与被裁决方）、`outline`（文档内容大纲）；
5. `stageStats` 与 `stageSummary` 由 `StructureStatsSupport` 现算（见下）；无任务或无产物时 `outline` / `warnings` / `conflicts` 是空列表、`summary` 与 `stageStats` 为 null、`stageSummary` 取决于状态（进行中为空）。

`stage-content` 的读取路径（白名单校验、参数归一、按 `task.productId` 取产物、过滤先于分页、`truncated` 口径）与解析环节同一份实现，区别只在组装元素的 `extra`：`level` / `page` / `rows` / `cols` / `bbox`，`alignKey` 是产物元素 ID。

## 组装执行链（`StructureTaskRunner` → `AssemblerPipeline`）

执行器领任务后读上游 `ParseResult` 产物，交给组装管线；管线是纯算法，不碰 DB 与对象存储：

| 步骤             | 做什么                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   | 产出                                                                                   |
|------------------|------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|----------------------------------------------------------------------------------------|
| ① 元素标准化     | `NormalizerImpl`：解析元素 → 统一元素（类型映射、全局 ID = 类型前缀 + 内容哈希、单元格嵌套、扩展区与溯源透传、目录行标记透传）                                                                                                                                                                                                                                                                                                                                                           | `UnifiedElement` 列表                                                                  |
| ② 去重与合并     | `DedupMergerImpl`：IoU + 文本相似度**双判定**，按来源顺序取舍；来源键语义为 `source` = 来源路名（`native` / `ocr` / …）、`provider` = 具体解析器；来源顺序属**临时口径**（接入第二路后改按证据裁决，业界无公开优先级表）；同框不同内容且无法裁决 → 两路都留并标 `PRIMARY` / `BACKUP` + 冲突记录                                                                                                                                                                                          | 元素列表 + 合并对数 + 冲突记录                                                         |
| ③ 阅读顺序       | `ReadingOrderResolverImpl`：有坐标元素按页分组、页内 XY-cut（横向切行带 → 带内纵向切块 → 块内递归）；无坐标元素保持解析顺序直通                                                                                                                                                                                                                                                                                                                                                          | 阅读顺序列表                                                                           |
| ④ 结构组装       | `StructureAssemblerImpl`：标题推定规则链（样式 → 章级 → 单级数字 → 多级数字 → 中文括号 → 中文顿号 → 字号加粗，命中即止；样式名锚定匹配且级数收敛到 1~9、编号规则需含 CJK 且有字号佐证才定级、模型兜底默认关闭）+ Excel 章节与表格交错插入、同级章节互为兄弟；**关系在跨页接续之后按最终元素表重建**（章节树 / 阅读顺序 / 单元格归属，关系端点保证落在存活元素上）                                                                                                                        | 标题（`type` / `level` / 判定证据）、候选计数、关系                                    |
| ⑤ 跨页接续       | `TableContinuationResolverImpl`：仅 PDF 表格；主规则 = 相邻页（按当前末页比较）+ 上页表尾 + 下页页首 + 表头可读且相似 + 列数已知且相同；表头或列数不可判定时不进主规则，放宽规则按参考行（表头不可读时用首行）的列宽模式一致 → 疑似接续；合并结果保留首页 `page` 与 `bbox`，跨页位置由 `pageRange` / `bboxes` 逐页累积，同一张表可链式跨任意页数；续页行按保留行序号重编号（表头未判定时不跳行，行数 = 声明行数 − 实际丢弃的表头行数）；`headerInherited` 仅在确实丢弃了续页表头行时置真 | 合并后的表格 + `CONTINUATION_OF` 关系 + 疑似计数                                       |
| ⑥ 溯源校验       | 统计可回溯元素占比并写进组装报告（可回溯 = 元素自身或其单元格带「文件引用 + 定位路径」；结构性节点 SECTION 不计入分母）                                                                                                                                                                                                                                                                                                                                                                  | 可溯源比例（溯源偏低阈值 80%，可由 `knowledge.structure.provenance-low-percent` 覆盖） |
| ⑦ 重复与噪声识别 | `RepeatNoiseMarkerImpl`：重复页（页文本 bigram Jaccard 超阈值）、重复段（相似度超阈值且长度达标，排除页眉页脚）、噪声页（无元素 / 仅图片 / 乱码率超阈值；页覆盖范围按 `pageRange` 计）——判定语义即"与之前所有同类项逐个比 Jaccard"，实现上按集合规模分桶剪枝（Jaccard 上界 = min/max）、集合按需从原文重建不常驻、配容量有界的缓存，另加"集合指纹相同且集合相等"的精确快车道                                                                                                             | 元素 `marks` 与页 `marks`（只标记，不改结构）                                          |

随后构建 `UnifiedDocument`：`documentInfo`（`documentId` = `doc-{fileResultId}`、源文件引用与类型、上游解析运行 ID、产物 `schemaVersion`、能力快照）、`pages`（取首个带页面尺寸的解析来源）、`elements`、`relations`；再挂 `quality`（冲突记录 + 五类告警：`TITLE_CANDIDATE` / `SUSPECTED_CONTINUATION` / `PROVENANCE_MISSING` / `NOISE_PAGE` / `ELEMENT_TYPE_UNMAPPED`）；其中 `NOISE_PAGE` 文案为「计数 + 最多 3 条样例（`页 N 原因`）+ 等」，完整逐页原因进日志。

### 关系类型

| 关系                | 由谁构建                             | 含义                                              |
|---------------------|--------------------------------------|---------------------------------------------------|
| `PARENT_CHILD`      | 结构组装（章节树）+ Excel sheet 归并 | 标题 / 章节节点指向其子内容                       |
| `NEXT` / `PREVIOUS` | 结构组装（阅读顺序）                 | 正文阅读顺序链，**页眉页脚排除在外**（仍在树内）  |
| `TABLE_CELL_OF`     | 结构组装                             | 单元格 → 所属表格                                 |
| `CONTINUATION_OF`   | 跨页接续                             | 续表后续页 → 首页；`from` / `to` 带 `#p页码` 后缀 |

`CAPTION_OF` / `DERIVED_FROM` 是字典里预留、当前不产出的类型。

### 终态与落库

`TaskRunnerSupport.complete` 按管线的建议状态分派：

- **成功**：写产物（对象存储 sha256 寻址）+ `wb_knowledge_pipeline_product` 行（`upstream_product_id` = 本次选定的解析产物）+ 子步骤记录，任务置 `SUCCESS`；
- **失败**（含空树与上游不可读）：**写子步骤记录、不写产物与产物行**，任务置 `FAILED` 并落 `errorCode` / `errorMsg`（原因截断到 1000 字符）。

空树判定在管线末尾：`elements` 为空 → `STRUCTURE_EMPTY` + 「无任何可组装元素（空树）」；**组装不产出 `PARTIAL_SUCCESS`**。上游失败有四种入口，统一落 `STRUCTURE_UPSTREAM_UNREADABLE`：任务未指定上游且该环节没有产物、产物对象读不出、产物 JSON 反序列化为空、解析产物本体或其文件信息缺失。

## 组装统计（`StructureStatsSupport`）

**统计在读取侧现算**：执行树的组装节点与组装详情共用同一份口径，纯读取，不落库、不改产物、不进能力快照。产物读不到时统计为 null，摘要为 null —— 「结构可用」这类断言只在统计到手时成立。

- `readDocument(fileStorage, artifactId)`：产物引用为空、对象读不到、JSON 解析失败一律返回 null；
- `stats(startedAt, finishedAt, document)`：按产物现算全部键（键名与含义见 `02-接口交互.md`）；`chapterCount` 按「有 `SECTION` 节点用章节节点数，没有时用一级标题数」；`withoutBboxCount` 是阅读顺序的推断口径；`continuationFromPage` / `continuationToPage` 从 `CONTINUATION_OF` 关系的 `#p页码` 后缀取最小 / 最大页；`suspectedContinuationCount` 取关系 `detail` 标「疑似」的条数；`schemaVersion` 取 `documentInfo`；
- `summary(errorMsg, stats, status)`：失败取 `errorMsg`、进行中与统计缺失为 null、空树给「无任何可组装元素（空树）」、有异常项时按「结构可用 · 溯源偏低 N% · 疑似续表 N 处 · 重复与噪声待处置」拼接（阈值 80 与产物告警同源）。

### 统计承载字段的划分

| 承载字段                               | 谁用                                                                                                      |
|----------------------------------------|-----------------------------------------------------------------------------------------------------------|
| 通用 `stats`（`StageStatsVO`）         | 组装节点的全部统计（含 `schemaVersion`，实际为 `StructureStatsVO`）；切片 / 向量化 / 预处理各自走对应子类 |
| 通用 `stageSummary`                    | 组装结论一句话                                                                                            |
| 解析专用 `parseStats` / `parseSummary` | 解析环节的固定统计结构与结论（组装不下发）                                                                |

**组装统计在通用统计之后落位**：`LineageQueryServiceImpl.toNode` 先构造本地通用 map（只覆盖切片 / 向量化 / 预处理），随后由 `fillStructureStats` 用组装统计**整份替换**，最后统一转成 `StageStatsVO`（组装节点实际为 `StructureStatsVO`）。顺序反过来会被那次空 map 覆盖，组装节点将没有任何统计；同理组装统计不做增量合并，一个组装节点的 `stats` 要么是完整组装统计，要么是空对象（产物不可读）。

## 只读字段的边界（现状）

- `structure-detail` 只给 `summary` / `warnings` / `conflicts` / `outline` 与公共任务字段，**不下发上游产物 ID**：左栏展示的是组装产物本身；
- `outline` 元素带 `cells`（表格行列明细），**不带溯源字段**：左栏排版不需要按溯源与上游对齐；溯源覆盖率只以统计形式出现；
- 执行树节点与组装详情都不下发 `upstreamProductId`，「基于哪次上游」由链图的边表达；
- `stage-content` 对组装环节的 `extra` 只有 `level` / `page` / `rows` / `cols` / `bbox`，元素身份走 `alignKey`。

## 错误码

| code  | 语义                                                                             |
|-------|----------------------------------------------------------------------------------|
| 40001 | 参数错误：环节不在白名单、`taskId` 不属于该文件该环节                            |
| 40101 | 未认证或令牌无效：无登录上下文                                                   |
| 40401 | 知识库不存在 / **越权访问**（两者响应一致）                                      |
| 40431 | 已有同执行键的组装任务（任何状态都拒），请勿重复触发                             |
| 40432 | 文件结果不存在；指定的上游产物不存在 / 环节不是 `PARSE` / 不属于该文件结果       |
| 40436 | 触发组装时没给 `upstreamProductId`（下游环节必填）                               |
| 40453 | 链的源文件所在数据源与当前启用的数据源不一致，触发被拒（消息带两侧数据源显示名） |
| 40500 | 系统异常兜底                                                                     |

任务级错误码落在 `wb_knowledge_pipeline_task.error_code`：`STRUCTURE_EMPTY`、`STRUCTURE_UPSTREAM_UNREADABLE`、`STRUCTURE_FAILED`。失败文案不落 `null`（异常无消息时退化为异常类名，业务异常直接用其原因）；上游文件或文件结果已不存在（`ErrorCode.FILE_NOT_FOUND` / `FILE_RESULT_NOT_FOUND`）无论从哪条路径冒出都归 `STRUCTURE_UPSTREAM_UNREADABLE`，其余执行异常归 `STRUCTURE_FAILED`。
