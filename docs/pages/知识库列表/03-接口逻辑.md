# 03 接口逻辑

## 可见范围的实现：一处定义、一个入口

列表页的口径要同时落在「查得到」和「改得动」两侧，实现不是一个 `WHERE`，而是三层：

| 层       | 位置                                                                              | 做什么                                                                    |
|----------|-----------------------------------------------------------------------------------|---------------------------------------------------------------------------|
| 规则     | `KnowledgeBaseRules.visibleOwnerId` / `checkAccessible`（`workbuddy-common`）     | 唯一口径来源：管理员不限归属，普通用户只能是自己创建的；越权抛 `40401`    |
| 应用服务 | `KnowledgeBaseServiceImpl` 的 `getAccessibleById` / `visibleOwnerId`              | **本类所有按 ID 的读写都必须走这两个私有方法**，漏一处就是越权口子        |
| 数据访问 | `KnowledgeBaseDbServiceImpl.pageByCondition` / `countByStatus` / `listIdsByOwner` | 收 `ownerId` 参数：**null = 不加条件（管理员），非 null = `user_id = ?`** |

三条实现约定：

- **无登录上下文一律拒绝**（`40101`），不把"没登录"退化成"不过滤"。
- **归属条件必须落在 `user_id` 上**：Lambda 引用写错（例如误用 `create_by`）不会报错，只会静默按别的列过滤，等于隔离失效。单测里直接断言生成的 SQL 片段含 `user_id =`。
- **越权按"不存在"处理**：`checkAccessible` 抛 `KB_NOT_FOUND` 而不是 `FORBIDDEN`。抛后者等于确认"这个库存在，只是不是你的"，会把别人的库 ID 变成可枚举、可探测的信息。

## 一、`page`

1. 取可见范围：`visibleOwnerId()`（普通用户 = 自己 ID，管理员 = null）。
2. 查询：`pageByCondition`，条件为 `name like ?`（关键字非空时）+ `status = ?`（传了才加）+ `user_id = ?`（ownerId 非空时），再按口径排序：
   - `UPDATED` → `update_time DESC, id DESC`；
   - `NAME` → `name ASC, id ASC`；
   - `DEFAULT`（含未知值）→ `id DESC`。
3. 回填三件（都是**批量**查询，与页大小无关，不做逐行查询）：
   - **策略摘要**：按类型各查一次绑定行，再批量取策略版本行，装配成 `name-version`；版本行已被删除的跳过（不返回半截数据）；
   - **文档数**：一次分组查询回填每库的 `kb_file_result` 行数，无记录的补 0 而不是留 null；
   - **已发布索引版本**：`kb_knowledge_base.published_index_set_id` → `kb_index_set.current_published_version_id` → `kb_index_version.version_no`，两次查询覆盖整页。
4. 逐行转 VO（`status` 返回码值，`strategyBindingEnabled` 把 null 归一化成 1）。

## 二、`stats`

用同一个 `ownerId`：

- `knowledgeBaseCount` = `countByStatus(null, ownerId)`；
- `enabledCount` = `countByStatus(ACTIVE, ownerId)`；
- `documentCount` = 先 `listIdsByOwner(ownerId)` 取可见库 ID，再 `countByKbIds(ids)`。

**文档数的实现路径**：`kb_file_result` 只有 `knowledge_base_id`，没有归属列，"按归属数文档"先换算成"按库集合数"。`countByKbIds` 对空集合返回 0，不生成 `IN ()` 这种非法 SQL。

## 三、`detail`

`getAccessibleById(id)`（存在性 + 归属）→ 逐类型查绑定并回填摘要与版本 ID → `countByKb(id)` 回填文档数。

## 四、`create`

1. **归属必须取得到**：当前用户为空（含 ID 为空）直接 `40101`，不落 `user_id = NULL` 的孤儿行。
2. 落库：`status = ACTIVE`、`strategyBindingEnabled` 归一化（null/非 0 视为开启，兼容存量）。
3. 写审计 `kb_audit_log`：动作 `CREATE`，对象 `KNOWLEDGE_BASE`，before 为 null，after 是新建实体的 JSON。
4. 返回新库 ID（`String`：雪花 ID 超 JS 安全整数，裸 Long 序列化成数字会被前端读丢末几位）。

## 五、`update`

`getAccessibleById` → 取 before JSON → 改名称/说明/绑定开关（开关同样做 null 归一化）→ `updateById` → 写审计 `UPDATE`（before/after 都有，可回溯改了什么）。**状态与绑定不在这里改**。

## 六、`disable` / `enable`

两者都是「校验 → 改状态 → 写审计」：

| 接口      | 校验顺序                                     | 审计动作  |
|-----------|----------------------------------------------|-----------|
| `disable` | 归属 → `checkCanDisable`（必须当前是启用态） | `DISABLE` |
| `enable`  | 归属 → `checkCanEnable`（必须当前是停用态）  | `ENABLE`  |

**停用的实际效果**：`knowledgeBase.status = 0` 后，提交入口的 `checkCanSubmit` 会抛 `40421`，即拒绝新文件接入（检索侧同样以启用态为前提）。历史数据、已发布索引都保留。

## 七、`delete`

`getAccessibleById` → **逻辑删除**（`BaseInfo.delFlag` 由 `@TableLogic` 自动补 `del_flag = '0'` 过滤、删除是 UPDATE 置 `DelFlag.DELETED`）→ 写审计 `DELETE`（after 为 null）。无恢复接口。

## 八、`bindStrategies`（三件套绑定）

1. `getAccessibleById` → 库关闭了策略绑定开关则 `40001`。
2. 逐项校验：类型在可绑定白名单内（预处理/切片/向量化，**检索不绑库**）、请求内类型不重复、**必须给全三件套**、每项版本非空。
3. 逐类型复用单类型绑定逻辑（`bindStrategy`）：解绑是绑定行逻辑删除；绑定是 **upsert 复用原行**（含已逻辑删除的行，避免唯一键被占用），并校验版本存在、类型匹配、状态为启用。
4. 每次绑定/解绑都写一条 `BIND` 审计（before/after 是 `类型=版本串` 的形式）。
5. 外层同一事务：任一项失败整体回滚，不会出现"绑了一半"。

## 九、文件提交的归属校验

`KnowledgeBaseServiceImpl.submit` 在幂等检查之后、建档三写之前，按 **存在/未删除 → 归属 → 启用** 的顺序校验；先归属后状态，错误码差异反推不出"别人某个库是启用还是停用"。归属不过报 `40401`。

这一步是"看不到也写不进"的关键：列表收窄只影响界面，接口本身仍按 ID 定位，不校验归属的话拿着别人的 ID 照样能建档。

## 涉及的表

| 表                                  | 用途                                                            |
|-------------------------------------|-----------------------------------------------------------------|
| `kb_knowledge_base`                 | 主表：名称/说明/状态/归属（`user_id`）/默认标记/已发布索引集合  |
| `kb_strategy_binding`               | 三件套绑定（含逻辑删除列 `del_flag`，码值见 `DelFlag`）         |
| `kb_pipeline_strategy_version`      | 策略版本行（取 `name` + `version` 拼摘要）                      |
| `kb_file_result`                    | 文档数（一次提交 = 一行）                                       |
| `kb_index_set` / `kb_index_version` | 已发布索引版本号回填                                            |
| `kb_audit_log`                      | 创建/更新/启停/删除/绑定的审计（写链路在 `AuditEventListener`） |
